# ADR 0046: A recovery-pending device-state stage for `rv recovery complete`

- Status: Proposed
- Date: 2026-10-11
- Deciders: project owner
- Milestone: M1

## Context

ROADMAP §4.3 "Recovery story written down and implemented" is an M1 Must; HANDOFF gap 12 tracks it as open. `rv recovery complete`'s own module docs (`crates/rizzy-cli/src/recover.rs`, "An open gap between two Accepted documents") report that it writes nothing to disk between confirming the new Emergency Kit and the server's acknowledgement of the commit, even though CRYPTO.md's normative "Secrets before commit" rule (just above §11.1) lists recovery (§11.9) among the flows that must run step 3, "A durable client (kind 1–3) persists a pending record in its device state," before step 4, "Upload." `rizzy-client`'s `recovery.rs` module docs read the absence of a prior device-state record as license to skip step 3 ("a recovering client has no device state before the commit, so there is no pending record to write"), citing the rule's exemption for a client that "holds no device state" — but that exemption is CRYPTO.md's text for the **web vault** (kind 4), not for a durable client enrolling for the first time. [ADR 0026](0026-client-device-state-and-cache.md) §2 defines a pending stage only for signup (`stage = 2`: the base fields are what signup is about to register) and a `pending` sub-record for an **already-committed** device changing its own credentials (password/SK change, rotation). Neither fits recovery: the recovering client is not registering a new account, and it has no prior committed record of its own to attach a `pending` sub-record to. `rv` therefore persists nothing, and its own docs say the cost: after a crash or an unknown-outcome answer between the send and the cache write, the server may have applied the recovery while this computer holds no record of it, and "`rv` cannot tell which kit is valid in that case."

The machinery to fix this already exists and needs no new ADR of its own: ADR 0028's retry table makes a byte-identical repeat of `account/commit` a success, and CRYPTO.md §11.9 step 3 lets `recovery/complete` "be repeated with the same token, until the step 6 replace commits." What is missing is a place in the device-state record to hold the recovering client's not-yet-committed secrets across a restart, the way signup and credential changes already do.

What binds: CRYPTO.md §11 "Secrets before commit" and "Replacing credentials"; §11.9; §5.9; §5.10; ADR 0012 §7 (certificate-carrying reconciliation); ADR 0026 §1–§5 (persisted vs. never persisted, write order, floors); ADR 0028 item 1 (paths), item 5 (`SessionKind::Recovery` carries a bearer token only, no `device-request` signature), item 6, and its Commit and Recovery retry-table rows; ADR 0021 §9 (the healing-only `record_conflict` code); ADR 0025 §1, §3 (the vault half's cursor check); ADR 0031 point 8 (the `setup_retired` restart); ADR 0045 (the pending-recovery field this ADR's resume cannot use, §3). Code (V, 5a78bb5): `crates/rizzy-client/src/{recovery,signup,device,reregister,rotation,login}.rs`, `crates/rizzy-client/src/store/{mod,record}.rs`, `crates/rizzy-cli/src/{recover,paths}.rs`, `crates/rizzy-domain-auth/src/{recovery,change,session,device,login,trust,error}.rs`, `crates/rizzy-domain-vault/src/{error,rotation}.rs`, `crates/rizzy-proto/src/auth.rs`, `crates/rizzy-server/src/http/api.rs`.

## Decision

### What this ADR supersedes

[ADR 0026](0026-client-device-state-and-cache.md) §2, §3 and §4, four parts, replaced in full:

- The whole `device_state` notation block of §2:
  ```text
  device_state = u16(record_version = 1) ‖ u8(stage: 1 committed | 2 signup-pending | 3 recovery-pending)
               ‖ str(server_origin) ‖ account_id (16) ‖ device_id (16) ‖ u8(device_kind: 1–3)
               ‖ secret_key (16) ‖ device_salt (16) ‖ u16(kdf_id) ‖ bytes(E_dev)
               ‖ u8(has_local: 0 | 1) ‖ [u32(local_account_key_epoch) ‖ u32(local_password_epoch) ‖ bytes(E_local)]
               ‖ u8(pending: 0 | 1) ‖ [pending]
  pending      = secret_key' (16) ‖ device_salt' (16) ‖ u16(kdf_id') ‖ u32(account_key_epoch')
               ‖ u32(password_epoch') ‖ bytes(E_local') ‖ bytes(E_dev' or empty)
  ```
- §2's "Parsing" bullet's sentence `` `stage = 2` requires `has_local = 1` and `pending = 0`. `` becomes: `` `stage = 2` or `stage = 3` requires `has_local = 1` and `pending = 0`, and neither stage carries a `pending` sub-record. ``
- §3's sentence `` `pending_commit.request` is the exact JSON body to send: a `CommitChangeRequest`, or a `RegisterFinishRequest` in stage 2. `` becomes: `` `pending_commit.request` is the exact JSON body to send: a `CommitChangeRequest` (a stage-1 pending record, or stage 3), or a `RegisterFinishRequest` in stage 2. ``
- §4 step 5's parenthetical `` (after the offline unlock; a state with `has_local = 0` or `stage = 2` does not unlock, §2) `` becomes: `` (after the offline unlock; a state with `has_local = 0`, `stage = 2` or `stage = 3` does not unlock, §2) ``.

Nothing else in ADR 0026 changes.

Two sibling M1-batch drafts partially supersede neighboring parts of the same sections: [ADR 0057](0057-device-state-v2-keystore.md) supersedes §1's "Device-state record" table row and §4 step 5's "Load" step (the same step this ADR's fourth bullet edits), and [ADR 0051](0051-equivalence-list-version-persistence.md) supersedes §3 (the same section this ADR's third bullet edits). Per [ADR 0020](0020-partial-supersession.md) point 9, whichever of this ADR, 0051 and 0057 is accepted last appends its own edit to ADR 0026's status line and to the overlapping text rather than overwriting the other's.

### 1. Stage 3: recovery-pending

Add `Stage::RecoveryPending = 3` beside `Committed` and `SignupPending` (`crates/rizzy-client/src/store/record.rs`). Like `SignupPending`, its base fields are the values the device holds once the commit lands: the new Secret Key, `device_salt`, `kdf_id` and `E_local` that `Reregistering::finish` already builds via `DeviceState::create` (CRYPTO.md §11.9 step 5), and the new `E_dev` for the new device keys. `DeviceRecord::parse`/`encode` require `has_local = 1` and refuse a nested `pending` record in stage 3, exactly as for stage 2. `DeviceRecord::unlock` refuses stage 3 (a new `ClientError::RecoveryPending`, mirroring `SignupPending`); a new `DeviceRecord::unlock_recovery_pending`, mirroring `unlock_signup`, opens the record for everything §3 below needs: the account key and the new device keys for the device-auth attempt, the Secret Key and new password for the OPAQUE-login probe, and `pw_in`/`E_srv`'s rebuild on a `setup_retired` restart. It is the single entry point for every branch of §3, not only the `setup_retired` one — the original draft budgeted it for that branch alone, which is corrected below. `RECORD_VERSION` stays 1: a build that does not know stage 3 reports `CacheCorrupt`, not `CacheUpdateRequired`, for such a record — accepted below (open question 2).

### 2. Persist before the send, not after

`PendingRecovery::store_writes` (`crates/rizzy-client/src/recovery.rs`) moves earlier: the host calls it and commits it as one cache transaction — `store::create_writes` for `cache_meta` and the stage-3 record, `Write::PendingCommit(Some(commit_json))`, `store::object_writes` for the bundle, certificate, self-grants and `E_id`, and `Write::Wraps` per vault — **before** `POST /api/v1/account/commit`, mirroring `PendingSignup::store_writes` (`crates/rizzy-client/src/signup.rs`) exactly. Both run only after `confirm_kit`, so the write never races the render-and-confirm step CRYPTO.md orders first. `rv recovery complete` (`crates/rizzy-cli/src/recover.rs`) opens the cache file and takes the account lock at this point, not after the server answers. Once the server acknowledges, the existing `finalize_writes` promotes the record to `stage = 1` and clears `pending_commit`, exactly as a signup's finalise does.

**Proposed INV-71** (client-side; allocated across the 2026-10-11 batch in ADR-number order — the owner may still relocate it into THREAT_MODEL.md §8 differently on acceptance). Provisional: the allocation was made across the 2026-10-11 batch in ADR-number order; if ADRs are accepted out of order, the owner renumbers at acceptance. A durable client holds at most one unconfirmed recovery commit's secrets on disk per account at a time. Before it generates a second, different Emergency Kit for the same account, it must first learn, through §3, that the first attempt's commit did not reach the server. Stage 3 exists to make that checkable instead of assumed.

(ADR 0045's `pending_recovery` field does not help this check: it rides the signed `account-state`, which a stage-3 client cannot fetch without a session it does not yet have — the very thing §3 is working out.)

**Finding the record on the next invocation.** The host no longer assumes a bare slate. Before `rv recovery complete` prompts for anything, it calls `enrolled_accounts` (`crates/rizzy-cli/src/paths.rs`, already used to list a data directory's cache files without knowing an account id in advance) and opens each. A stage-3 record for the server origin given hands control straight to §3's resume below — no login name or recovery code is asked for, because the record already carries the account id, device id and keys §3 needs. Only when no stage-3 record is found does `rv` fall through to today's flow: prompt for the login name and the recovery code, and call `recovery/start`/`recovery/complete` as before. The existing guard — `if cache_path(&env.data_dir, &account).exists() { return Err(CliError::AlreadyEnrolled) }` (`crates/rizzy-cli/src/recover.rs`) — now fires only once that fresh flow resolves to a **stage-1** record for the account; a stage-3 record is caught by the check above instead, and a fresh start after §3's abandon step finds no cache file at all (step 5 below), so the guard never wrongly blocks it.

### 3. Resuming a stage-3 record

On open, a stage-3 record does not unlock for ordinary use. §2's entry-point change puts the host here before any login name or recovery code is asked:

1. **Unlock first — every later step needs it.** Ask for the new master password just chosen in this attempt and call `DeviceRecord::unlock_recovery_pending` (§1). This cannot be deferred or skipped to save a secret re-entry: `offline_unlock` (`crates/rizzy-client/src/device.rs`) and CRYPTO.md §5.10 ("Device secret keys are wrapped under the account key") both require the account key, itself unwrapped from the password, before the device's own Ed25519 signing key can be read out of `E_dev'` at all — there is no path to device keys, and so no path to step 2 below, that skips this. The original draft's step 1 budgeted this unlock only for the `setup_retired` branch of the old step 3; every branch below needs it, an internal contradiction now fixed by asking once, first. A wrong password answers `ClientError::WrongPasswordOrSecretKey` locally; no round trip is spent.
2. **Device-auth short-circuit, with no `Reconciliation`.** Using the keys step 1 just unwrapped, attempt `device-auth/start`/`finish` (CRYPTO.md §5.10) with the stage-3 record's own device id, sending `reconciliation: None`. This matters: `device_key` (`crates/rizzy-domain-auth/src/device.rs`) only reaches the certificate-carrying reconciliation path (ADR 0012 §7) when the request supplies one, and that path can accept a *carried, not-yet-landed* certificate once a backup-reconciliation epoch is open — exactly the false positive this step must not risk. With `reconciliation: None`, `device_key` succeeds only through `devices.usable_durable`, i.e., only if the server's own stored device set already lists this certificate as not suspended, revoked or expired. Success is unambiguous: the commit landed and this device still stands. Finalise (promote to `stage = 1`, drop `pending_commit`) and continue as an ordinary unlock on an enrolled device (§11.3). A `401` is **not** proof the certificate was never stored: `usable_durable` (`crates/rizzy-domain-auth/src/trust.rs`) answers the identical `401` for an unknown device and for one that landed and was later revoked, suspended or expired — plausible once ADR 0045 notifies other devices of a completed recovery from an unrecognised one. (The uniform answer is CRYPTO.md §5.9's family, not ADR 0028 item 6, which governs already-sessioned requests; `device-auth/start` carries no session at all.) A `401` means only "try the next check" — go to step 3.
3. **The OPAQUE-login probe.** Before resending anything or touching the pending record, check whether the account's credentials actually moved, using the login every account already has — no new wire message, just `rizzy-client`'s existing `login::start_login`/`LoginStarted::finish` (`crates/rizzy-client/src/login.rs`) against the login name (asked for again, as `rv` already asks for every argument on each invocation) and the password step 1 just verified locally. Only a successful commit replaces the server's OPAQUE record under the new password, so:
   - **Login succeeds, or answers `AuthError::SecondFactorRequired`** (`crates/rizzy-domain-auth/src/login.rs` reaches that code only after OPAQUE's KE3 verifies, i.e., only once the password itself matched — no TOTP code is needed to learn this): the commit landed. Discard the resulting session without using it; finalise the stage-3 record (promote to `stage = 1`, drop `pending_commit`). If step 2's device-auth still fails afterward, this device needs the ordinary re-enrolment flow, not another recovery — out of this ADR's scope.
   - **Login answers plain `Unauthorized`:** the server's credentials are still the old ones; this attempt's commit did not land. Go to step 4.
   - **The probe cannot complete** (a network or server error, not a clean answer either way): leave the record in stage 3 and stop; the next `rv` invocation retries the whole procedure — the safe side, matching the Risks section's existing partition case.
4. **Resend through recovery.** Reached only once step 3 has ruled out "this attempt's own commit is already live." Ask the user to re-type the original recovery code (never persisted, ADR 0026 §1) and call `recovery/complete` again. `crates/rizzy-domain-auth/src/recovery.rs` answers `Unauthorized` alike for "an unknown name, a wrong code, or no pending recovery for this code," including after this very recovery committed — but step 3 already ruled that case out, so:
   - **Still pending:** a fresh `SessionKind::Recovery` bearer token (bearer-only; no signature to rebuild, ADR 0028 item 5). Resend the stored `pending_commit` bytes to `account/commit` byte-identically; a byte-identical repeat is success (ADR 0028's Commit row; CRYPTO.md §11). Finalise as in step 2.
     - **`state_conflict` on this resend.** Neither `VaultError` nor `AuthError` has a `record_conflict` variant for this endpoint: `ErrorCode::RecordConflict` is reserved for `vault/upload`/healing op-level conflicts (ADR 0021 §9 "Healing request"), a different endpoint; the vault half's stale-cursor check (`check_cutoff`, `crates/rizzy-domain-vault/src/rotation.rs`) and the account-state compare-and-swap (`AuthError::StateConflict`/`StateFork`) both answer `state_conflict` instead, with nothing in the response telling them apart. Abandon (step 5). Because step 3 already proved this attempt's own commit is not the live one, abandoning here cannot discard a live kit — the open question of telling "an unrelated vault write staled the cursor" apart from "an unrelated account change lost the CAS" (open question 4) no longer bears on safety, only on whether a rebuild-and-resend could have salvaged this one attempt.
   - **`Unauthorized` on this resend** (step 3 already ruled out "it landed as mine"): the pending recovery was cancelled, or raced by another credential change. Abandon (step 5).
   - **`setup_retired`** (ADR 0031 point 8): rerun `account/reregister/start` with `pw_in` already rebuilt in step 1, replace only `registration_upload` and `account_key_server_wrap` in the stored request, keep everything else, resend — the general rule CRYPTO.md §11 already states, unchanged here.
5. **Abandon, spelled out.** Drop, in one cache transaction, every row §2's pre-commit write created: `cache_meta`, the stage-3 record itself, `pending_commit`, the `account_objects` rows (bundle, certificate, self-grants, `E_id`) and the per-vault `Write::Wraps`. Nothing is left behind: a fresh `rv recovery complete` afterward finds no cache file for this account (§2's entry-point check above) and does not trip `CliError::AlreadyEnrolled`. The user re-runs `rv recovery complete` from the start.

No step generates new secrets; `start_commit`/`finish` (`recovery.rs`) still run at most once per stage-3 record.

### 4. What does not change

The vault half's cursor check (ADR 0025 §3), the credential-replacement rule, OPAQUE re-registration and ADR 0031's `setup_retired` handling are unchanged: this ADR only gives the existing resend and restart paths a record to resume from, plus the OPAQUE-login probe of §3 step 3, itself the account's already-existing login path used read-only. No new envelope, derivation or wire message: `CommitChangeRequest` and `pending_commit` are exactly what ADR 0026 §3 and `rizzy-proto::change` already define.

### 5. Tests

Extending ADR 0026 §6's existing coverage, not a new suite: a known-answer vector for a stage-3 record; the `client_device_state` fuzz target extended to stage 3's `has_local`/`pending` constraints (§1); a crash-injection case that fails after §2's pre-commit write, reloads, runs §3's resume end to end (device-auth fails, the OPAQUE probe fails, the resend abandons) and asserts the resend is byte-identical, that no second Emergency Kit is ever generated for a record still in stage 3, and that the abandoned cache leaves no row behind; and a second crash-injection case where the OPAQUE probe succeeds instead, asserting finalisation and no destructive action — the executable form of proposed INV-71 and of step 3's safety property.

## Consequences

### Positive

- Closes HANDOFF gap 12: an interrupted `rv recovery complete` resumes or safely abandons instead of leaving two kits with no way to tell which is live.
- No new cryptography, no CRYPTO.md edit, no new wire type: stage 3 reuses the same `pending_commit` column, the same `CommitChangeRequest`, and — for the resume itself — the already-existing device-auth, OPAQUE-login and recovery-only session machinery, none of it modified by this ADR.
- The device-auth short-circuit means the common "it actually landed" case needs no recovery-code re-entry. It still needs the new master password once, to unlock the stage-3 record itself (§3 step 1); no path through §3 avoids that.

### Negative

- One more stage value to keep in sync across `parse`/`encode`/`unlock` and the `client_device_state` fuzz target, and one more branch in `rv`'s startup.
- A build older than this change that opens a stage-3 record reports `CacheCorrupt`, a less precise message than `CacheUpdateRequired`, on a downgrade mid-recovery.
- A crash before `confirm_kit` is not covered by stage 3 (nothing is written until after confirmation, matching CRYPTO.md's own order) — but nothing was shown or confirmed either, so there is nothing to resume; the user just restarts.
- One extra round trip (the OPAQUE-login probe, §3 step 3) on the path where the device-auth short-circuit answers an ambiguous `401`, before any resend or abandon is attempted.

### Risks

- The abandon path no longer rests on a single ambiguous server answer to tell "someone else changed the account" apart from "this device is briefly offline": §3 step 3's OPAQUE-login probe runs first, and abandoning (step 5) is reached only after it cleanly rules out "this attempt's own commit is live." A partition that answers neither cleanly at any step leaves the record in stage 3 until the next retry, the safe side.
- If `device-auth/start` ever needs to rate-limit by a device id the server does not yet trust, the short-circuit of §3 step 2 would need its own carve-out; CRYPTO.md §5.10 states no such requirement today.
- The stored request's `vault_rotation` carries a cursor ADR 0025 §3 check 4 requires to equal the server's heads exactly. If another device writes an op to a vault between the first `recovery/complete` and a resend, the byte-identical resend goes stale and fails as `state_conflict` even though nothing about *this* recovery attempt's own credentials changed — the abandon path then fires for a reason unrelated to credentials, costing a third kit, though never a *live* one, since §3 step 3 already confirmed this attempt's commit was not live before any abandon runs. See open question 4.

## Alternatives considered

- **Do nothing; keep today's documented gap.** Rejected: ROADMAP §4.3 marks recovery a Must for M1, and the gap is exactly what CRYPTO.md's own rule already requires closed.
- **Reuse stage 1 plus the existing `pending` sub-record.** Rejected: that sub-record's base fields assume an already-committed device id for this account on this machine; a recovering client has none.
- **Persist only `pending_commit`, with no new stage.** Rejected: nothing would then gate `unlock` or signal "not yet usable," and a bare `pending_commit` with no stored Secret Key has nothing to rebuild `pw_in` from for the `setup_retired` path.
- **Skip the device-auth short-circuit; always resend through `recovery/complete`.** Simpler, but forces the user to re-type the recovery code even when the commit already landed, with no way to tell that case apart from "the recovery was cancelled." Rejected as the primary path; kept as the fallback.

## Open questions for the owner

1. **Mandatory or optional short-circuit?** Should the device-auth attempt of §3 step 2 be required by this ADR before the `recovery/complete` fallback, or left to whoever implements it? *Recommendation:* required — one extra round trip against an unmodified existing endpoint, and the only way to avoid re-typing the recovery code when the commit already landed.
2. **`RECORD_VERSION` bump.** Keep it at 1 (a build lacking stage 3 reports `CacheCorrupt`) or bump to 2 now, before any stage-3 record exists in the wild, for a cleaner `CacheUpdateRequired` message? *Recommendation:* keep it at 1. ADR 0026 §5 already defers migration machinery to when it is needed, and the cost of the wrong message is a deliberate downgrade mid-recovery repeating one command.
3. **How long an unresumed stage-3 record may sit.** The recovery-only session's 10-minute TTL does not bound how long the local record survives before the user next runs `rv`. *Recommendation:* no client-side expiry in M1; §3's procedure is safe at any later time, since every exit is either finalise, abandon-after-two-independent-confirmations, or stay in stage 3 and retry.
4. **Stale vault cursor on resend: abandon, or rebuild with the same keys?** §3 step 4's plain resend abandons on `state_conflict` even when only the vault half went stale (Risks), but — unlike the original draft — never while this attempt's own commit might still be the live one, since step 3's OPAQUE-login probe rules that out first. `crates/rizzy-client/src/rotation.rs`'s `PendingRotation::on_state_conflict` already rebuilds a rotation's vault half against fresh heads under the *same* new keys and resends, bounded by `MAX_REBUILDS`. *Recommendation:* abandon in M1, matching signup's own stage-2 pattern (no rebuild loop) and keeping this ADR's scope to the record format and the resume's safety, not a rebuild loop; revisit only if real interrupted recoveries show the race firing often enough to matter.
