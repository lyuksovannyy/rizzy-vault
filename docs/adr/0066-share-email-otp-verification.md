# ADR 0066: Recipient email verification by one-time code

- Status: Accepted
- Date: 2026-10-11
- Deciders: project owner
- Milestone: M5

## Context

[ROADMAP §4.7](../ROADMAP.md#47-public-sharing-m5) row 6 (Should): "Restrict to specific email addresses, verified by one-time code." ADR 0064 (sibling, this batch) already stores `recipient_emails` in clear on the `shares` row (it must, to send to them), and [CRYPTO.md §11.10](../CRYPTO.md#1110-public-share-link-creation-m5) step 5 already sends `recipient_emails?` to the server at creation. [CRYPTO.md §11.11](../CRYPTO.md#1111-public-share-link-opening-m5) step 3 already fixes the open call's wire shape as `{link_token, access_token, email_otp?}` and its "Limits" paragraph already states that "email restriction [is] enforced by the server," an honest-server-only control. This ADR gives that `email_otp` field, and the mail that carries its value, their mechanism. It does not touch ADR 0063's flags byte or ADR 0065's page origin (both sibling, this batch), and it is not the M6 mail subsystem: sibling ADR 0070 approves `mail-auth` for *inbound* alias mail verification; this is a narrow *outbound* transactional sender.

[ADR 0010](0010-server-shape.md) §1's role table already gives `worker` an outbound column, "SMTP relay for notification mail, if configured (M3)," and gives `api`'s outbound column "none." Nothing has used that allowance yet. This ADR is its first mechanism, not a change to the table: `api` queues, `worker` dials out, exactly as the table already splits the roles. `worker` already deletes "expired shares" among other buckets (§1) and holds no special isolation rule — that applies only to `smtp` and `icons` (§2), neither touched here.

[ADR 0028](0028-api-v1-http-conventions.md) item 12 fixes the enumerated `RIZZY_*` settings and says only `RIZZY_DATABASE_URL` may carry a secret. Outbound mail needs a relay credential, so item 12's settings list and its secret-boundary passage must widen; see "What this ADR supersedes." Item 11 fixes where per-source rate-limit state lives for the existing `rizzy-domain-auth`-owned buckets: "the buckets and numbers stay `rizzy-domain-auth`'s." This ADR touches none of that state: its per-source-IP backoff and its share-keyed counters (§2, §4) are all new, share-domain-owned buckets, kept out of `rizzy-domain-auth` because [ADR 0016](0016-workspace-layout.md) R4 forbids `rizzy-domain-share` depending on another domain crate directly — the same constraint ADR 0064's own "Rate limiting" section already applies to `/open`'s link-token throttle, for the identical reason.

A human-typed 6–8 digit code is not high-entropy like a bearer token or the recovery code (INV-20): `SHA-256(code)` over a 10^6–10^8 space is reversible from a DB dump in well under a second. The floor this ADR must not lower is INV-8's split — tokens are hashed, secrets are sealed under a server key kept outside the DB ([CRYPTO.md §5.11](../CRYPTO.md#511-server-side-encryption-not-zero-knowledge)) — so the code is sealed, not hashed, reusing exactly that construction rather than inventing a KDF for low-entropy codes.

## Decision

**Recommended option.** A `share_`-prefixed table holds a sealed one-time code per (share, recipient email), an `api` endpoint requests one, `worker` sends it over SMTP using settings the operator configures, and the existing `/open` call verifies it. No new cryptographic construction: sealing reuses §5.11. §5.10/§11.11's hash-and-compare pattern is deliberately *not* reused for the code itself, because the code is low-entropy (see Context) — it is reused only for `link_token`/`access_token`, unchanged.

### 1. Storage

`share_email_codes` (owned by the share domain, [ADR 0011](0011-storage.md) rule 5, `share_` prefix, no cross-domain FK): `code_id` (16B, server-random, PK), `share_id` (16B), `recipient_email` (text, lower-cased, NFC-normalized), `sealed_code` (the envelope below), `data_key_id` (u32, the key the envelope was sealed under — required by [§5.11](../CRYPTO.md#511-server-side-encryption-not-zero-knowledge)'s universal rule that the DB record every sealed row's key id and the server refuse to start if a row names one the secrets file lacks; it is also the HKDF `info` input for the subkey, so it is not additionally carried in AAD), `attempts_remaining` (u8, starts at 8), `expires_at` (ms), `sent_at` (ms, NULL until `worker` delivers it), `created_at` (ms). Unique on `(share_id, recipient_email)`: a new request deletes and replaces the row for that pair, which is how a resend invalidates the old code.

`sealed_code` is `Envelope(server_data_key subkey, SERVER_SHARE_EMAIL_CODE, share_id ‖ code_id ‖ u64 expires_at_ms)`, [§5.11](../CRYPTO.md#511-server-side-encryption-not-zero-knowledge)'s construction, purpose id **0x0104** in the server-only range — allocated after sibling ADR 0060's SMTP-credentials purpose (`0x0103`, same batch) in ADR-number order. **CRYPTO.md gains**, on acceptance: the row above in [§8.4](../CRYPTO.md#84-aad-and-purposes)'s purpose table; a fourth [§5.11](../CRYPTO.md#511-server-side-encryption-not-zero-knowledge) bullet naming it, the plaintext being the code's ASCII digits, with one clause stating that a `--data-key` rotation does **not** re-seal `share_email_codes` (unlike the existing `SERVER_TOTP_SECRET` reseal): these rows expire within 15 minutes, so the old key stays briefly loaded for them, which §5.11's own drop rule ("the old key is dropped once no row names it") already permits without a new carve-out; and a new §11.16 "Share recipient email verification (M5)" with the flow in §2–§3 below. **THREAT_MODEL.md gains**, on acceptance: the D row of [§7.16](../THREAT_MODEL.md#716-share-recipient-page-m5) widens to the text quoted in §4 below.

The code itself: 8 CSPRNG decimal digits (`rand_core::CryptoRng`, injected per [ADR 0009](0009-crypto-dependency-policy.md)'s RNG rules — no client involvement, this is server-generated and server-verified). 10^8 states is deliberately not password-grade; the attempt counter and expiry below are the actual control, matching how TOTP server 2FA ([CRYPTO.md §11.15](../CRYPTO.md#1115-totp-m1)) bounds a similarly small space.

### 2. Requesting a code

`POST /api/v1/shares/request-email-code {share_id, link_token, email}`, anonymous (no session), under the share's public endpoints — `share_id` is a body field, not a path parameter, matching ADR 0064's "every id is a body field" convention (itself superseding ADR 0028 item 1, INV-52). This is a fifth endpoint on the `shares` resource, beyond ADR 0064's four (`create`, `list`, `revoke`, `open`); this ADR adds 1 endpoint, taking the cumulative figure from ADR 0064's 36 to 37 under the ADR-number-order allocation (sibling ADR 0068 adds its own +3 after this one, for 40). The retry-class figure in ADR 0028's superseded "Retry after an unknown outcome" text still needs a further amendment at acceptance to give `request-email-code` a row class; this ADR does not itself amend that text (Open question 7, below). The server hashes and checks `link_token` exactly as `/open` does; a wrong one is `404 not_found`, uncounted toward anything (holding only the path proves nothing, same reasoning as [§11.11](../CRYPTO.md#1111-public-share-link-opening-m5) step 4). With the right `link_token`, the server first increments the `(share_id, email)` request counter below **identically on both branches**, before it looks at whether `email` matches — otherwise hitting that counter's 429 after 5 tries would itself say "this address is a recipient," reopening the oracle the 204 is meant to close. It also always does the same CPU-equivalent dummy work: generate and seal a candidate code. **Only then** does it branch: if the normalized `email` is **not** in the share's `recipient_emails`, the candidate is discarded (never written) and the answer is `204 No Content` — the same account-enumeration-style uniform answer as [§5.9](../CRYPTO.md#59-account-enumeration), with the dummy seal-and-discard standing in for §5.9's dummy OPAQUE record, so neither response latency nor the request-counter's rate-limit boundary reveals which addresses are recipients (residual: DB cache state and mail-queue depth can still differ slightly between the branches, accepted the way §5.9 accepts its own "prober who polls daily" residual). If `email` matches, the server instead replaces any existing row for that pair, writes the generated code to `share_email_codes`, increments the separate per-`share_id` **send** counter (next paragraph), and answers `204`. That send counter, unlike the request counter, counts only real sends: a prober who only ever hits the no-match branch never touches it, and never seeing it does not tell them anything, since the response is `204` either way and the counter itself is never returned.

**Rate limits.** At most 1 request per `(share_id, email)` per 60 s and 5 per rolling 24 h; at most 20 sends per `share_id` per rolling 24 h. These two counters live in `share_email_code_limits` (share-domain-owned, `share_` prefix, [ADR 0011](0011-storage.md) rule 5, checked by `cargo xtask check-tables`) — a share-keyed limit is not one of the account- or source-keyed categories [ADR 0010](0010-server-shape.md) §5 enumerates for `auth_` state, so it does not belong there. The per-`share_id` cap does **not** bound total mail volume across an account: an owner who names the same recipient on a fresh share gets a fresh 20-send budget, and no address is consent-verified before the server starts mailing it, an open-relay-reputation risk for self-hosters (see Negative). A per-account or per-recipient-email cap across all of an account's shares is ADR 0064's (share creation) to add; this ADR is not where that bound is enforced (Open questions). Separately, **exponential backoff per source IP**, never a hard lockout, mirroring INV-7, is its own copy inside `rizzy-domain-share`, keyed by source alone, in the same `share_email_code_limits` table as the two counters above: [ADR 0016](0016-workspace-layout.md) R4 forbids `rizzy-domain-share` depending on `rizzy-domain-auth`, so this ADR does not add a call into `rizzy-domain-auth`'s public API, and ADR 0028 item 11's "buckets and numbers stay `rizzy-domain-auth`'s" is neither superseded nor extended by this ADR — no `rizzy-domain-auth` state is touched. This mirrors ADR 0064's own "Rate limiting" section, which reaches the same conclusion for `/open`'s link-token throttle for the identical R4 reason. Over any of these limits: `429 rate_limited`.

### 3. Sending it: `worker`, not `api`

`api` never dials SMTP ([ADR 0010](0010-server-shape.md) §1's outbound column for `api` stays "none"). On the write above, `api` also publishes a `rizzy-bus` event when `worker` is co-resident (default `api,web,worker`) so delivery is prompt; correctness never depends on the event, only on `worker`'s next tick. Like every other scheduled job, `worker.rs` does not query `share_email_codes` with raw SQL ([ADR 0011](0011-storage.md) rule 5: a domain crate queries only its own tables); it calls one function the share domain crate exports — "send pending, then delete expired" — on its existing `RIZZY_WORKER_INTERVAL_SECS` tick, the same shape as its other scheduled-deletion calls into the other domains. `worker` already holds DB credentials and server secrets like `api`; this adds one outbound capability to a role that already has DB access, so none of §2's `smtp`/`icons` run-alone isolation applies.

That exported function unseals `sealed_code`, renders a fixed, compiled-in template (no user-supplied subject or body: the owner's share name/fields are never put in the mail, only the code and a generic sentence), and sends one message through a vetted SMTP client crate, recommended `lettre` (U: version, audit history and advisories unverified here; record the real [ADR 0009](0009-crypto-dependency-policy.md)-style checklist, if the owner judges one needed, in the implementation PR, as [ADR 0041](0041-p256-crate-approval.md) did for `p256`). The checkable constraint, enforced by `cargo deny check` and `cargo xtask check-deps`, not by review alone: `default-features = false`, the crate's `rustls`-backed TLS feature only, never `native-tls` or an `openssl` feature. `deny.toml` (checked against HEAD, V) currently bans `openssl` and `openssl-sys` outright, with no wrapper exception at all yet — the `webauthn-rs`-scoped exception is only a decision recorded for M3's WebAuthn work and is not yet applied to the file — which if anything makes this constraint stronger today, not weaker. On success it sets `sent_at`; on failure it retries with backoff (1, 5, 15, 30, 60 min, 5 tries), then deletes the row and logs the failure with no content ([INV-48](../THREAT_MODEL.md#8-security-invariants)). It also deletes any row past `expires_at` regardless of `sent_at`, folded into `worker`'s existing **"expired shares"** duty ([ADR 0010](0010-server-shape.md) §1), not its "expired auth state" one — this table is share-domain-owned, not auth-domain-owned.

### 4. Verifying it: extending `/open`

Unchanged from [§11.11](../CRYPTO.md#1111-public-share-link-opening-m5): `link_token`, then `access_token`, checked and burned exactly as already specified. Only once both are right, and only when the share's `recipient_emails` is non-empty, does the server look at `email_otp`. It fetches every non-expired `share_email_codes` row for the `share_id` (bounded by the recipient list's size), unseals each `sealed_code`, and compares each to the submitted value with `subtle::ConstantTimeEq` ([ADR 0009](0009-crypto-dependency-policy.md) constant-time rules). A match: delete that row (single use) and proceed to the normal open (envelope returned, `views` incremented).

**No match.** `email_otp` **present but wrong**: every candidate row's `attempts_remaining` is decremented (the server cannot attribute a wrong guess to one pending recipient without an email field the fixed wire shape does not carry — an accepted, narrow cost when two recipients are mid-verification at once, Open question 4); a row reaching zero is deleted, forcing a fresh `request-email-code`. `email_otp` **absent**: no row's `attempts_remaining` is touched at all — an adversary who holds only the link/fragment but is not a named recipient cannot guess, so a missing value must not spend a real recipient's attempt budget, and must not be able to force `request-email-code` lockouts by repetition either. Both cases instead count against a **new share-scoped limiter**, independent of §2's throttle: a tight per-`(share_id, source)` bucket plus a looser per-`share_id` ceiling, in the same `share_email_code_limits` table as §2. Over either: `429 rate_limited`, same as §2 (residual: a distributed caller can still exhaust the per-`share_id` ceiling, but that costs the real recipient a wait, never a code, since absent `email_otp` never decrements anything). Short of that limit, the response for "missing," "wrong" and "expired" stays `401 second_factor_required` (already in [ADR 0028](0028-api-v1-http-conventions.md) item 3's closed set; reused here for a route outside session auth, with the same meaning: one more factor is needed or was wrong). **This failure never feeds the existing 10-failure share burn** — that counter is `access_token` only, and burning the whole share over a mistyped or absent mail code would be out of proportion and would cost every other recipient their view.

[THREAT_MODEL §7.16](../THREAT_MODEL.md#716-share-recipient-page-m5)'s D row widens to: "Link scanners burn the view limit; a path-only caller burns the share; a link/fragment holder who is not a named recipient tries to burn every pending `share_email_codes` row by omitting `email_otp`. | A view counts only on explicit reveal; only failures carrying a valid link token count toward the burn; an absent `email_otp` never decrements `attempts_remaining` and is throttled by its own per-share limiter. | INV-33, AR-23, Proposed INV-91."

### What this ADR supersedes

[ADR 0028](0028-api-v1-http-conventions.md) item 12, in part — the settings-name sentence and the whole secret-boundary passage:

- The settings-name sentence: "Settings `RIZZY_ROLES`, `RIZZY_ORIGIN`, `RIZZY_LISTEN` (default `127.0.0.1:8080`), `RIZZY_DATA_DIR` (`/data`), `RIZZY_DATABASE_URL`, `RIZZY_SECRETS_FILE` (`/run/rizzy-secrets/secrets.json`), `RIZZY_SIGNUP` (`closed`|`open`), `RIZZY_TRUSTED_PROXIES`, `RIZZY_LOG_LEVEL`, `RIZZY_WORKER_INTERVAL_SECS`, `RIZZY_MAX_UPLOAD_BYTES`, `RIZZY_SMTP_URL`, `RIZZY_SMTP_FROM`; from the environment or a `NAME=value` file (64 KiB, `#` comments, no quoting; unknown, repeated or malformed lines refused); environment over file, `--roles` over both; `--roles` and `--config` are the only flags. No secret on the command line." (`RIZZY_SMTP_URL` unset disables outbound mail entirely; `request-email-code` then answers `invalid_request` for an email-restricted share, whether it was never set or was removed after the share was created. Share *creation* with non-empty `recipient_emails` while it is unset is ADR 0064's to refuse at `POST /api/v1/shares` — a dependency this ADR states but does not implement, see Open questions — so a share is never left permanently unopenable by an SMTP setting that was already missing when it was made.)
- The secret-boundary passage: "**Secret boundary:** no setting holds a key. `RIZZY_SECRETS_FILE` is a path, not a secret; keys live only in the file it names (item 13). Two settings can carry a secret: `RIZZY_DATABASE_URL` (`postgres://` or `postgresql://`, possibly with the password; unset means SQLite in the data directory), and `RIZZY_SMTP_URL` (`smtp://`, `smtps://` or `smtp+starttls://`, with an optional user and password). Both come only from the environment or the file, are held in a zeroizing buffer, and appear in no `Debug` output, log line or error (errors name the setting, never its value). A configuration file that holds either is readable by the server's user only; the server does not check that file's mode, so this is the operator's duty."

(Aside, not fixed here: item 12's settings list was already missing `RIZZY_RECOVERY_WAIT_HOURS`, pre-existing drift from `config.rs`, unrelated to this change.)

`RIZZY_SMTP_FROM` (the envelope/display From address) carries no secret and is additive, not a supersession of anything already closed. [ADR 0010](0010-server-shape.md) §1's role table is **extended**, not superseded: the worker row's existing "SMTP relay for notification mail" text stands unchanged; this ADR just gives it a mechanism.

### Proposed invariant

**Proposed INV-91** (allocated across the 2026-10-11 batch in ADR-number order. Provisional: the allocation was made across the 2026-10-11 batch in ADR-number order; if ADRs are accepted out of order, the owner renumbers at acceptance.): the one-time email verification code is never logged, never put in a response body, and never compared to a value derived only from a URL path or query; `worker`'s outbound mail contains the code and a fixed template only, never a share's field data or owner-chosen name; `request-email-code` does identical work and identical counter increments whether or not the submitted email matches a recipient; and `/open`'s `attempts_remaining` is decremented only when `email_otp` is present and wrong, never when it is absent.

## Consequences

### Positive
- Reuses two existing constructions (§5.11 sealing, §9.1 symmetric envelope) and one existing error code; no new KDF, no new TLS stack.
- `api`'s "no outbound" and `worker`'s "outbound, if configured" split, already fixed by ADR 0010, needed no change.
- A self-hoster who never sets `RIZZY_SMTP_URL`, and whose ADR-0064 create endpoint refuses `recipient_emails` accordingly, simply cannot create an email-restricted share; nothing else breaks (mirrors INV-43's "subsystem optional" pattern). Without that refusal in ADR 0064, the share would be created but could never be opened by anyone — this ADR does not own that guard and flags it as a dependency instead of assuming it away.

### Negative
- A second setting that can carry a secret widens ADR 0028 item 12's secret boundary, and `rizzy-server`'s config review now has two zeroizing-buffer paths instead of one.
- Two recipients verifying at once share one attempt budget per row-set; one mistyping can force the other to request a fresh code.
- A new outbound network dependency (the SMTP relay) is a new per-deployment thing to misconfigure and monitor; failures are silent to the owner beyond a log line.
- Mailing an address on the strength of the owner typing it, with no consent step and no cross-share cap, is an open-relay-reputation risk for self-hosters; §2's per-`share_id` cap does not bound it.

### Risks
- If `lettre`'s real checklist turns up an advisory or an `unsafe` surface the owner is not willing to accept, the crate choice changes before implementation; nothing else in this ADR depends on which crate is used, only on the rustls-only constraint.
- If the owner later wants per-recipient attempt attribution, the wire shape (`email_otp` with no `email` field) has to widen, which is ADR 0064's endpoint to change, not this one's.

## Alternatives considered

- **`SHA-256(code)` like link/access tokens.** Rejected: those are 16–32 random bytes; a 6–8 digit code hashed the same way is free to reverse from a DB dump, which is exactly the gap INV-8 already exists to close for TOTP and login state.
- **`api` sends the mail directly, synchronously.** Rejected: contradicts ADR 0010 §1's fixed "none" outbound column for `api`, and ties request latency and availability to the mail relay.
- **A third-party transactional email HTTP API (SendGrid, Postmark) instead of SMTP.** Rejected for v1.0: adds a required external account for a self-hoster where ROADMAP's model is self-hosted infrastructure; SMTP lets an operator point at any relay, including one they already run.
- **Burn the share on a wrong `email_otp`,** folding it into §11.11's existing counter. Rejected: destroys the view budget for every recipient over one mistyped mail code, not just the one guessing.
- **Carry `email` in the `/open` call** so attempts attribute to one row. Rejected here: CRYPTO.md's wire shape is already fixed without it, and widening it is ADR 0064's (sibling) call, not this ADR's.
- **Answer the no-match branch of `request-email-code` with no dummy work at all** (the earlier draft of this ADR). Rejected: a caller could then tell recipients apart either by timing or by which side of the rate limit they land on after enough probes, defeating the §5.9-style uniform answer the endpoint claims to give.

## Open questions for the owner

1. **Code length and lifetime (8 digits, 15 min, 8 attempts, resend limits in §2).** *Recommendation:* accept as specified; all are config-free constants in the share domain, cheap to retune later without a new ADR if M5 usage shows otherwise.
2. **Does `lettre` need the full ADR 0009 crate-approval checklist?** It performs no AEAD/KDF/curve/signature/PAKE itself and reuses the already-pinned `rustls` stack ([ADR 0009](0009-crypto-dependency-policy.md) 2026-10-05 amendment). *Recommendation:* no full checklist, but still require the standard CLAUDE.md dependency justification, `cargo deny check`, and the rustls-only feature constraint in §3 at review time.
3. **Final purpose id for `SERVER_SHARE_EMAIL_CODE`.** Resolved: allocated as `0x0104`, the batch's purpose ids reconciled in ADR-number order (0060 → `0x0103`, this ADR → `0x0104`, ADR 0071 → `0x0105`, ADR 0072 → `0x0106`); confirm at acceptance in case an ADR lands out of order.
4. **Collateral attempt-counter decrement when two honest recipients verify concurrently (§4).** *Recommendation:* accept it for M5; revisit only if real usage shows multi-recipient shares verifying simultaneously often enough to matter. (The adversarial case — a non-recipient forcing decrements with no `email_otp` at all — is closed in §4 itself, not left to this question.)
5. **Must ADR 0064's create endpoint refuse `POST /api/v1/shares` with non-empty `recipient_emails` when `RIZZY_SMTP_URL` is unset?** *Recommendation:* yes — otherwise the share is created but can never be opened by anyone, for the share's whole lifetime. This ADR states the dependency; ADR 0064 must implement it.
6. **Should mail volume be capped per account or per recipient email across all of an account's shares**, beyond this ADR's per-`share_id` cap? *Recommendation:* yes, owned by ADR 0064 (share creation), not this ADR; pick a number (for example 50 sends per account per rolling 24 h) at that ADR's review.
7. **`request-email-code` is a fifth `shares` endpoint, beyond ADR 0064's four.** The endpoint count is resolved: reconciled across the whole batch in ADR-number order — base 27, ADR 0054 +5 (32), ADR 0064 +4 (36), this ADR +1 (37), ADR 0068 +3 (40); confirm at acceptance in case an ADR lands out of order. Still open: ADR 0028's "Retry after an unknown outcome" table has no row class for `request-email-code` yet; *recommendation:* add it as a "Single use" row (a request/response pair, not safely repeatable blind) at acceptance.
