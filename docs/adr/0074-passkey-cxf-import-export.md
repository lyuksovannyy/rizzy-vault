# ADR 0074: Passkey import/export via the FIDO Credential Exchange Format (CXF)

- Status: Accepted
- Date: 2026-10-11
- Deciders: project owner
- Milestone: M8
- Supersedes: [ADR 0027](0027-export-payload.md) §1 in part (the "file's version stays 1" bullet); [ADR 0034](0034-export-reauth-and-plaintext-hold.md) point 3 in part (the sentence naming `export_encrypted`, `export_plaintext_json` and `export_plaintext_csv`), on acceptance.

## Context

[ROADMAP §4.10](../ROADMAP.md#410-mobile--passkeys-m7), Should, M8: "Passkey import/export via FIDO Credential Exchange Protocol (CXP/CXF) when stable." [ADR 0039](0039-passkeys-vault-and-extension.md) §6 deferred this and left the field design open for it: "A future CXF importer, in `rizzy-import`..., would build the same `passkey/<id>/…` fields from a parsed CXF payload." That table ([ADR 0039](0039-passkeys-vault-and-extension.md) §1) is used here unchanged.

**Stability check (V, fetched 2026-10-11, fidoalliance.org's download page).** The FIDO Alliance publishes two documents: the **Credential Exchange Format (CXF)** 1.0, named on the download page as **Proposed Standard** with an errata version (`cxf-v1.0-ps-errata-20260309`); and the **Credential Exchange Protocol (CXP)** 1.0, a **Working Draft** (`cxp-v1.0-wd-20241003`), with no errata listed. CXF is the file schema; CXP is the live, same-device companion-channel transfer (QR/BLE) the ROADMAP row's "when stable" was written against, and is out of scope here regardless. **The signal is not clean**, though: the same download page also describes both specifications together as an "early review draft" stage, which reads as stale page copy next to a document labelled Proposed Standard with errata, but was not independently resolved for this ADR (**U**). Whether CXF (not CXP) is "stable" enough to clear the ROADMAP row is therefore the owner's call, not a settled fact; open question 1 asks it directly.

**What CXF actually is (V, read from the Proposed Standard text).** The root is a `Header` object: `version{major,minor}`, `exporterRpId`, `exporterDisplayName`, `timestamp` (Unix seconds), and `accounts[]`, each holding items with a `credentials[]` array. A passkey credential has `type:"passkey"` and carries `key` (the private key, **PKCS#8 DER, RFC 5958, base64url**), `rpId`, `userHandle` (base64url), `credentialId` (base64url), `username`, `userDisplayName`; no public-key field and no algorithm field — ES256 vs. EdDSA is implied by the PKCS#8 `AlgorithmIdentifier`. **The format defines no encryption**; it leaves confidentiality to "the exporter." That is the gap the `EXPORT_FILE` envelope already closes.

**What exists.** [CRYPTO.md §8.4](../CRYPTO.md#84-aad-and-purposes) purpose `EXPORT_FILE` (0x0070) and [§11.14](../CRYPTO.md#1114-encrypted-export-m1) fix the export file key, the file wrapper JSON and the envelope; [ADR 0027](0027-export-payload.md) §1 fixes `payload_version = 1` inside it (our own item-list payload); [ADR 0034](0034-export-reauth-and-plaintext-hold.md) fixes re-authentication for every export and the warning/hold/phrase for a plaintext one; [ADR 0039](0039-passkeys-vault-and-extension.md) §1 fixes `passkey/<id>/rp_id`, `/user_handle`, `/credential_id`, `/private_key`, `/public_key_cose`, `/alg` (`1` = ES256, `2` = EdDSA/Ed25519 — both values already reserved, even though only ES256 is created today), `/discoverable`. `rizzy-import` holds one bounded, fuzzed JSON reader per vendor (`json.rs`, `rizzy_json.rs`, `bitwarden.rs`, …) with shared caps in `limits.rs`; no crate holds an ASN.1/DER reader today. **`rizzy-core::passkey` (`crates/rizzy-core/src/passkey.rs`, 276 lines) has `Es256SigningKey`/`Es256VerifyingKey` and nothing else — no EdDSA type.** The project's one Ed25519 wrapper, `rizzy_core::sign::SigningKey<R: SignerRole>`, is role-typed for identity/device keys; its `from_seed`/`write_seed`/`sign_message` are `pub(crate)`, and its own doc comment states "there is no public way to sign arbitrary bytes... a signing key is never a general signing oracle" — it signs only pre-framed statement types (§10.2), never a raw WebAuthn/CXF message, and it cannot derive a public key from an arbitrary decoded seed either. **This ADR therefore needs new `rizzy-core` API for EdDSA passkeys** (a seed-based constructor, public-key derivation, raw-message sign/verify, parallel to but not reusing `Es256SigningKey`/`Es256VerifyingKey`) wherever an EdDSA credential needs its public key derived (§3 below; export only re-wraps already-stored bytes and needs none of this, §2 "Building the item").

**Forces.** A CXF file, ours or another vendor's, is hostile input on the way in ([THREAT_MODEL](../THREAT_MODEL.md) A16): size-limited, parsed without panics, fuzzed. No home-made crypto ([CLAUDE.md](../../CLAUDE.md)): `hpke`, `p256` and `ed25519-dalek` are already approved ([ADR 0009](0009-crypto-dependency-policy.md), [ADR 0041](0041-p256-crate-approval.md)); this ADR adds no new primitive, pin or feature. [AST-9](../THREAT_MODEL.md#2-assets) and [AST-20](../THREAT_MODEL.md#2-assets) already name passkeys and exports as assets.

## Decision

### 1. Scope: CXF JSON only, passkey credentials only

File-based CXF import and export (this ADR). Not CXP (live, companion-device transfer — out of scope, needs its own channel). Not CXF's other credential types (password, note, …): a CXF item whose `credentials[]` holds no `"passkey"` entry is skipped and counted, the same way an unsupported item type is skipped today (ADR 0027 §2 step 4, §6 "Per-item failures").

### 2. Export: a second EXPORT_FILE payload version, gated like plaintext

- **Encoding.** `payload_version = 2` inside the `EXPORT_FILE` envelope ([CRYPTO.md §9.1](../CRYPTO.md#91-symmetric-envelope-algorithm-0x01)): `u16(payload_version = 2) ‖ bytes(cxf_json)`, `cxf_json` the UTF-8 CXF document. No new envelope purpose, algorithm or key derivation; the same 16 MiB plaintext cap applies (ADR 0027 §1 "Too large").
- **File wrapper.** A sibling of [CRYPTO.md §11.14](../CRYPTO.md#1114-encrypted-export-m1)'s JSON, tagged `"format":"rizzy-vault-cxf-export"` instead of `"rizzy-vault-export"`, with the same `version`, `kdf_id`, `export_salt`, `export_id`, `created_at`, `data` fields and the same key derivation. The tag lets `detect_format` ([ADR 0034](0034-export-reauth-and-plaintext-hold.md) point 6) name it before any password is asked.
- **Gate.** Re-authentication, as every export (ADR 0034 point 1; its wording already covers any export call, no change needed). A new `VaultSync::export_cxf` takes `PlaintextExportAuth` and `PlaintextExportAck`, the exact tokens `export_plaintext_json`/`export_plaintext_csv` take, even though its output is `EXPORT_FILE`-encrypted: once decrypted, a CXF document is a complete, portable, unencrypted credential dump for a foreign importer, the risk class ADR 0034 point 5 already gates with a warning, a 10-second hold and the typed `EXPORT PLAINTEXT` phrase.
- **Warning: a new constant, not ADR 0027 §5's frozen text.** That text says the file itself "will hold ... unencrypted" and ends "To keep a copy of your vault, use the encrypted export instead" — both false here, since `export_cxf`'s output already is an `EXPORT_FILE`-encrypted file (unlike ADR 0027's plaintext CSV/JSON, where the base text is accurate). The CSV bullet's "frozen base text plus an adds-bullet" mechanism therefore does not carry over; `export_cxf` gets its own full warning instead: "Once decrypted with its export password, this file holds a standard CXF credential-exchange document: the private key of every passkey in this vault, in a form any compliant password manager can read. It carries only passkeys, not the rest of this vault." Shown under the same gate as above (re-authentication, the 10-second hold, the typed `EXPORT PLAINTEXT` phrase).
- **Why two payload versions under one purpose is safe.** The outer `format` string (`"rizzy-vault-export"` vs. `"rizzy-vault-cxf-export"`) is cleartext, not part of the `EXPORT_FILE` ctx (ADR 0027 §1 already makes the same point about the file's `version`); the authenticated discriminator is the in-envelope `payload_version`. Swapping the outer tag on an envelope sealed with the other `payload_version` fails at the reader's dispatch step, not silently.
- **Building the item.** Each Login item's `passkey/<id>/…` list ([ADR 0039](0039-passkeys-vault-and-extension.md) §1) becomes one CXF passkey credential: `rpId`, `userHandle`, `credentialId` copied; `key` is the already-decrypted, already-stored `/private_key` bytes re-encoded as PKCS#8 DER (§4) — opaque bytes, read and re-encoded without needing the new rizzy-core API of the Context above, whether the credential is ES256 or EdDSA; `username`/`userDisplayName` from the Login's username field. `exporterDisplayName` is the fixed literal `"rizzy-vault"`; `exporterRpId` is left empty (we are not ourselves a relying party).

### 3. Import: one bounded reader, two entry points

A new `rizzy-import::cxf` module and `Format::CxfJson` variant, under the same no-I/O, no-panic rules and caps as every other reader (`limits.rs`'s `MAX_JSON_LEN`, `MAX_DEPTH`, `MAX_NODES`, `MAX_ENTRIES`, reused, not redefined), fuzz target `import_cxf`.

- **Bare file (the interop case).** `detect_format` gains a CXF rule: a JSON root with `accounts` (array) and `version.major` (integer) is `Format::CxfJson`, read directly, no password — exactly how a Bitwarden or 1PUX file is read today. This is how a file exported from another vendor's own CXF writer comes in.
- **Our own export (round trip).** Opening a `rizzy-vault-cxf-export` file asks for its export password like any encrypted export, decrypts the envelope, checks `payload_version = 2`, and hands the decrypted bytes to the same reader.
- **Per-credential checks, before any allocation beyond the shared caps:** `version.major` must be 1 (another major is "update required"; an unknown `minor` field is ignored, matching CXF's own additive-minor rule); `accounts[]`, each account's `items[]` and each item's `credentials[]` are each capped by `MAX_ENTRIES`, and the product of the three is already bounded by `MAX_NODES` (every array entry is a JSON node), the same backstop `limits.rs` already documents for other nested formats; only `type:"passkey"` entries are read; `key`, `userHandle`, `credentialId` are checked against the same base64url and length rules `rizzy_json.rs` already applies to typed values, before decoding.
- **Private key.** `key` is parsed as PKCS#8 (§4). The public key is never read from the file (CXF carries none); it is always **derived** from the decoded private scalar — through `rizzy-core`'s existing `Es256VerifyingKey` for ES256, or through the new EdDSA derivation API the Context above requires (not yet written) for EdDSA — so a file cannot assert a public key that disagrees with its own private key.
- **Writes.** One new Login item per imported passkey credential (ADR 0027 §2 step 3's pattern: new item id, new item key, create op of the importing device): `passkey/<id>/rp_id` = `rpId`; `/user_handle`, `/credential_id` = the decoded bytes; `/private_key` = the decoded scalar (concealed); `/public_key_cose` = the derived key, COSE-encoded as ADR 0039 §4 already does for a created credential; `/alg` from the PKCS#8 algorithm identifier (unknown OID: skip the credential, count it); `/discoverable` = `0x01` (CXF passkeys are resident by definition); `/created_ms` = the file's `Header.timestamp` × 1000 (CXF's timestamp is Unix **seconds**; ADR 0039 §1's field is milliseconds, "same convention as `import.created_ms`"). `item.name` and the username field come from `username`/`userDisplayName`.
- **Per-credential failures skip the credential, never the file**, counted in the import report, which names positions only (INV-48), matching ADR 0027 §2 step 4 and §6 "Per-item failures."

### 4. PKCS#8 encoding: a hand-written reader and writer, not a new crate

A passkey's private key travels in CXF as PKCS#8 `PrivateKeyInfo` (RFC 5958): for ES256, an EC private key (RFC 5915) wrapping the raw 32-byte scalar; for EdDSA, an RFC 8410 `CurvePrivateKey` wrapping the raw 32-byte seed directly. Both shapes are small and fixed. Following the precedent [ADR 0039](0039-passkeys-vault-and-extension.md) §4 set for WebAuthn's CBOR ("hand-write the small, fixed set... rather than add a general-purpose [format] crate"), this ADR recommends the same here: a reader and writer in `rizzy-core` (next to `passkey.rs`, same no-I/O, no-`unsafe` rules) that parses and emits exactly the two fixed `AlgorithmIdentifier`/wrapping byte patterns ES256 and EdDSA need, rejecting any other OID or nested length, with its own fuzz target and known-answer vectors (OpenSSL- and browser-produced PKCS#8 files for both algorithms). **This is encoding, not a new construction**: it moves bytes already produced by `p256`/`ed25519-dalek` into and out of an externally mandated DER layout; no new signature, KDF or AEAD is introduced. The alternative — enabling `p256`'s and `ed25519-dalek`'s own `pkcs8` features — is open question 2. **This DER layer is separate from, and does not substitute for,** the new EdDSA sign/verify and key-derivation API the Context above requires: this section only moves bytes into and out of PKCS#8, it does not give EdDSA passkeys a signing or verifying type.

### 5. What this ADR supersedes

1. **[ADR 0027](0027-export-payload.md) §1**, the bullet: "**The file's `version` stays 1.** A reader requires `version` = 1 and `payload_version` = 1; a payload of any other version is refused as 'update required'." Replacement: "**The file's `version` stays 1.** A reader requires `version` = 1. `payload_version` = 1 is ADR 0027's own item-list payload; `payload_version` = 2 is a CXF JSON payload ([ADR 0074](0074-passkey-cxf-import-export.md) §2). A payload of any other version is refused as 'update required'."
2. **[ADR 0034](0034-export-reauth-and-plaintext-hold.md) point 3**, the sentence: "`VaultSync::export_encrypted`, `export_plaintext_json` and `export_plaintext_csv` take `EncryptedExportAuth` or `PlaintextExportAuth`, which have no public constructor: only `ExportGate::authorize_encrypted` / `authorize_plaintext` create them (`ReauthRequired` otherwise)." Replacement: "`VaultSync::export_encrypted`, `export_plaintext_json`, `export_plaintext_csv` and `export_cxf` take `EncryptedExportAuth` or `PlaintextExportAuth`, which have no public constructor: only `ExportGate::authorize_encrypted` / `authorize_plaintext` create them (`ReauthRequired` otherwise); `export_cxf` takes `PlaintextExportAuth` ([ADR 0074](0074-passkey-cxf-import-export.md) §2)."

ADR 0027 §5 (the warning bullets) is **not** superseded: its base text and "CSV adds" bullet stay exactly accurate for the plaintext JSON/CSV exports they describe. `export_cxf` instead gets its own warning constant, new and separate (§2 "Warning" above) — it does not extend or reuse ADR 0027 §5's text, so no entry for it belongs in this list.

### Owner answers at acceptance (2026-10-22)

The owner accepted this ADR as drafted; the recommendations of "Open questions for the owner" stand:

1. CXF is built now. CXP stays out of scope.
2. PKCS#8 is a hand-written reader and writer in `rizzy-core`, not the `pkcs8` features of `p256` and `ed25519-dalek`.
3. CXF export reuses the literal `EXPORT PLAINTEXT` phrase.
4. A bare, unencrypted CXF export: the recommendation is yes, in the same change, behind the same warning, hold and phrase. But it needs a ROADMAP §4.10 edit, and §4.10 still names only "Passkey import/export via FIDO Credential Exchange Protocol (CXP/CXF) when stable". Until the owner makes that edit, the bare form is out of scope. This stays open.
5. `exporterDisplayName` is the fixed literal `"rizzy-vault"` and `exporterRpId` is empty for M8.

Of the "On acceptance" edits, items 1, 2 and 4 are made in the accepting change: CRYPTO.md §11.14 gains the CXF wrapper; the status lines of ADR 0027 (§1 in part) and ADR 0034 (point 3 in part) change, with their index rows; and THREAT_MODEL.md AST-9 and AST-20 gain their sentences. This ADR's index row already exists, as Accepted. Item 3 asks for no edit.

## Consequences

### Positive
- No new envelope purpose, algorithm id or key derivation; CXF export reuses `EXPORT_FILE` byte for byte.
- No new crypto crate or dependency; `hpke`, `p256`, `ed25519-dalek` stay exactly as ADR 0009/0041 pinned them.
- Import's two entry points (bare file, our own wrapped export) share one reader, so interop and self-backup cost one fuzz target, not two.

### Negative
- A hand-written PKCS#8 reader/writer is new parsing surface in `rizzy-core`, small but new; it needs its own vectors and review before M8 ships.
- EdDSA passkey support needs new `rizzy-core` API (seed-based construction, public-key derivation, raw-message sign/verify) that does not exist today and is not a reuse of `Es256SigningKey`/`Es256VerifyingKey` or of the role-typed, statement-only `sign::SigningKey` (Context above).
- Reusing `PlaintextExportAuth`/the `EXPORT PLAINTEXT` phrase for an encrypted file is a slight semantic stretch: the file at rest is not plaintext, only its contents once decrypted are.
- CXF export as decided here produces a file only *we* can open; it does not by itself hand another vendor an importable file (open question 4).

### Risks
- **CXF or CXP changes shape before M8 implementation lands.** Signal: a new CXF minor/major version, or FIDO Alliance errata changing the `Passkey` dictionary. Mitigation: the `version.major` check refuses rather than guessing at a new major; a minor bump is additive by the spec's own rule.
- **A PKCS#8 parsing bug.** Mitigation: the fuzz target and known-answer vectors of §4, and M8 audit scope growing to cover this reader the way it already must for ADR 0039's CBOR.

## Alternatives considered

- **A general ASN.1/DER crate** (`der`, `pkcs8`) instead of hand-writing the two shapes. Rejected for now: a new dependency needs its own ADR 0009 pass for marginal gain over two fixed, well-known byte layouts; revisit if a third algorithm or a richer PKCS#8 shape is ever needed.
- **Bare, unencrypted CXF export only** (no `EXPORT_FILE` wrapper), matching ADR 0027 §4's plaintext CSV exactly. Simpler and actually interoperable on the output side, but drops every exported private key to disk in the clear behind only the existing plaintext gate; the wrapped form was the given recommendation instead. Revisited as open question 4.
- **"Not now," waiting for an unambiguous "stable."** Not rejected outright — see open question 1 — but not recommended: CXF itself (not CXP) carries a Proposed Standard label with errata as of 2026-03-09, and waiting for every trace of "early review draft" language to disappear from FIDO's own site is a moving, externally controlled bar.

## Open questions for the owner

1. **Build CXF now, or conclude "not now" (ADR 0033's shape) and revisit when CXF is unambiguously stable?** CXF 1.0 is labelled Proposed Standard with errata (2026-03-09, V), but the same source page also calls the specifications "early review draft" (Context); that inconsistency was not resolved further. *Recommendation:* build now — CXP (the part genuinely still a Working Draft) is out of scope regardless, and a Proposed Standard with a dated errata round is a reasonable bar for a file format whose own worst case (a shape change) this ADR already bounds with a `version.major` check (§3). Revisit only if the owner reads the "early review draft" line as current.
2. **PKCS#8 encoding: hand-written reader/writer in `rizzy-core` (§4), or enable `p256`'s and `ed25519-dalek`'s own `pkcs8` features** (new transitive `der`/`spki`/`pkcs8` crates, an ADR 0009 Amendment to the existing pins)? *Recommendation:* hand-written; smaller, audited surface, no new dependency.
3. **Reuse the literal `EXPORT PLAINTEXT` phrase for CXF export, or a dedicated phrase** (e.g. `EXPORT PASSKEYS`)? The warning text itself is already settled, not reopened here: §2 "Warning" gives `export_cxf` its own constant, since ADR 0027 §5's base text is false for a file that is already `EXPORT_FILE`-encrypted. *Recommendation:* reuse the phrase; the underlying risk (a readable credential dump once decrypted) is the one it already names.
4. **Should M8 also ship a bare, unencrypted CXF export** (ADR 0027 §4's plaintext-CSV shape, gated the same way), so a user can hand a file straight to another vendor's importer, not only round-trip through rizzy-vault? Without it, this ADR's export side is a CXF-shaped self-backup, not interop-out. *Recommendation:* yes, as a `payload`-free plaintext form in the same change, behind the identical warning/hold/phrase; flagged because the brief for this ADR did not ask for it. ROADMAP §4.10's M8 row names only "Passkey import/export via FIDO Credential Exchange Protocol (CXP/CXF) when stable," not a second, bare export form, so **a yes here is also a ROADMAP §4.10 edit for the owner to make**, not something this ADR can decide on its own (the same flag ADR 0027 open question 4 used for its own new reader format).
5. **`exporterRpId`/`exporterDisplayName` values** (§2): fixed literals, or configurable per self-hosted instance? *Recommendation:* fixed `"rizzy-vault"` display name, empty `exporterRpId`, for M8; revisit only if an importer rejects an empty value.
