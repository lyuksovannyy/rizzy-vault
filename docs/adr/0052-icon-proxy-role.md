# ADR 0052: Icon-proxy (favicon) role: fetch, cache and re-encode mechanism

- Status: Proposed
- Date: 2026-10-11
- Deciders: project owner
- Milestone: M3
- Partially supersedes: [ADR 0028](0028-api-v1-http-conventions.md) item 1 (first two sentences), in part; [ADR 0030](0030-client-tls-rv.md) Decision 1 (the "`rizzy-cli` only" parenthetical), in part; [ADR 0009](0009-crypto-dependency-policy.md#amendments) Amendments, 2026-10-05 entry, "Where it is applied" sentence, in part — see "What this ADR supersedes" below.

## Context

[ROADMAP §4.1](../ROADMAP.md#41-foundations--project-hygiene-m0) names `rizzy-icon-proxy` among the planned crates. [ROADMAP §4.4](../ROADMAP.md#44-url-matching--autofill-m2) (Won't for M2) requires that fetching favicons through our server happen only "optional / proxied / cached anonymously," scheduled as "M3 design." [ADR 0010](0010-server-shape.md) §1 already names the `icons` role (fetch, re-encode, cache; no DB; outbound internet only; M3) and §2 fixes its isolation: no DB credentials, no server secrets, an allow-list SSRF guard that "connects only to globally routable unicast addresses on ports 80 and 443," checked "after DNS resolution and on every redirect," with "the connection goes to exactly the IP that was checked." Owner decision 5 there sets the role off by default. [ADR 0016](0016-workspace-layout.md) §3 already lists `rizzy-icon-proxy` as a planned crate (lib, M3, "Favicon fetch, SSRF guard, re-encoding, cache," may depend on `proto` only) and R3 forbids it from depending, directly or transitively, on `rizzy-storage`, sqlx, any `rizzy-domain-*` crate, `rizzy-bus`, or `rizzy-core` ("it handles no keys"). [THREAT_MODEL](../THREAT_MODEL.md) §7.11, TB-8, G-11, Q-11 and **INV-51** already fix that allow-list invariant in full (ranges refused, IPv4-mapped/NAT64 handling, no SVG, no per-user logs); this ADR does not restate or change INV-51, it implements it. §7.11's "D" row ("slow or huge responses; decompression bombs" → "timeouts, byte caps, pixel caps") carries no invariant ID today — a real gap this ADR closes.

[ADR 0019](0019-native-clients.md) §5.1 (Accepted) already anticipates this role from the client side: native clients decode server-served image bytes, favicons included, with their own safe-Rust decoder in the binding leaf and never pass them to a platform codec, precisely because "a malicious server skips the `icons` role's re-encoding." That client-side decoder is a separate, M3 native-client decision ADR 0019 reserves for itself (U there); this ADR's server-side re-encoding (below) is for honest operators and for the web vault, which has no such second decode step, and does not pre-empt ADR 0019's choice.

None of this is coded yet: `crates/rizzy-server/src/config.rs`'s `Roles::parse` refuses `"icons"` with `ConfigError::RoleNotInThisBuild("icons")`, and `crates/rizzy-server/src/http/` has only `api.rs`, `web.rs`, `headers.rs`, `security.rs` (checked by reading the files, V). [ADR 0028](0028-api-v1-http-conventions.md) fixes `/api/v1` conventions (POST for reads with a body, uniform `{"error":"<code>"}` codes, `Cache-Control: no-store` on API responses) for `rizzy-server/src/http/api.rs`'s 27 endpoints; this ADR adds one more endpoint under the same conventions, not an exception to them. No cryptography is involved: a favicon is public, non-secret metadata, and [CRYPTO.md](../CRYPTO.md) has no mention of icons today and gains none here. The one new dependency this ADR needs, an image codec, is not a cryptographic crate, so [CLAUDE.md](../../CLAUDE.md)'s ordinary "Justify every new crate" / `cargo deny check` rule applies, not [ADR 0009](0009-crypto-dependency-policy.md)'s checklist — the same distinction the workspace `Cargo.toml` already draws for `url`/`idna`/`psl` (ADR 0037 §2 point 1).

## Decision

### What this ADR supersedes

ADR 0010 and ADR 0016 are extended, not superseded: ADR 0016 §3 already lists `rizzy-icon-proxy` with `proto` as its only allowed internal dependency, and §6 only requires that a crate be created in the PR that gives it real code — this ADR is that PR's design, not a change to either rule. Three narrow parts of other Accepted ADRs do change, under [ADR 0020](0020-partial-supersession.md) point 9:

- **[ADR 0028](0028-api-v1-http-conventions.md) item 1, first two sentences** ("The 27 endpoints of `rizzy-server` `http/api.rs` (module table), under `/api/v1/`, grouped by resource (`register`, `login`, `device-auth`, `account`, `devices`, `healing`, `recovery`, `totp`, `vault`), verb last (`start`, `finish`, `commit`, …). POST for everything, including reads that carry a body; GET (and HEAD) only for GET `/api/v1/devices/grants`.") are replaced by: "The 27 endpoints of `rizzy-server` `http/api.rs` (module table), under `/api/v1/`, grouped by resource (`register`, `login`, `device-auth`, `account`, `devices`, `healing`, `recovery`, `totp`, `vault`), verb last (`start`, `finish`, `commit`, …), plus one endpoint outside `http/api.rs`: `POST /api/v1/icons/fetch`, resource `icons`, verb `fetch`, served by the `icons` role's own router and listener, never combined with `api` or `web` ([ADR 0010](0010-server-shape.md) §2; this ADR). POST for everything, including reads that carry a body; GET (and HEAD) only for GET `/api/v1/devices/grants`." Nothing else in item 1 changes: the verb, error-shape (item 3), body-limit (item 7) and header (item 10) rules all apply to `icons/fetch` unchanged, by the Decision below.
- **[ADR 0030](0030-client-tls-rv.md) Decision 1's opening parenthetical** ("all in `[workspace.dependencies]`, used by `rizzy-cli` only; a leaf, so [ADR 0016](0016-workspace-layout.md) is unchanged") is replaced by: "all in `[workspace.dependencies]`, used by `rizzy-cli` and, from this ADR, by `rizzy-icon-proxy` for its own, separately configured outbound TLS client (follows redirects, connects to a pinned `SocketAddr`, no shared state with `rv`'s client); `rizzy-cli` is a leaf and `rizzy-icon-proxy` is not, but [ADR 0016](0016-workspace-layout.md) R2(b) already lets a server-side library pull a third-party crate in directly, so ADR 0016 stays unchanged." Decision points 2–7 of ADR 0030 (protocol, trust, CA file, origins, tests) are `rv`-specific and stay as written; they do not bind `rizzy-icon-proxy`, which sets its own protocol version, trust roots and scheme/port policy in point 2 below.
- **[ADR 0009](0009-crypto-dependency-policy.md#amendments) Amendments, "2026-10-05: client TLS for `rv`" entry, "Where it is applied" paragraph, the sentence "The three crates are declared in `[workspace.dependencies]` with the pins and feature sets above and used by `rizzy-cli` alone"** is replaced by: "The three crates are declared in `[workspace.dependencies]` with the pins and feature sets above and used by `rizzy-cli` and, from this ADR, by `rizzy-icon-proxy`, each running its own `ClientConfig` with no shared state." The rest of that paragraph (the `tls12` test feature, the `dangerous`/`danger::` scan, the CA-PEM fuzz target, the lockfile deltas) is `rv`-specific and stays as written; it does not describe `rizzy-icon-proxy`, which has no CA-file option (point 2 below).

CRYPTO.md is not an ADR and so is fixed directly, not superseded (CLAUDE.md's ADR gate: an Accepted ADR wins on a mechanism, "fix the doc in the same change"): §3's row whose first cell reads "Transport (`rv`)" is replaced in full by two rows, since `rizzy-icon-proxy` has no private-CA option (point 2) and the old row's second cell named one: "Transport (`rv`) | TLS 1.3, ring provider, Mozilla roots or a private CA | `tokio-rustls`, `rustls` (`std`, `ring`), `webpki-roots` | =0.26.6 / =0.23.45 / =1.0.9 | rustls: Cure53 2020 on an older version (U)" stays, unedited, for `rv`; a new row is added directly below it: "Transport (`rizzy-icon-proxy`) | TLS 1.3, ring provider, Mozilla roots only, no private CA | `tokio-rustls`, `rustls` (`std`, `ring`), `webpki-roots` | =0.26.6 / =0.23.45 / =1.0.9 | rustls: Cure53 2020 on an older version (U)". This ADR's acceptance makes that edit, the same way ADR 0030's acceptance added the original row.

1. **Crate.** Create `rizzy-icon-proxy` (lib) exactly as ADR 0016 §3 already specifies: depends on `rizzy-proto` only (for the shared request/response types), not on `rizzy-core`, `rizzy-match`, `rizzy-storage`, `rizzy-bus` or any `rizzy-domain-*` crate (R3; `rizzy-match` is also excluded because it depends on `rizzy-core`, which would reintroduce the forbidden edge transitively). `rizzy-server` depends on it directly (R5) and wires it into a new `icons` role: `Roles::parse` in `config.rs` gains an `icons: bool` field instead of the `RoleNotInThisBuild` refusal, `server.rs` starts it only when no other role is requested (ADR 0010 §2's "runs alone" check), and `http/mod.rs` gains a minimal `icons_router()` next to today's `router(api, web)`, in a new `http/icons.rs`. Default roles (no `--roles`) stay `api,web,worker[,notify]`; `icons` is never in the default set (unchanged, ADR 0010 owner decision 5 / Q-11).
2. **Fetch, DNS-pinned, scheme/port fixed.** For a requested host, resolve it once (`tokio::net::lookup_host`, the OS resolver; no new DNS crate), check every returned address against the INV-51 allow-list, and open a TCP connection to exactly one checked `SocketAddr` — never a second hostname resolution. **Scheme policy:** try `https://` on port 443 first, with TLS over that pinned connection: the same pinned `rustls`/`tokio-rustls` versions as `rv` but `rizzy-icon-proxy`'s own `ClientConfig` (TLS 1.3, `webpki-roots`, no private-CA option) — the extension this ADR makes to ADR 0030 Decision 1 and the ADR 0009 Amendment, above — verifying the certificate against the original hostname, not the pinned IP. Only if the TCP connection itself fails (refused, reset, timed out) — never on a TLS or certificate failure — retry once on plain `http://` port 80, on the same already-checked IP, with no second resolution, since INV-51 explicitly allows port 80 and the asset is cosmetic, non-secret metadata; a host that answers only on 80 is otherwise unreachable. A `3xx` response with `Location` repeats the whole resolve-check-connect sequence for the new target (host, scheme and port all taken from the `Location` URL, defaulting to 443/https when it gives no scheme), capped at 3 hops total; a redirect that downgrades scheme on the *same* host (https→http) is refused and ends the fetch with no icon, to keep a passive network attacker from forcing the plaintext leg — INV-51's port-80 allowance exists for honest hosts, not for this. A target that fails the allow-list, or a chain over the cap, also ends the fetch with no icon. The allow-list itself is the exact IANA ranges INV-51 names, hand-coded against `std::net::{IpAddr, Ipv4Addr, Ipv6Addr}` in `rizzy-icon-proxy` — no new crate, because it is a fixed table lookup, not cryptography or DNS logic.
3. **Discovery.** Try `GET https://<host>/favicon.ico` first (port 443, falling back to port 80 only by rule 2's TCP-failure case, never for `<host>` alone). If that 404s, fetch `GET /` at the same scheme/port and scan at most the first 64 KiB of a `text/html` body for `<link rel="icon"|"shortcut icon">`, resolve its `href` against that request's own scheme+host+port as the base (never assumed), and repeat step 2 for the resulting absolute URL (which may name a different host, e.g. a CDN, or a different scheme/port). No HTML parser is used, only a bounded substring scan, to keep the attack surface small.
4. **Re-encode.** Decode the fetched bytes with the `image` crate (new dependency; pure Rust codecs for PNG/JPEG/GIF/BMP/ICO/WebP, MIT/Apache-2.0, no `openssl` edge — consistent with `deny.toml`; exact version pin and `cargo deny check` run in the implementation PR, per CLAUDE.md's ordinary dependency rule, not ADR 0009's). The decoder's byte and pixel limits are set before any allocation (proposed INV-76, below). Every successful decode is re-encoded to a single canonical PNG, resized to fit 128×128 (never upscaled), before caching or serving. SVG and any other vector or script-bearing format is never served (INV-51, restated here only as "implemented by re-encoding to raster").
5. **Cache.** An unauthenticated, shared, on-disk cache under the `icons` role's own cache volume ([ADR 0010](0010-server-shape.md) §4), keyed by the validated lowercase ASCII host *and* the scheme and port the successful fetch used: `<cache_dir>/<host>-<scheme>-<port>.png` (e.g. `example.com-https-443.png`), so a host reachable on both 80 and 443 — both allowed by INV-51 — never collides on one slot. "Validated" means RFC 1123 syntax, checked before any cache or network use — 1–63 bytes per label, labels only `[a-z0-9-]`, no leading or trailing hyphen, no empty label, no leading or trailing dot, ≤ 253 bytes total — which also rules out `/`, `..` and every other path-traversal or injection character, so no hash and no new dependency are needed. No account, session or request identifier ever reaches `rizzy-icon-proxy` — the endpoint (below) carries none — so the cache cannot correlate requests to a user. A cached entry older than its TTL (default 14 days; `RIZZY_ICON_CACHE_TTL_SECS`, matching the naming style of `RIZZY_MAX_UPLOAD_BYTES`) is refetched; the cache directory is capped by total bytes (default 256 MiB; `RIZZY_ICON_CACHE_MAX_BYTES`), evicted oldest-`mtime`-first when over the cap, checked before each write.
6. **Endpoint.** `POST /api/v1/icons/fetch`, body `{"host":"<ascii hostname>"}` (no scheme or port: the client never chooses one, step 2 does), following [ADR 0028](0028-api-v1-http-conventions.md) item 1's path/verb convention (resource `icons`, verb `fetch`) exactly: `200` with `{"content_type":"image/png","data":"<base64url>"}` on a hit; the existing uniform codes otherwise (`invalid_request` for a malformed host, `not_found` when no icon could be fetched or decoded, `rate_limited`, `internal`). No bearer token, like `register/start` and `GET /api/meta`; item 7's 1 MiB body limit easily covers the request and the (small, size-capped) base64 response; item 10's `Cache-Control: no-store` applies unchanged, because the shared cache above is the caching layer, not the HTTP response. The web vault turns the response into an `<img>` source with `URL.createObjectURL(new Blob([bytes], {type}))`, a `blob:` URL, not `response.data` as a `data:` URL: `WEB_CSP`'s `img-src` is `'self'` exactly, with no `data:` token (`crates/rizzy-server/src/http/security.rs`, V — read directly); a `data:` URL is opaque-origin and `img-src 'self'` refuses it outright, which is why the response is never turned into one. Whether `'self'` also matches a same-origin-created `blob:` URL is a CSP3/browser-behavior claim this session did not test (L, general CSP semantics, open question 6): if it does, as is widely documented, no further change is needed; if an implementation PR finds otherwise, `img-src` gains `blob:` and that one token change supersedes ADR 0028 item 10's CSP wording in part, rather than this ADR assuming either outcome. Because the role has no DB (R3) and so no access to the `auth_` rate-limit tables ([ADR 0010](0010-server-shape.md) §5), `icons/fetch` keeps its own in-process, per-source token bucket (ADR 0028 item 11's source rule, reused; counters live in memory only). ADR 0010 §4 gives `icons` no single-replica rule the way §2 gives `worker` one (a DB advisory lock) — profile C explicitly allows `icons` "one more container in any profile" with no replica cap — so this bucket's budget multiplies by the replica count exactly as ADR 0028 item 8 already accepts for `api`'s large-body slots ("With N `api` processes the bound is N times that... the operator sizes every process for it"): a deployment running several `icons` replicas gets that many times the nominal rate limit, and the operator is the one who can keep `icons` at one replica if the budget matters to them. Served on its own listener, in its own process, by the new `icons_router()` (step 1), never by the combined `api`/`web` `router()`. The operator's reverse proxy (ADR 0010 §4's `edge` network) gains one path-based rule, `/api/v1/icons/` → the `icons` container; the shipped Caddy example is updated in the implementation PR.
7. **Proposed INV-76** (allocated across the 2026-10-11 batch in ADR-number order; fills the untracked §7.11 "D" row. Provisional: the allocation was made across the 2026-10-11 batch in ADR-number order; if ADRs are accepted out of order, the owner renumbers at acceptance.): *The icon fetcher caps the fetched response at 2 MiB before decoding, decodes with the image library's own byte/pixel/dimension limits (never allocating a decode buffer sized from unchecked header fields), follows at most 3 redirects and refuses a scheme-downgrading redirect (step 2), holds a time budget of 10 s for the whole fetch-discover-decode sequence per request, and caps its on-disk cache at a configurable total size with oldest-first eviction.* Verified by: a fuzz target with crafted/oversized headers and a decompression-bomb PNG/GIF; a cache-eviction test that writes past the cap; a redirect-loop test; a scheme-downgrade-redirect refusal test.

## Consequences

### Positive
- The `icons` role goes from a hard-coded refusal to a real, isolated implementation, closing [ROADMAP §4.4](../ROADMAP.md#44-url-matching--autofill-m2)'s M3 design item and fulfilling the role ADR 0010 and ADR 0016 already reserved.
- No new attack surface on `rizzy-core`, the DB or any secret: the crate graph (R3) makes this mechanical, not a review promise.
- A later ADR (0053, Proposed) can reuse this role's DNS-pinned, allow-listed outbound fetch for HIBP queries without redesigning it, because step 2 is one self-contained function.

### Negative
- One more server-side dependency tree (`image` and its codec sub-crates) to keep patched; `cargo deny check` gains a new subject.
- Favicons change rarely but not never; a 14-day TTL means a changed icon can lag that long. Acceptable for a non-secret, cosmetic asset.
- The redirect-and-discovery walk (step 2–3) is more HTTP round trips per cache miss than a naive single fetch, which is the cost of closing DNS rebinding.
- An operator who runs several `icons` replicas without reading this ADR's rate-limit note gets a softer per-source limit than they may expect (point 6).

### Risks
- A bug in the hand-coded allow-list table (step 2) is exactly the SSRF INV-51 exists to prevent; the fuzz/test suite INV-51 already calls for is the mitigation, not this ADR.
- `image`'s codec crates are a larger dependency surface than a single-purpose PNG decoder; a future advisory against one codec may force dropping input formats rather than the whole crate.

## Alternatives considered

- **A general-purpose HTTP client crate (`reqwest`) instead of reusing `hyper`/`hyper-util`/`tokio-rustls`.** Rejected: those are already pinned and audited for `rv`'s TLS client (ADR 0030); a second HTTP client stack duplicates review for no gain, and `reqwest`'s own redirect-following would re-resolve hostnames, defeating DNS pinning unless disabled and reimplemented anyway.
- **A CIDR-matching crate (e.g. `ipnet`) for the allow-list.** Rejected for now: the ranges are a short, fixed table from the IANA registries INV-51 already names; `std::net::IpAddr` covers the needed checks, and a dependency buys little for a table that changes only when IANA reallocates address space.
- **Serving the icon as a direct image response (`GET /api/v1/icons/fetch?host=`) for use as a plain `<img src>`.** Rejected: it would need new `Cache-Control` and error-body exceptions to ADR 0028 items 3 and 10 for one endpoint, and it would put the requested host in a URL and so in access logs (INV-52). The chosen `POST` + base64-JSON shape stays fully inside ADR 0028's existing rules, and the client turns the response into a `blob:` `<img>` source (point 6) rather than a `data:` one, so it needs no `WEB_CSP` change either.
- **Multiple cached sizes per host.** Rejected for M3: one canonical 128×128 PNG keeps the cache and endpoint simple; multiple sizes is an additive follow-up if the UI needs it.
- **SQLite-backed cache metadata (cached-at, etag) instead of file `mtime`.** Rejected: it would pull `sqlx`/`rizzy-storage` into `rizzy-icon-proxy`, which R3 forbids outright.
- **Enforce a single-`icons`-replica rule like `worker`'s (point 6).** Rejected for M3: `worker`'s lock exists for a correctness reason, running it twice double-processes deletions, that `icons` has no analogue of; `icons` replicas are stateless and interchangeable. The cost of leaving them unbounded is a per-source rate limit that is N× looser in an N-replica deployment, the same shape of trade-off ADR 0028 item 8 already accepts for `api`'s body-limit slots, not a correctness bug. A cross-process lock for a role with no DB would cost more than that looser limit is worth.

## Open questions for the owner

1. **Canonical output format: PNG or WebP?** *Recommendation:* PNG. Universally decodable by every client (including older WebView-based clients), no patent history to re-check, and the size difference is negligible at 128×128.
2. **Redirect cap and per-request time budget: 3 hops / 10 s, as drafted, or different numbers?** *Recommendation:* keep these; they match typical favicon redirect chains (bare domain → `www` → CDN) with margin, and 10 s keeps a cache-miss request from holding the in-process rate-limit slot too long.
3. **Cache TTL and size cap: 14 days / 256 MiB defaults, as drafted?** *Recommendation:* yes, both operator-tunable by environment variable, matching `RIZZY_MAX_UPLOAD_BYTES`'s pattern (ADR 0028 item 12).
4. **Exact `image` crate version and feature set.** *Recommendation:* pin at the implementation PR, after `cargo deny check` and a feature audit that enables only the codecs actually needed (PNG, JPEG, GIF, BMP, ICO, WebP decode; no encode-only or unused codec features) — this ADR commits to the crate choice, not an unverified version string.
5. **In-process rate-limit numbers for `icons/fetch`, and whether to cap `icons` at one replica.** *Recommendation:* a per-source token bucket of 30 requests/minute, burst 10, mirroring the order of magnitude of ADR 0028 item 11's other buckets, accepting the N-replica multiplication (point 6); no replica cap, since nothing but this soft limit depends on it. Tune after real traffic is observed, since this role has no DB to log against for review.
6. **HTTP:80 fallback: on by default, or opt-in only?** *Recommendation:* on by default (point 2), since INV-51 already allows port 80 and refusing it would silently drop favicons for the plain-HTTP sites that still exist; revisit if abuse shows up on the plaintext leg.
7. **If a `blob:` `<img>` source turns out not to match `img-src 'self'` in a tested browser (point 6), add `blob:` to `WEB_CSP`'s `img-src`, or keep `data:`-only sites icon-less?** *Recommendation:* add `blob:` and name ADR 0028 item 10 as superseded in that one token; it is strictly narrower than `data:` (no arbitrary payload URL, only a same-origin object the page itself created) and losing favicons silently is worse than a one-token CSP addition the implementation PR can make and test.
