# ADR 0059: Crypto-crate approval: webauthn-rs for the FIDO2 2FA ceremony

- Status: Partially superseded by [ADR 0077](0077-webauthn-rs-integration-fixes.md) (Decision "Recommendation" in part, checklist item 7 in part, owner answers 1 and 6)
- Date: 2026-10-11
- Deciders: project owner
- Milestone: M3

## Context

ROADMAP §4.3 "2FA: TOTP, WebAuthn/FIDO2 security keys" is a Must, split "M1 (TOTP) / M3 (WebAuthn)". ADR 0058 (Proposed, M3; title "WebAuthn/FIDO2 security keys as a server-side second factor," exact filename to confirm when it lands) is the feature ADR: registration and assertion ceremonies, RP-ID/origin binding, public-key and sign-counter storage, clone/replay detection, for logging into rizzy-vault itself with a hardware security key, alongside TOTP (`crates/rizzy-domain-auth/src/totp.rs` is TOTP's sibling module today). This ADR does the other half: approving the crate the ceremony runs on, the same split [ADR 0041](0041-p256-crate-approval.md) made from [ADR 0039](0039-passkeys-vault-and-extension.md) for client-side ES256 passkeys, and [ADR 0029](0029-kdbx-import.md) made for KDBX's legacy primitives. No code and no CRYPTO.md edit lands with this ADR; the implementation PR that lands with ADR 0058's acceptance does that, per [ADR 0009](0009-crypto-dependency-policy.md)'s own text and the pattern its `blake2`/`poly1305`, client-TLS and `p256` Amendments already set.

ADR 0009's M0 fact sheet named the problem: "`deny.toml` bans `openssl`/`openssl-sys`, which blocks `webauthn-rs` (M3): its core crate depends on openssl unconditionally (V)," and "the alternative `webauthn_rp` pulls `rsa` 0.9, which carries RUSTSEC-2023-0071 with no fix (V)." The owner answered on 2026-09-25 (ADR 0009 owner decision 1, restated in [THREAT_MODEL Q-14](../THREAT_MODEL.md#10-open-questions-for-the-owner)): "a narrowly scoped `webauthn-rs` exception whose `openssl` edges `cargo xtask check-deps` confines to the server," with the exact `deny.toml` wrapper lines and the exact `check-deps` scope ("`rizzy-server` and the domain crate that does WebAuthn") already written down. `crates/xtask/src/rules.rs` already carries that scope as code: its `CrateRule` for `rizzy-domain-auth` and for `rizzy-server` both set `openssl: true` (lines 377-394, 429-438), and its `OPENSSL` constant (line 702) names `openssl`/`openssl-sys` as the two crates that rule confines — written and merged before any crate uses the right. `rizzy-domain-auth` is the ADR 0016 §3 domain crate for "OPAQUE server side, sessions, 2FA, devices, key bundles, account state" and already holds `totp.rs`; it is a `Side::Server` crate, not one of ADR 0016 R1's no-I/O/wasm32 crates, so R1's getrandom and wasm constraints do not bind it or this crate.

CRYPTO.md Rule 1 requires standardised algorithms "implemented by established crates, and we use them as their specifications intend" ([§1](../CRYPTO.md#1-goals-non-goals-and-rules)); Rule 2 lists the eleven compositions that are ours, and a WebAuthn RP ceremony is not and must not become a twelfth: hand-rolling origin/RP-ID binding, COSE/attestation parsing and counter-based clone detection on the already-approved `p256` primitive (ADR 0041) alone would be exactly that, since `p256` covers ES256 verification only, not the RP-ID/origin checks, the multi-format attestation-statement parsing (packed, fido-u2f, tpm, android-safetynet, apple, none) or the counter bookkeeping the WebAuthn Level 3 / CTAP2 specifications define around it, and a hardware key may assert with an algorithm `p256` cannot verify at all (RS256, EdDSA). CRYPTO.md has no §11.x flow for server-side WebAuthn yet (only [§11.15](../CRYPTO.md#1115-totp-m1) TOTP); a new §11.16 is what ADR 0058 must write before any WebAuthn code lands, and this ADR adds no construction to stand in for it (open question 6).

## Decision

### Recommendation: `webauthn-rs` (Kanidm project), pinned `=0.5.5`, approved for `rizzy-domain-auth` only

```toml
webauthn-rs = { version = "=0.5.5", default-features = false, features = ["attestation"] }
```

The facade crate, not `webauthn-rs-core` alone: ceremony correctness (the `Webauthn` builder's RP-ID/origin binding, and the `Passkey`/`SecurityKey` credential types that carry the sign counter and clone-detection state back to our storage) lives in the facade, and calling `-core` directly would re-introduce the hand-rolling this ADR exists to avoid. `webauthn-rs-core` `=0.5.5` and `webauthn-rs-proto` `=0.5.5` enter transitively, version-locked to the facade inside the crate's own workspace (V, crates.io dependency listing for `webauthn-rs` 0.5.5, 2026-10-11). `features = ["attestation"]` is behaviourally identical to the crate's own `default = ["attestation"]`; named explicitly anyway, per ADR 0009's convention of spelling out every feature rather than inheriting defaults silently. Never `resident-key-support` (discoverable passkeys as a sole factor are ROADMAP §4.3's post-1.0 "Could," out of this ADR's and ADR 0058's scope), `conditional-ui` or `workaround-google-passkey-specific-issues` (passkey-specific, not security-key 2FA), and never a `danger-*` feature (each is named for exactly what CRYPTO.md Rule 6, fail closed, forbids weakening). `attestation` does not change the dependency graph: `webauthn-rs-core` is itself a non-optional, default-on dependency of the facade, and `der-parser`, `nom`, `x509-parser` and `webauthn-attestation-ca` are all non-optional, default-on dependencies of `webauthn-rs-core` (V, crates.io dependency listings for `webauthn-rs` and `webauthn-rs-core` 0.5.5, 2026-10-11) — none of the four is reachable only through the `attestation` feature. What the feature gates is API surface only (which functions/credential-verification paths are exposed): **U**, to confirm in the implementation PR with `cargo tree --features` if the exact surface matters.

Whether attestation-chain validation needs live network access is checked directly, not left open. `webauthn-attestation-ca` 0.5.5's own dependency list is `base64urlsafedata`, `openssl`, `openssl-sys`, `serde`, `tracing`, `uuid` only (V, crates.io dependency listing, 2026-10-11) — no HTTP client, DNS resolver or async runtime, so the crate cannot fetch anything at runtime. Its types (`AttestationCaList`, `AttestationCaListBuilder`, `SerialisableAttestationCa`) are a generic container the RP populates, not a bundled trust-anchor set: the crate's own source (`attestation-ca/src/lib.rs`, 9.3 KB) ships no hardcoded vendor root certificates (V, GitHub source, 2026-10-11). `webauthn-rs-core`'s own attestation code (`webauthn-rs-core/src/attestation.rs`) treats OCSP and CRL checking as optional and implements neither; its only mention of the FIDO Metadata Service is a comment that certificate status "is available through metadata services," not a call to one (V, GitHub source, 2026-10-11). So neither crate does network I/O for attestation today. What is still open, and is not a network question, is where **our own code** gets the CA list to populate the builder with: a static list we vendor and update by reviewed PR (no runtime fetch), or something that fetches the FIDO MDS BLOB ourselves — ADR 0058's implementation PR must say which (new open question 8). Only the second choice is a new outbound need for `rizzy-domain-auth`/`api`; today [ADR 0010](0010-server-shape.md) §1's `api` role `Outbound: none` row is unaffected (unchanged by [ADR 0022](0022-server-mode-only.md) §2's own partial-supersession text for that row, which edits only the "Does" cell, V, 2026-10-11), and nothing here touches ADR 0053's icons-role SSRF routing (Proposed/forthcoming, M3; filename to confirm when it lands, the sibling ADR for new server-side outbound needs such as HIBP). If a live fetch is ever added, it must route through `icons`'s allow-list per ADR 0053, or this ADR or ADR 0058 must name ADR 0010 §1's `api` row as a part it partially supersedes ([ADR 0020](0020-partial-supersession.md) point 9) — not added ad hoc.

### The ADR 0009 checklist

1. **Need.** The WebAuthn Level 3 / FIDO2 CTAP2 registration and assertion ceremonies for server-side 2FA (ADR 0058); standardised by the W3C and FIDO Alliance, not a construction of ours (V, the specs).
2. **Provenance.** Maintained by the Kanidm identity project (`kanidm` GitHub organisation; lead maintainer William Brown / `Firstyear`, also the crate's original 2021 author), repository `kanidm/webauthn-rs`: 713 stars, last push 2026-10-08, three days before this ADR (V, GitHub API, 2026-10-11). Lifetime downloads 7,714,963, last-90-day 2,799,276 (V, crates.io API). `max_stable_version` is `0.5.5`; `newest_version` is `0.6.1-dev` — `0.6.0-dev`/`0.6.1-dev` are prereleases, not taken, the same "latest *stable*" reading ADR 0041 used for `p256` (V, crates.io API, 2026-10-11). License MPL-2.0, already on `deny.toml`'s allow-list (V).
3. **Audit history.** None found for `webauthn-rs`, `webauthn-rs-core` or `webauthn-rs-proto` (U, absence of evidence; the same RustSec-advisory-db-directory method ADR 0041 used — a 404 on the crate's own advisory directory, cross-checked against `openssl`, which does have one (item 4), confirming the method). Widely depended on in the Rust WebAuthn ecosystem through the Kanidm project itself (L, not independently enumerated).
4. **Advisories.** None filed for `webauthn-rs`, `webauthn-rs-core`, `webauthn-rs-proto`, `der-parser`, `x509-parser`, `serde_cbor_2` or `nom` (V, RustSec advisory-db directory listing, 404 for each, 2026-10-11). `openssl` carries one historical advisory, RUSTSEC-2016-0001 (insecure TLS defaults), patched at `>= 0.9.0`; `webauthn-rs-core` 0.5.5 requires `openssl ^0.10.75`, far above (V). `rand` carries RUSTSEC-2026-0097 (`rand::rng`/`thread_rng`, "unsound," informational, not a vulnerability class; already in ADR 0009's own References list), affecting `>= 0.9.0` and patched at `>= 0.9.3`; `webauthn-rs-core` requires `rand ^0.9.2`, which Cargo resolves forward to a patched 0.9.x unless something pins it down (U, confirm the resolved version in the implementation PR's lockfile). Whether `webauthn-rs-core` itself calls the affected functions: U.
5. **`unsafe` in the crate.** Out of scope to re-decide: ADR 0009 owner decision 1 already accepted `openssl-sys`'s FFI surface by name for this exact exception, and `unsafe_code = "forbid"` binds our own source, never a dependency's. `webauthn-rs`, `webauthn-rs-core` and `webauthn-rs-proto` themselves: not inspected line by line for this ADR (U). `der-parser`, `x509-parser`, `nom`, `serde_cbor_2`, `rand`, `rand_chacha`: spot-check only, the same depth ADR 0041 gave `elliptic-curve`/`crypto-bigint` (U for a full count).
6. **Constant-time claims.** None made or needed: WebAuthn assertion verification checks a public signature against public data (the authenticator's public key, the signed client data and authenticator data); this is not a secret-dependent comparison the way OPAQUE or envelope-key comparisons are. The sign-counter compare is a plain integer check on public state, already the same shape as TOTP's `last_step` compare in `rizzy-domain-auth` today.
7. **Builds and hygiene.** `rizzy-domain-auth` is `Side::Server`, not an ADR 0016 R1 no-I/O crate, so no `cargo check-wasm` obligation applies here (unlike `p256`); `cargo check`, `cargo deny check` and `cargo xtask check-deps` are the gates, all **U**, run in the implementation PR. New to `[workspace.dependencies]` (confirmed absent today by a direct scan, V, 2026-10-11): `openssl`, `openssl-sys`, `rand`, `rand_chacha`, `nom`, `der-parser`, `x509-parser`, `serde_cbor_2`, `base64`, `base64urlsafedata`, `webauthn-attestation-ca`. This is the first direct `rand` 0.9.x in the workspace; today only `rand_core` 0.10.1 is direct, and `rand` 0.8.8 is opaque-ke's transitive-only, feature-off dependency. ADR 0009's RNG rules state the `rand` 0.8 exception inside their second bullet, naming the `check-deps` no-I/O allow-list (ADR 0016 R1); the bullet immediately after it is the leaf-crates-depend-on-`getrandom`-directly bullet, and the R2 server-side-libraries bullet comes two bullets later, not immediately after the "fails CI" sentence as a first pass of this item read it — open question 6 restates the scope argument without relying on that adjacency. `rizzy-domain-auth` is `Side::Server`, not an R1 no-I/O crate (see Context), so on the textual scope alone ("the check-deps allow-list **for no-I/O crates**") the sentence does not bind it and this is a new `rand` table row, not an edit to the `rand` 0.8 row — supersedes nothing, same as the p256 Amendment's shape, not ADR 0029's `chacha20` supersession. `rand_chacha` is not merely `rand`'s own optional backend: `webauthn-rs-core` 0.5.5 declares it directly, `req = "^0.9.0"`, non-optional, default features on (V, crates.io dependency listing for `webauthn-rs-core` 0.5.5, 2026-10-11), alongside its own direct, non-optional `rand ^0.9.2` (default features on, same listing). Whether `webauthn-rs-core` uses its direct `rand_chacha` only as an OS-seeded CSPRNG path (fine) or constructs it from a fixed seed anywhere reachable outside tests (which would need the dev-dependency-only treatment the existing `chacha20`/`rng` row already gets under "deterministic RNGs are dev-dependencies only") is **U**, not resolved by the dependency listing alone — to confirm in the implementation PR by reading `webauthn-rs-core`'s own use of it, alongside the `rand` scope question. Open question 6 covers both. Either way, expect a new `rand`/`rand_chacha` cargo-deny duplicate-versions `warn` entry, the same category of debt ADR 0009 already carries for the two RustCrypto generations. `deny.toml`'s `openssl`/`openssl-sys` bans need the `wrappers` lines ADR 0009 owner decision 1 already specified: `openssl` with `wrappers = ["webauthn-rs-core"]`, `openssl-sys` with `wrappers = ["openssl", "webauthn-rs-core"]` (V, confirmed against the live manifest: `webauthn-rs-core` 0.5.5 depends on both directly, not only through `openssl`). The existing `openssl: true` rows in `crates/xtask/src/rules.rs` are the enforcement; no new xtask rule is needed beyond extending their reachable-crate sets once `Cargo.lock` shows the real closure. ADR 0009's checklist preamble ("the PR that adds the dependency must update this ADR... and CRYPTO.md §3") applies here too: the implementation PR adds a CRYPTO.md §3 row for the WebAuthn RP-ceremony crate, the way the `p256` Amendment added the "WebAuthn passkey signatures" row.
8. **Test vectors.** FIDO Alliance / W3C conformance vectors are not a RustSec-style published KAT set; `webauthn-rs`'s own test suite and its `webauthn-rs-device-catalog` dev-fixtures exercise registration and assertion against real authenticator data (L, not independently verified for this ADR). ADR 0058's implementation adds fixtures against real hardware (a security key) and/or a software authenticator from the same `kanidm` org, the way ADR 0029 required real KeePass/KeePassXC fixtures rather than invented ones. `p256`'s own RFC 6979/CAVP/Wycheproof vectors (ADR 0041 §8) are unaffected: this crate verifies signatures a user's hardware key makes, never signs with our own `p256` key.

## Consequences

### Positive
- Ceremony correctness (origin/RP-ID binding, multi-format attestation parsing, counter/clone detection) comes from a crate the Kanidm identity project maintains and exercises against real authenticators, not from code written once and rarely re-tested against new hardware.
- Confines the one `openssl`/FFI exception the project has already accepted to the exact two crates ADR 0009 named for it, before any WebAuthn code exists to tempt a wider one.
- Keeps CRYPTO.md Rule 2's "ours" list at eleven: no custom RP-ceremony construction joins the M8 audit scope.
- Neither `webauthn-attestation-ca` nor `webauthn-rs-core`'s attestation code does network I/O today (Decision, Recommendation), so `api`'s `Outbound: none` row (ADR 0010 §1) needs no change for this ADR.

### Negative
- A sizeable, mostly-unaudited dependency surface for one Must feature: at minimum `openssl`, `openssl-sys`, `rand`, `rand_chacha`, `nom`, `der-parser`, `x509-parser`, `serde_cbor_2` new to the workspace, on top of the three `webauthn-rs*` crates themselves.
- `openssl-sys`'s FFI, and `der-parser`/`x509-parser`'s parsing of attestation certificate chains from a device at registration time, both sit on data a hostile or counterfeit authenticator could shape during the ceremony — an adversary [THREAT_MODEL §4](../THREAT_MODEL.md#4-adversaries) does not currently name. A8 is a victim's own stolen or lost device, not a hostile authenticator presenting attacker-shaped data to the server at registration. The two nearest rows both miss: A16 covers a user-initiated import file (KDBX/XML, 1PUX, CSV) parsed client-side in `rizzy-import`, a different crate and trust boundary; A15 covers anonymous/unauthenticated network abuse (enumeration, IDOR, `icons` as an open proxy), not a physical authenticator's attestation statement. No row covers the latter. This ADR's checklist did not line-by-line audit either crate; ADR 0058 or a THREAT_MODEL update should add the missing adversary, not this ADR.
- Verified attestation means the server learns each account's authenticator AAGUID, and for batch/surrogate-basic attestation the signing CA's identity (device make/model), at registration — new server-visible, per-account metadata beyond [CRYPTO.md §14](../CRYPTO.md#14-what-a-malicious-server-can-still-do)'s current "metadata the server sees" list. Hiding server metadata in general is already a stated CRYPTO.md non-goal, and this does not touch Goal 1 (zero knowledge of secrets, not metadata), but it is a new category of disclosure, not another instance of a listed one, so §14 needs a new line either way, and the verify-and-discard-vs-verify-and-store choice belongs to ADR 0058 (open question 2).
- Grows the server image's build dependency on a system OpenSSL (or `openssl-sys`'s `vendored` feature), a cost ADR 0009 owner decision 1 already flagged as "confirmed in M3," not yet done.

### Risks
- **No public audit, as item 3 says.** A ceremony bug (a weak RP-ID check, a counter that never advances) would defeat the whole second factor silently. Mitigation: this is exactly the class of bug a dedicated, widely-deployed crate is less likely to ship than code written once in-house; M8 audit scope grows to match.
- **The new `rand` 0.9 line and RUSTSEC-2026-0097** (item 4): if `webauthn-rs-core` calls an affected function on a path our code reaches, the informational advisory could matter more than its "unsound, not a vulnerability" label suggests. Signal: `cargo deny check` in the implementation PR; mitigation is pinning forward to a patched `rand` if the lockfile does not already land on one.

## Alternatives considered

- **`webauthn_rp`.** Already rejected by ADR 0009's own fact sheet: pulls `rsa` 0.9 with RUSTSEC-2023-0071 (Marvin), unfixed.
- **Hand-rolled ceremony on `p256` alone.** Rejected in Context: covers ES256 only, not RP-ID/origin binding, multi-format attestation or counters, and is exactly the home-made construction CRYPTO.md Rule 1 and Rule 2 exist to prevent.
- **`webauthn-rs-core` directly, skipping the facade.** Saves nothing in dependency count (the facade is a thin wrapper; `-core` is the heavy crate) and loses the facade's RP-ID/origin-binding and credential-state API, pushing that correctness burden back onto our own code.
- **Waiting for a published audit.** Rejected as impractical, the same reasoning ADR 0041's "Alternatives considered" gives: no crypto crate this project ships has an audit of its exact shipped version, and the working rule is pinned-and-reviewed-now plus an M8 external audit.
- **CTAP2 directly, no WebAuthn browser layer, native-only.** Out of scope: ROADMAP §4.3 and ADR 0058 are the W3C WebAuthn ceremony, usable from the web vault too, not a CLI-only CTAP2 integration.

## Open questions for the owner

1. **Approve `webauthn-rs` `=0.5.5`, `default-features = false, features = ["attestation"]`, confined to `rizzy-domain-auth`, per the checklist above.** *Recommendation:* approve. No viable alternative exists (see Alternatives), and the open **U** items are exactly the mechanical checks ADR 0009's own text defers to the PR that adds the dependency.
2. **The `attestation` feature: keep it on, or default it off for a smaller untrusted-parsing surface at registration time?** *Recommendation:* keep it on. The Decision section confirms the dependency graph does not change either way (`der-parser`/`nom`/`x509-parser`/`webauthn-attestation-ca` are non-optional regardless), so turning it off buys no reduction in audited surface — only a smaller exposed API — while dropping verified attestation gives up real authenticator-provenance signal. Keeping it on also means accepting the AAGUID/attestation-cert metadata disclosure named in Consequences (Negative); ADR 0058 should decide verify-and-discard vs. verify-and-store and add the corresponding line to CRYPTO.md §14.
3. **The `deny.toml` wrapper lines (item 7): land now, standalone, or only with the implementation PR that adds the crate?** *Recommendation:* together, so `cargo deny check` is never green against a wrapper exception nothing yet uses; ADR 0009's own "the PR that adds the dependency must update this ADR" reads the same way for `deny.toml`.
4. **Proposed INV-85: add it to THREAT_MODEL §8.8 at acceptance?** *Recommendation:* yes; it costs one row and gives the existing `rules.rs` enforcement a named, testable invariant, the way every other dependency-boundary rule in §8.8/§8.9 already has one.
5. **Who re-runs the mechanical checks before the dependency lands.** *Recommendation:* the same PR that implements ADR 0058, mirroring ADR 0041's "owner answers at acceptance" split and its own `p256` Amendment of 2026-10-09.
6. **Does ADR 0009's RNG-rules sentence "any other path to `rand`... fails CI" bind `rizzy-domain-auth`, or only the R1 no-I/O crates, as item 7 reads it — and does the same answer cover `rand_chacha`?** *Recommendation:* only R1. The sentence sits inside the RNG rules' second bullet, naming the no-I/O `check-deps` allow-list edge for `rand` 0.8 through opaque-ke; the bullet right after it is about leaf crates depending on `getrandom` directly, and the R2 bullet about server-side libraries pulling `getrandom` in transitively comes two bullets later, not immediately after the "fails CI" sentence — item 7's first-pass claim of adjacency to R2 does not hold, but the scope reading does not depend on that adjacency: the sentence's own text is scoped to "the allow-list **for no-I/O crates**," and `rizzy-domain-auth` is not one. On that reading `webauthn-rs-core`'s direct `rand ^0.9.2` and `rand_chacha ^0.9.0` dependencies need no ADR 0009 change, provided the implementation PR confirms `rand_chacha` is used only as an OS-seeded CSPRNG path and never constructed from a fixed seed anywhere our code's execution can reach outside tests (item 7). If the owner reads the sentence as workspace-wide, or if `rand_chacha` is reachable as a seedable generator outside tests, this ADR's recommendation changes to a partial supersession of that one sentence (ADR 0020 point 9), named explicitly, not an Amendment, covering `rand_chacha` the same way as `rand`.
7. **Which CRYPTO.md section must exist before implementation?** *Recommendation:* a new §11.16 "WebAuthn 2FA (M3)", written by ADR 0058 before any WebAuthn code lands, parallel to §11.15's TOTP; this ADR defines no construction to stand in for it. §14's "metadata the server sees" list also needs a new line for the AAGUID/attestation-cert disclosure (Consequences, Negative; open question 2), in the same ADR 0058 PR.
8. **Where does the attestation CA list itself come from?** `webauthn-attestation-ca` ships no bundled trust anchors (Decision, Recommendation); we must supply the list. *Recommendation:* vendor a static list from the FIDO MDS BLOB, checked in and updated by reviewed PR, like any other dependency — no runtime fetch, so no outbound-network change for `api` (ADR 0010 §1). If the owner instead wants `rizzy-domain-auth` to fetch the MDS BLOB itself, that is a new outbound need and must route through ADR 0053's `icons` allow-list, or name ADR 0010 §1 as partially superseded (ADR 0020 point 9) — ADR 0058's implementation PR settles this before any attestation code ships.
