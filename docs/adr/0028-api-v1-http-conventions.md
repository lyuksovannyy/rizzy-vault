# ADR 0028: `/api/v1` HTTP conventions

- Status: Partially superseded by [ADR 0031](0031-retiring-old-opaque-setups.md) (item 3 in part); [ADR 0032](0032-healing-rotation-after-backup.md) (item 3 in part)
- Date: 2026-09-29
- Deciders: project owner
- Milestone: M1

## Context

[ADR 0002](0002-own-protocol.md) point 3 fixes `/api/v1/`, the unversioned `GET /api/meta`, `410 Gone` with a machine-readable code for a removed version, the `Rizzy-Client: <platform>/<version>` header with `client_too_old`, JSON over HTTPS with base64url binary fields ([CRYPTO.md §9.6](../CRYPTO.md#96-encoding-for-transport-and-storage)), and the types in `rizzy-proto`. [CRYPTO.md §5.10](../CRYPTO.md#510-sessions-after-authentication) fixes the bearer token (32 random bytes, stored as `SHA-256`) and the `device-request` signature over "the method, the path and query, and `SHA-256(request body)`", with a per-session `request_counter` accepted once in a sliding window of 64. CRYPTO.md §11 calls its paths "illustrative; the API specification owns them".

Everything else was chosen by the code and reported as a pre-v1.0 choice (V, 3087233): `rizzy-server` `lib.rs` "Wire and format details this crate decides", `http/{api,headers,security,web}.rs`, `config.rs`, `secrets_file.rs`, `secrets_backup.rs`, `server.rs` (`ServeLimits`); `rizzy-proto` `lib.rs` "Left open", `error.rs`, `meta.rs`. Clients (`rv` now, the web vault in M1 step 5, the extension in M2) need these fixed before they ship ([ADR 0002](0002-own-protocol.md) point 5: store-distributed clients update slowly). [ADR 0025](0025-rotation-vault-half.md) (Accepted) §1 moves `account/commit` and `recovery/complete` to the upload limit; for `recovery/complete` what grows is the response (the wraps), not the request (item 7).

Forces: [THREAT_MODEL](../THREAT_MODEL.md) §7.6 (uniform errors, body limits, "XFF trusted only from configured proxies", backoff per (account, source)), §7.7, INV-48, INV-49, INV-52; [ADR 0010](0010-server-shape.md) (TLS at the operator's reverse proxy, roles, secrets mount).

## Decision

The fifteen choices below are frozen for `v1` as described. Until v1.0 they change only under ADR 0002 point 5 (a server release that raises the minimum client versions); from v1.0, only additively. Items 11–15 are the operator's interface, not the client's: a rename keeps the old name working, with a logged warning, for two server releases.

1. **Paths and methods.** The 27 endpoints of `rizzy-server` `http/api.rs` (module table), under `/api/v1/`, grouped by resource (`register`, `login`, `device-auth`, `account`, `devices`, `healing`, `recovery`, `totp`, `vault`), verb last (`start`, `finish`, `commit`, …). `POST` for everything, including reads that carry a body; `GET` (and `HEAD`) only for `GET /api/v1/devices/grants`. *Why:* a request body never goes in a URL, so no id list, cursor or token reaches a URL or an access log (INV-52); one method keeps the signing rule simple.
2. **Success.** `200` with `Content-Type: application/json` and a `rizzy-proto` response body; `204 No Content`, no body, for the "empty success" rows. "No body" requests are `POST` with an empty body. *Why:* the empty success carries nothing to parse.
3. **Errors.** Every error under `/api/` is `{"error":"<code>"}` with this status: `invalid_request` and `client_too_old` 400; `unauthorized` and `second_factor_required` 401; `fresh_session_required` 403; `not_found` 404 (also an unknown `/api/` path, and a role not running); `state_conflict`, `stale_epoch`, `record_conflict`, `prev_seq_mismatch` 409; `api_version_gone` 410; `payload_too_large` 413; `rate_limited` 429; `internal` 500. A method a route does not serve is `405` with `invalid_request`. No message, no echo of input (§7.6 "I", INV-48). Clients read an unknown code as `unknown` and branch on the code, never on the status. *Why:* one table, one body shape; the status lets proxies and `curl` users see the class.
4. **Bearer token.** `Authorization: Bearer <43 base64url characters>`, the scheme name case-insensitive, nothing else accepted; never a query parameter or cookie (INV-52). *Why:* the standard header; no cookie means no ambient credential and no CSRF surface.
5. **Request signing.** `Rizzy-Request-Counter`: the `u64` counter in decimal, 1–20 digits, no sign, no leading zero; `Rizzy-Request-Signature`: the 82-byte signature container as 110 base64url characters. Both or neither (`0` alone is a valid counter). [CRYPTO.md §5.10](../CRYPTO.md#510-sessions-after-authentication) and the `device-request` row of §10.2 are the single owner of the signed message and of the counter rule; this item fixes only the HTTP bytes that feed them. *Why:* the `Rizzy-` prefix matches `Rizzy-Client`; the rules below are stated rather than guessed, because a proxy or a URL library that "tidies" a target breaks every signature.
   - **Signed bytes.** `method` is the request method as sent (upper case). `path_and_query` is the raw bytes of the origin-form request-target on the request line: the path and, when a `?` is present, the `?` and everything after it. Neither side parses, decodes, normalises or re-encodes them before signing or verifying: percent-encoding and its hex case, dot segments, `//`, a trailing `?` (an empty query is not "no query"), parameter order and duplicate parameters are signed exactly as sent. Clients send origin-form only, and `v1` defines no query parameter, so clients send no query. What the code does (V, 9ee3d72, `http/api.rs` `authenticate`): it takes `Uri::path_and_query()` of the target hyper parsed, which keeps those bytes unchanged; for an absolute-form target (`POST http://host/path`) that is its path-and-query part, the scheme and authority ignored (L: not covered by a test). The router matches the 27 literal paths byte for byte, so a path with a dot segment, `//`, a trailing slash or a percent-encoded octet is `404 not_found` before any session check; only the query can vary under a valid signature, and no endpoint reads it.
   - **Reverse proxy.** The server verifies the request-target bytes the client sent to the public origin. The proxy forwards path and query byte for byte and serves the API at the origin's root; one that rewrites, normalises, re-encodes or prefixes them is an unsupported deployment (every signed request fails `401`, closed). The scheme, the host and the `Host` header are not read into the signed message, and no other header is (`rizzy-core` `DeviceRequest`). That is acceptable because `server_origin` (scheme, host and port, CRYPTO.md §2) is signed: the client signs the origin it dialled, the server rebuilds the message from its configured `RIZZY_ORIGIN`, so a signature made for another origin fails whatever `Host` says, and a proxy may rewrite `Host`.
   - **Replay window.** CRYPTO.md §5.10 says "at most once per session, within a sliding window of 64" and leaves the edges open; the code (V, `rizzy-domain-auth` `rules.rs` `RequestWindow`, `REQUEST_WINDOW = 64`) fixes them, and CRYPTO.md §5.10 takes this text when this ADR is accepted. Per session the server stores `max`, the highest counter accepted, and a 64-bit map of `max − 63 ..= max`. The first signed request may carry any counter. `c > max` is accepted whatever the jump, and the window slides (a jump of 64 or more forgets the map). `max − 63 ≤ c ≤ max` is accepted once. A duplicate, or `c ≤ max − 64`, is refused. The window lives in the session's database row and is updated in the same write transaction as the check, under the account lock, only after the signature verified: a forged request cannot move it, a restart does not reset it, and replicas share it. A counter is spent once the request authenticates, even if the request then fails. Clients start at 1, add 1 per request and never reuse one.
   - **One answer.** A bearer token that is missing, malformed, unknown or expired, a counter or signature that is malformed, replayed, too old or wrong, a signature missing on a device session or present on any other, and a device no longer usable all get the same `401` `{"error":"unauthorized"}`, with no `WWW-Authenticate`, no detail and no per-component log line: the server does not say which part failed. Timing is not equalised: header-only failures answer before the body is read (item 6), signature and counter failures after it, which tells only the holder of a valid token that the token is valid.
   - **Vectors.** `crates/rizzy-core/tests/vectors/statements.json` (tier A, CRYPTO.md §15 item 1) has one `device-request` vector; it gains vectors for an empty query (`/p?`), duplicate parameters, the same octet percent-encoded in lower and upper case, `/a/./b`, `/a/../b` and `//a`, and a `rizzy-server` listener test sends the same targets to pin that the bytes verified are the bytes sent.
6. **Order of checks.** (a) Routing: an unknown path is `404`, a wrong method `405`. (b) On an endpoint that takes a session, `Authorization` and the two signing headers are parsed: a missing or malformed one is `401` before any database lookup. (c) The token is looked up in one read transaction: an unknown or expired token, a session kind that does not fit the presence of a signature, or the recovery-only session on an "OPAQUE or device" row is `401` before any body byte is read. (d) Only then does a large-limit request take a large-body slot (item 8). (e) Body limit and deadline. (f) Full authentication: the token again, the signature over the body as received, the counter. (g) Parsing (unknown fields refused). (h) The domain. No route without a session has the upload limit (item 7), so an anonymous request never gets it or a slot; `login/start` and `login/finish` run (b)–(c) only when `Authorization` is present. Step (c) cannot check the signature, which covers the body, so the holder of a valid device-session token can occupy a slot for one body read with a wrong signature; items 7–8 bound that. *Why:* §7.6 "D".
7. **Body limits.** 1 MiB for every endpoint; `RIZZY_MAX_UPLOAD_BYTES` (default 32 MiB, minimum 32 MiB, maximum 256 MiB) for the session-gated `vault/upload`, `vault/heal` and `account/commit` (the last per ADR 0025 §1); 0 for the body-less endpoints. `recovery/complete` has no session, and its request is the fixed-size `RecoveryRequest`, so its **request** stays at 1 MiB, outside the large-body slots; ADR 0025 §1's limit is read as applying to its response (open question 5). Enforcement is streaming: a `Content-Length` that is not a decimal `u64` is `400`, and one above the limit is `413` before a body byte is read; the body, with or without a declared length (chunked), is read frame by frame into a buffer that never grows past the limit, and the first frame that would pass it ends the read with `413`, the rest left unread. `rizzy-proto` limits hold the 256 MiB maximum as `MAX_UPLOAD_BODY_LEN`, which clients use as their own cap ([ADR 0026](0026-client-device-state-and-cache.md) §3). *Why:* sized for one maximal record (a 16 MiB envelope with a 1.5 MiB statement) and for ADR 0025's wrap sets; an anonymous large body would let anyone hold every slot (§7.6 "D").
8. **Slow and concurrent bodies.** Read deadline = 30 s + limit ÷ 64 KiB/s (46 s for 1 MiB); a missed deadline or an aborted body is `400 invalid_request`, logged as `body_read_timeout` or `client_aborted` with the route only. It stays `400` rather than `408` or a new code: the code set stays closed (item 3), an aborting client reads no answer, and a slow client is told what any malformed request is told, which says nothing about the session or the deadline; nothing was applied, so the request may be sent again. At most 8 large-limit requests at once **per `api` process** (an in-process semaphore, not shared through the database); a slot is held from step (d) of item 6 until the response is built; a request that waits 10 s for a slot is `429 rate_limited`. Worst-case request bodies held by one process: 8 × the upload limit plus 1 MiB for each of the other 1016 connections (item 9; HTTP/1.1, one request per connection), about 1.25 GiB at the default and 3 GiB at the 256 MiB maximum, and up to about 1.75 × that while bodies are parsed, since the decoded copy lives beside the raw one (estimate, not measured). With N `api` processes the bound is N times that: M1 has no cluster-wide cap, so the operator sizes every process for it and limits connections at the proxy. *Why:* bounds memory per process and slow-loris bodies.
9. **Listener.** HTTP/1.1 in clear on the listener, TLS at the reverse proxy (ADR 0010); header-read and keep-alive idle timeout 10 s; at most 1024 connections; shutdown grace 30 s. The listener is plaintext only because the hop from the proxy is trusted: loopback or a private network the operator controls (ADR 0010's `edge` network); it is never published directly. No response compression under `/api/`. *Why:* §7.6 "D"; compressing responses that hold tokens next to request-controlled bytes invites BREACH-style length oracles.
10. **Response headers.** Every response: `Strict-Transport-Security: max-age=31536000` (no `includeSubDomains`, no `preload`: the operator's other hosts are not ours to pin), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, and `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`, except the web role's pages, which carry `WEB_CSP` of `http/security.rs` (`'self'` only, `'wasm-unsafe-eval'`, no inline script or style, `object-src`, `base-uri`, `form-action` `'none'`, `require-trusted-types-for 'script'`). API responses add `Cache-Control: no-store`. HSTS is sent because the public origin must be HTTPS (`RIZZY_ORIGIN` is `https://…`); on the plaintext hop it is only bytes the proxy forwards. CRYPTO.md §2's origin parser also admits `http`, the server does not refuse it today, browsers ignore HSTS there, and such an origin is for local testing only (open question 6). No CORS headers: the web vault is same-origin; the extension's access is the M2 ADR's. *Why:* INV-49, §7.7.
11. **Rate-limit source and trusted proxies.** The source is the peer address, or, when the peer is in `RIZZY_TRUSTED_PROXIES`, the first address from the right of all `X-Forwarded-For` lines that is not a trusted proxy. Elements are read from the right only, up to 16 lines and 1024 bytes counted from the right; the client-controlled part left of the found address is never read. **Amended:** when the peer is a trusted proxy and the header is missing, or a malformed element, the read bound or the left end comes before an untrusted address, the request is `400 invalid_request`; it never falls back to the proxy's address, whose bucket every user behind it shares (the code falls back today). IPv4-mapped IPv6 is read as IPv4. A source is the IPv4 address or the IPv6 /64. `Forwarded` (RFC 7239) is not read. The buckets and numbers stay `rizzy-domain-auth`'s. `RIZZY_TRUSTED_PROXIES` lists only infrastructure the operator controls (its own proxy or load balancer, by the address the listener sees), never a network it does not run: a listed address can name any source. Grammar, as `config.rs` parses it: a comma-separated list of single IP addresses, spaces around each trimmed, IPv4 dotted quad or IPv6 text (Rust `IpAddr`); no CIDR prefix, port, brackets, zone id or host name; an unset or blank value means no proxy; an element that does not parse, an empty one from a stray comma included, refuses the configuration. Matching is address equality after the IPv4-mapped rule, so a proxy pool lists every address (CIDR would be an additive change). *Why:* §7.6 "S"; one subscriber holds a whole /64, so per-address buckets would give 2^64 of them.
12. **Configuration.** The file is named by `--config <path>` or `RIZZY_CONFIG`, from the command line or the environment only, never from the file itself. Settings `RIZZY_ROLES`, `RIZZY_ORIGIN`, `RIZZY_LISTEN` (default `127.0.0.1:8080`), `RIZZY_DATA_DIR` (`/data`), `RIZZY_DATABASE_URL`, `RIZZY_SECRETS_FILE` (`/run/rizzy-secrets/secrets.json`), `RIZZY_SIGNUP` (`closed`|`open`), `RIZZY_TRUSTED_PROXIES`, `RIZZY_LOG_LEVEL`, `RIZZY_WORKER_INTERVAL_SECS`, `RIZZY_MAX_UPLOAD_BYTES`; from the environment or a `NAME=value` file (64 KiB, `#` comments, no quoting; unknown, repeated or malformed lines refused); environment over file, `--roles` over both; `--roles` and `--config` are the only flags. No secret on the command line. **Secret boundary:** no setting holds a key. `RIZZY_SECRETS_FILE` is a path, not a secret; keys live only in the file it names (item 13). The one setting that can carry a secret is `RIZZY_DATABASE_URL` (`postgres://` or `postgresql://`, possibly with the password; unset means SQLite in the data directory): it comes only from the environment or the file, is held in a zeroizing buffer, and appears in no `Debug` output, log line or error (errors name the setting, never its value). A configuration file that holds it is readable by the server's user only; the server does not check that file's mode, so this is the operator's duty. *Why:* ADR 0010's names and mounts; a typo must fail, not pass.
13. **Secrets file.** Single owners: CRYPTO.md §5.11 owns what the file contains (its "single normative list", `format = 1`, the key sizes) and the backup's header fields, context and key; this item owns the JSON layout of both files, and the module docs of `secrets_file.rs` and `secrets_backup.rs` mirror it. JSON, unknown members refused, ≤ 256 KiB, outside the data directory, written with mode 0600 (the reader does not check the mode): `{"format":1,"setups":[{"setup_id","server_setup"}],"enum_key","data_keys":[{"data_key_id","key"}],"current_data_key_id","bootstrap_token"?}`, binary as base64url. The secrets backup file mirrors §11.14: `{"format":"rizzy-vault-secrets-backup","version":1,"kdf_id","backup_salt","backup_id","created_at","data"}`. *Why:* exactly CRYPTO.md §5.11's list, in the file shape CRYPTO.md already uses.
14. **`GET /api/meta`.** `{"server_version":"x.y.z","api_versions":["v1"],"min_client_versions":[{"platform","version"}]}`, unauthenticated, unknown members ignored by clients. It is public on purpose: it holds no secret and nothing about any account, and the server version is disclosed so that a client can tell it is too old before it authenticates (ADR 0002 point 3). **Amended:** the server now reads `Rizzy-Client` (platform ≤ 32 bytes of `[a-z0-9-]`, one of `web`, `cli`, `extension`, `macos`, `windows`, `linux`, `ios`, `android`; version ≤ 64 bytes of `[0-9A-Za-z.+-]`, compared by SemVer 2.0.0 precedence, and a version that is not SemVer counts as below any minimum) and answers `400 client_too_old` when the platform has a minimum above the version; a missing or malformed header is served normally in M1 (so `curl` works) and refused from v1.0 (open question 2). Clients always send it. The header is compatibility signalling, not a security boundary: it is unauthenticated and chosen by the client, so nothing is granted or withheld for security on its strength, and a client that lies only loses the early `client_too_old` answer. *Why:* ADR 0002 point 3; today the header is ignored and the minimum list is empty.
15. **Web role paths.** `/` and `/index.html` (`GET`, `HEAD`); every other path outside `/api/` is a plain-text `404`; nothing is read from disk. *Why:* §7.7 "E".

**Retry after an unknown outcome** (the connection failed before the answer arrived). The client sends the same body again; over a device session it signs it again with a fresh counter, since a counter is spent once accepted (item 5) and the signature is no part of any comparison below. This table only points to the mechanism that makes the repeat safe; the named document owns it.

| Class | Endpoints | A repeat | Owner |
|---|---|---|---|
| Reads | `account/state`, `vault/fetch`, `devices/grants`, `GET /api/meta` | changes nothing | – |
| Upload | `vault/upload` | a byte-identical record is answered `already_stored`, an acknowledgement; a different record at that dot is `record_conflict` | [ADR 0021](0021-server-compaction.md) §9 "Already stored" |
| Healing | `vault/heal`; `healing/bundles`, `healing/account-state`, `healing/grants` | records already stored are skipped; held bundles, the byte-identical held state and re-sent grants are accepted | ADR 0021 §9; [ADR 0012](0012-sync-engine.md) §7 |
| Commit | `account/commit`, `devices/enrol`, `devices/web-certificate` | a byte-identical repeat of the applied state is success, before the vault half is read; anything else is `409` | CRYPTO.md §11 "Secrets before commit"; ADR 0025 §4 |
| Register finish | `register/finish` | a byte-identical repeat for the same `account_id` is success | CRYPTO.md §11.1 step 8; ADR 0026 (signup pending) |
| Recovery | `recovery/start`, `recovery/complete`, `recovery/cancel` | start returns the pending recovery; complete may be repeated with the same code until the recovery commits; cancel reports whether one was pending; start and complete count against the rate limit | CRYPTO.md §11.9 |
| Set to a value | `devices/suspend`, `devices/unsuspend`, `devices/grants/ack` | same result (suspend returns the same head) | CRYPTO.md §11.8, §10.1 |
| Single use | `login/*`, `device-auth/*`, `register/start`, `account/reregister/start`, `totp/*` | not safe to repeat blindly: the login state and the challenge are taken once, a TOTP code is accepted once; the client restarts the flow or reads `account/state` first | CRYPTO.md §5.10, §5.11, §11.15 |

`rizzy-proto` keeps the constants for items 1, 4, 5, 7 and 14 (it may, once this is Accepted), so clients and server share them. A header test pins items 3, 5, 10 and 14; `server_headers` fuzzes items 4, 5 and 11.

## Consequences

### Positive

- Clients can be built against a written contract; `rv`, the web vault and the extension agree by construction.
- Nothing that names an account, device or cursor can land in a URL or access log.

### Negative

- `POST` reads are not cacheable and not idempotent to intermediaries; retries are the client's decision.
- Operators whose proxy strips a path prefix must serve rizzy-vault at a host's root.
- Items 5, 11 and 14 need code changes (the pathological-target vectors and the listener test of item 5; refusing a missing or malformed `X-Forwarded-For` from a trusted proxy, with `server_headers` fuzz and unit tests; reading `Rizzy-Client`). CRYPTO.md §5.10 takes item 5's window edges in the change that accepts this ADR.
- Large-body capacity and its memory bound are per process; a deployment with several `api` processes has no global cap (item 8).
- A proxy that does not set `X-Forwarded-For` breaks every request once it is listed in `RIZZY_TRUSTED_PROXIES`; that is the operator's configuration error, and it fails closed.

### Risks

- If `v1` must change before v1.0, every store-distributed client has to update (ADR 0002 point 5); signal: an M2 extension review delay longer than a week.

## Alternatives considered

- **Resource-style REST** (`GET /vaults/{id}/ops?cursor=`). Puts ids and cursors in URLs and logs (INV-52), for no gain.
- **`426 Upgrade Required` for `client_too_old`.** RFC 9110 ties it to the `Upgrade` header; `400` with the code says the same without that meaning.
- **Signing a normalised path.** Would need a normalisation rule both sides implement identically; signing the bytes received is simpler and fails closed.
- **HSTS with `includeSubDomains; preload`.** Would pin hosts the operator may not control.

## Open questions for the owner

1. **`Retry-After` on `429`.** Recommendation: yes, whole seconds, from the bucket's backoff; it tells an attacker nothing the refusal does not.
2. **Require `Rizzy-Client` before v1.0?** Recommendation: no; require it from v1.0 (item 14).
3. **`Forwarded` (RFC 7239).** Recommendation: no in M1; `X-Forwarded-For` is what the shipped Caddy example sets.
4. **OpenAPI generator** (ADR 0002 point 3, "chosen in M1"). Recommendation: decide with the web vault (M1 step 5), as a dependency change under CLAUDE.md.
5. **ADR 0025 §1 and `recovery/complete`.** Its text gives the endpoint the upload limit; item 7 reads that as the response size and keeps the anonymous request at 1 MiB. Recommendation: confirm this reading, and correct ADR 0025's wording in a later ADR (ADR 0020 point 9) if the owner wants the text to match.
6. **Refuse an `http` `RIZZY_ORIGIN`?** The parser admits it (CRYPTO.md §2) and the server starts with it. Recommendation: refuse it at startup unless the host is a loopback address or `localhost`, so that "the public origin is HTTPS" (item 10) is enforced, not only documented.
