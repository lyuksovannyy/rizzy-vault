# ADR 0070: Crypto-crate approval: mail-auth for SPF/DKIM/DMARC verification

- Status: Accepted
- Date: 2026-10-11
- Deciders: project owner
- Milestone: M6

## Context

[ROADMAP §4.8](../ROADMAP.md#48-aliases--email-receiving-m6) lists as a Must, M6: "Spam/abuse filtering **before** encryption (rspamd or equivalent), SPF/DKIM/DMARC verification shown in UI." [THREAT_MODEL §6.1](../THREAT_MODEL.md#6-email-ingress-m6) step 4 already names the crate: "`smtp` sends the plaintext message to rspamd... It also verifies SPF, DKIM and DMARC (for example with mail-auth)." [CRYPTO.md §11.13](../CRYPTO.md#1113-mail-ingress-m6) point 1 fixes the same ordering: filtering runs on plaintext, before the HPKE seal.

[ADR 0009](0009-crypto-dependency-policy.md)'s RNG rules already name mail-auth as an anticipated case: "Server-side libraries may pull getrandom in through third-party crates (sqlx-postgres, mail-auth), but never depend on it themselves." [ADR 0016](0016-workspace-layout.md)'s M0 fact sheet recorded the same dependency (V, its own lockfile scratch build): "mail-auth 0.13.3 depends on getrandom 0.2 and 0.4 and on hickory-resolver → rand 0.10." Neither ADR ran [ADR 0009](0009-crypto-dependency-policy.md#approving-a-new-crypto-crate)'s approval checklist for it; this ADR does, the way [ADR 0041](0041-p256-crate-approval.md) ran it for `p256` for a comparable server/transport-adjacent signature crate rather than a plain dependency add. **This ADR adds no code.** The dependency lands only after acceptance, in the PR that amends ADR 0009's crate table and [CRYPTO.md §3](../CRYPTO.md#3-primitives), as ADR 0009's own Amendments section provides for — the mechanism [ADR 0030](0030-client-tls-rv.md)'s rustls/ring entry and ADR 0041's `p256` entry already used. This ADR therefore extends ADR 0009 and supersedes nothing.

**Where it lives.** `rizzy-smtp-ingress` ([ADR 0016](0016-workspace-layout.md) §3, M6) is "no" on the wasm32/no-I/O column, so [R1](0016-workspace-layout.md#4-dependency-rules) does not apply; [R2(b)](0016-workspace-layout.md#4-dependency-rules) and [R3](0016-workspace-layout.md#4-dependency-rules) do — no direct `getrandom` dependency, no route to `rizzy-storage`, sqlx or any domain crate. The crate's planned outbound set already includes DNS ([ADR 0010](0010-server-shape.md) §1 role table, `smtp` Outbound: "rspamd, the `api` internal listener, DNS"), which is what mail-auth's resolver needs.

**Trust boundary, stated plainly.** DKIM verifies a signature against a public key the *sending domain* publishes in its own DNS — not a parameter our server supplies, so this is a different relationship from [CRYPTO.md §1](../CRYPTO.md#1-goals-non-goals-and-rules) Rule 5 ("the client decides; the server only names"), which governs our zero-knowledge vault crypto, not third-party mail authentication. [THREAT_MODEL §6.3](../THREAT_MODEL.md#63-what-this-means-stated-plainly) already says the results are "only as trustworthy as the `smtp` role that produced them" — informational, shown in the UI, never a basis for access control. This ADR only approves the crate that computes that result.

**A second leak the crate itself introduces.** Mail-auth's SPF/DKIM/DMARC checks make `smtp`'s own outbound DNS queries (SPF TXT, DKIM `_domainkey.<sender-domain>` TXT, DMARC `_dmarc.<sender-domain>` TXT) for every accepted message, telling the configured resolver — and, for a sender domain whose records a recursive resolver fetches live, potentially that domain's own authoritative nameservers — which domains this instance is receiving mail from, and when. [THREAT_MODEL §6.2](../THREAT_MODEL.md#62-what-the-server-sees-and-for-how-long) already names the parallel case for rspamd's RBL/URIBL lookups but has no line yet for mail-auth's own lookups ([On acceptance](#on-acceptance) schedules one).

**Out of scope.** Which `smtp↔api` message carries the authentication results, own-listener vs. MTA-handoff, and the rest of the SMTP flow are ADR 0069's (this batch, Proposed), not this ADR's.

## Decision

### Recommendation: `mail-auth` (Stalwart Labs), pinned `=0.13.3`, verification only

```toml
mail-auth = { version = "=0.13.3", default-features = false, features = ["ring"] }
```

`ring` is already approved, but, per [ADR 0009](0009-crypto-dependency-policy.md)'s 2026-10-05 Amendment and [ADR 0041](0041-p256-crate-approval.md) §"Alternatives considered", only in `rizzy-cli` for `rv`'s TLS ([ADR 0030](0030-client-tls-rv.md)) — a leaf crate. This ADR extends its approved scope into `rizzy-smtp-ingress`, a second, separate dependency edge the ADR 0009 table must gain a second row for, not a reuse of the existing one.

**Feature choice (V, mail-auth 0.13.3's own `Cargo.toml`, `docs.rs/crate/mail-auth/0.13.3/source/Cargo.toml`, and `hickory-resolver` 0.26.3's, read 2026-10-11):**
- `ring` turns on `dep:ring`, `dns-hickory` (→ `dep:hickory-resolver` `=0.26.x`, which keeps its own on-by-default `system-config` and `tokio` features), and — unconditionally, not optionally — `hickory-resolver`'s `tls-ring`, `dnssec-ring` and `rustls-platform-verifier` features. **Never** the default `aws-lc-rs`: a second C/assembly crypto library, where `ring` ≥0.17.12 is already in the server's tree through sqlx-postgres/rustls ([ADR 0030](0030-client-tls-rv.md) Context) — the same "beside `ring`, which the server already ships" reasoning ADR 0030 used against `aws-lc-rs` for `rv`'s TLS.
- **Never** `rust-crypto`. Its `rsa` 0.9.8 dependency carries RUSTSEC-2023-0071 (Marvin attack: non-constant-time RSA, private-key recovery through network-observable timing), **still unpatched as of 2026-09-12** (`patched = []`); upstream's own advisory says to "avoid using the `rsa` crate in settings where attackers can observe timing, for example over the network" — exactly this role, and [CRYPTO.md §3](../CRYPTO.md#3-primitives) already rejects it project-wide ("RSA of any kind: `rsa` 0.9 carries RUSTSEC-2023-0071 (Marvin) with no fix"). `cargo deny check` would hard-fail on it; no fixed version exists to pin. `ring`'s RSA-PKCS1v15 and Ed25519 verification (BoringSSL-derived, written constant-time, **L**, the characterization [ADR 0030](0030-client-tls-rv.md) already gives `ring`) covers every signature algorithm RFC 6376 DKIM1 verification needs, without it.
- **Never** `generate` (RSA/Ed25519 key-pair generation) or any signing path: [ROADMAP §4.8](../ROADMAP.md#48-aliases--email-receiving-m6) lists sending/replying as Won't for v1.0, so only `verify_dkim`, `verify_spf`, `verify_dmarc` are called.
- **Never** `arc` (reclassified Historic upstream; ROADMAP asks only for SPF/DKIM/DMARC), `rkyv`, or `test`.
- **Never** `report` (DMARC aggregate XML generation/parsing; pulls `quick-xml` and `zip`): ROADMAP §4.8 does not ask us to send or receive aggregate reports.
- Always-on regardless of features (V, same manifest): `flate2`, `hashify`, `idna`, `memchr`, `rustls-pki-types`, `serde`, `serde_json`, `similar`, and — not new to the workspace — `mail-parser` `=0.11.9`, the MIME parser [THREAT_MODEL §6.4](../THREAT_MODEL.md#64-mitigations) already names for `rizzy-smtp-ingress`.

### The ADR 0009 checklist, answered

1. **Need.** RFC 6376 (DKIM1), RFC 7208 (SPF), RFC 9989–9991 (DMARC) verification, fixed by [ROADMAP §4.8](../ROADMAP.md#48-aliases--email-receiving-m6) and already named by [THREAT_MODEL §6.1](../THREAT_MODEL.md#6-email-ingress-m6) step 4. No construction of ours (**V**).
2. **Provenance.** Stalwart Labs LLC (`stalw.art`), which also ships the Stalwart Mail Server; repository `stalwartlabs/mail-auth`, 127 stars, 37 forks, 4 open pull requests (**V**, GitHub/crates.io, 2026-10-11). 41 published versions, current 0.13.3. Bus factor beyond one named maintainer (`mdecimus`): **U**.
3. **Audit history.** None found, for `mail-auth` or `hickory-resolver` (**U**, absence of evidence — the same position ADR 0009 accepts for `hpke`/`blake2`/`poly1305`).
4. **Advisories (V, RustSec advisory-db GitHub contents API, 2026-10-11).** `mail-auth`: none filed. `hickory-resolver`: none filed. `hickory-proto`: RUSTSEC-2025-0006 (DNSSEC RRSIG-chain bypass, fixed ≥0.25.0-alpha.5) and RUSTSEC-2026-0118 (NSEC3 closest-encloser DoS, code later moved out, unaffected ≥0.26.0-beta.1) are both already fixed in 0.26; RUSTSEC-2026-0119 (O(n²) CPU-exhaustion DoS in message encoding, fixed only ≥0.26.1). `hickory-net` — the crate RUSTSEC-2026-0118's NSEC3 code moved into, and (V, its own normalized `Cargo.toml`) a **non-optional** dependency of `hickory-resolver` 0.26.3, present whichever of mail-auth's resolver or crypto features we pick: **RUSTSEC-2026-0120**, the same NSEC3 unbounded-loop OOM, re-filed against its new home, fixed only ≥0.26.1. None of mail-auth's own `"0.26"`/`"0.26.3"` SemVer ranges, read alone, guarantee the fix — but `hickory-resolver` 0.26.3 (the current latest, V) already pins `hickory-net = "0.26.3"` and `hickory-proto = "0.26.3"`, both past every one of these fixes. The approval PR's `Cargo.lock` must resolve both to ≥0.26.1 and stay there; `cargo deny check` enforces it once the crate is in the tree. The predecessor name `trust-dns-proto` carries only a 2026 rename notice and one 2018 advisory, both moot post-rename.
5. **`unsafe` in the crate.** Not established for `mail-auth` itself here (**U** — GitHub code search needed sign-in; a `grep.app` repo filter did not isolate the crate in this session). The approval PR must run `cargo geiger` or an equivalent grep, as ADR 0009's `blake2`/`poly1305` entries do.
6. **Constant-time claims.** Covered under "Never `rust-crypto`" above: choosing `ring` is what keeps the Marvin-attack-affected `rsa` crate out of a process verifying attacker-controlled, network-delivered signatures.
7. **Builds and hygiene.** `mail-auth`/`hickory-resolver` licenses: `Apache-2.0 OR MIT` / `MIT OR Apache-2.0` (**V**), already on `deny.toml`'s allow-list. Neither crate's own manifest reaches `openssl`/`openssl-sys` (**V**); the existing ban is unaffected. **Real cost 1:** `hickory-resolver` turns on `rustls-platform-verifier` by its own crate default (V, its manifest), and mail-auth's `ring` feature names it a second, redundant way — no feature combination keeps `dns-hickory` and drops it. That is the same crate [ADR 0030](0030-client-tls-rv.md) rejected for `rv`'s TLS ("+20 packages… 26 `unsafe` lines in the crate and about 400 in `security-framework`"); here it lands one layer deeper, in the isolated `smtp` role (Open question 2), not a trust-sensitive client path. **Real cost 2:** mail-auth's `ring` feature also forces `hickory-resolver/dnssec-ring` unconditionally (V, manifest), so the DNSSEC/NSEC3-validation code path RUSTSEC-2026-0118/-0120 describe is compiled in whether or not we configure the resolver to use it (item 4, Open question 3). `rizzy-smtp-ingress` never targets wasm32 ([ADR 0016](0016-workspace-layout.md) §3), so mail-auth's wasm32-`cfg`-gated `getrandom` 0.2/0.4 edges (**V**, confirmed in its manifest) never enter this crate's real closure; native `getrandom` exposure instead comes through `hickory-resolver` → `rand` 0.10 and `ring`'s own OS-RNG use, which is [ADR 0009](0009-crypto-dependency-policy.md#rng-rules)'s existing R2(b) allowance, not R1. Running `cargo check-wasm`/`cargo deny check`/`cargo xtask check-deps` with the crate actually added is **U**, left to the approval PR, as ADR 0041 item 7 left its own mechanical checks.
8. **Test vectors.** RFC 6376 Appendix A gives a full DKIM1 worked example (key, message, signature) usable as a known-answer vector. SPF and DMARC have no single canonical IETF vector set (**U**); mail-auth ships its own `tests/`, run by upstream CI. [CRYPTO.md §15](../CRYPTO.md#15-testing) item 2 means the approval PR re-runs that suite against our pinned build and adds one project fixture: a real DKIM-signed message checked against a captured DNS answer, so a regression is caught without live DNS.

### The `MailAuthResult` mapping

[ADR 0068](0068-alias-identity-model.md) §4 fixes the one-byte `MailAuthResult` id set (`none`/`pass`/`fail`/`softfail`/`neutral`/`temperror`/`permerror`/`not evaluated`) that `smtp` writes into `MAIL_MESSAGE`, and names this ADR as the owner of the mapping from `mail-auth`'s own SPF/DKIM/DMARC result types onto those ids — a duty this ADR had not otherwise stated. This ADR accepts it: the implementing PR adds, in `rizzy-smtp-ingress`, one pure function per check (SPF, DKIM, DMARC) from `mail-auth`'s result type to `MailAuthResult`, with a known-answer unit test per `mail-auth` variant (checked against the pinned 0.13.3 API, not re-enumerated here, **U**), and maps any `mail-auth` variant with no exact `MailAuthResult` counterpart to `permerror` rather than inventing a new id (§4's own reserved range, `0x07`-`0xFE`, stays unused by this mapping). The mapping function is this ADR's addition to the implementing PR's scope, not a new ADR.

### Proposed invariant (owner assigns the ID at acceptance)

| ID | Invariant | From | Verified by |
|---|---|---|---|
| INV-?? | `mail-auth`'s crypto-provider feature is pinned to `ring`. Its `rust-crypto` feature (RUSTSEC-2023-0071, unpatched Marvin-attack timing side channel in `rsa`, directly network-observable at SMTP ingress) and its default `aws-lc-rs` feature are never enabled. | M6 | Two halves of `cargo xtask check-deps`'s existing machinery ([ADR 0009](0009-crypto-dependency-policy.md) Amendments, 2026-09-26; `crates/xtask/src/check.rs`), neither newly invented here. **Never default `aws-lc-rs`:** `crypto_default_features` already walks every workspace member's own declarations, not only `rizzy-core`'s, so once `mail-auth@0.13` joins `FEATURE_RULES` with `required: ["ring"]` it holds `rizzy-smtp-ingress`'s entry to `default-features = false` exactly as it already holds `opaque-ke`'s and `hpke`'s. **Never `rust-crypto`:** `FeatureRule.forbidden` is already a working absence-check — `hpke@0.14` forbids `mlkem`/`getrandom` and `opaque-ke@4` forbids `argon2`/`std` today — but `crypto_features`, the function that reads it, walks only `FEATURE_RULES_CRATE`'s (`rizzy-core`'s) own closure, and `mail-auth` is reached only from `rizzy-smtp-ingress`, outside it. Catching an enabled `rust-crypto` feature therefore needs `check-deps` extended to also walk `rizzy-smtp-ingress`'s closure; the approval PR makes that change (open question 4), not a reuse of an already-generalized check. |

## Consequences

### Positive

- Unblocks [ROADMAP §4.8](../ROADMAP.md#48-aliases--email-receiving-m6)'s M6 Must for SPF/DKIM/DMARC, already anticipated by name in [THREAT_MODEL §6.1](../THREAT_MODEL.md#6-email-ingress-m6) and by dependency fact in [ADR 0009](0009-crypto-dependency-policy.md#rng-rules)/[ADR 0016](0016-workspace-layout.md).
- Reuses `ring` and `mail-parser`, both already in the server's tree for other reasons, instead of a second crypto backend or a second MIME parser.
- Rules out the one concretely broken option (`rsa` via `rust-crypto`) before it ever enters the lockfile.

### Negative

- `rustls-platform-verifier` and its OS-specific backends enter the `smtp` role's build regardless of feature choice (item 7): new `unsafe`-bearing, platform-specific code in a role whose whole design point is a narrow, auditable surface ([ADR 0010](0010-server-shape.md) §2).
- Zero public audit for `mail-auth` or `hickory-resolver`; the M8 audit budget grows to cover them.
- `mail-auth`'s own `unsafe` count is unverified by this ADR (item 5).
- Mail-auth's own SPF/DKIM/DMARC DNS lookups are a new metadata leak to the resolver (and potentially the sender's own nameservers), parallel to the RBL/URIBL leak THREAT_MODEL §6.2 already names for rspamd but does not yet name for this crate (Context, "A second leak the crate itself introduces"; scheduled below).

### Risks

- A future `mail-auth` release could change its default crypto backend or fold `rust-crypto`-only code into a shared path; the exact pin and the proposed invariant are the guard. Signal: a Dependabot PR touching the feature set.
- `hickory-proto`'s SemVer range resolving to the RUSTSEC-2026-0119-affected 0.26.0 if `cargo deny check` is ever skipped. Mitigation: it already is not skippable in CI ([ADR 0016](0016-workspace-layout.md) §5).

## Alternatives considered

- **`mail-auth` with `aws-lc-rs` (its default).** Rejected: a second large C/assembly crypto library beside `ring`, [ADR 0030](0030-client-tls-rv.md)'s own reasoning against it for `rv`'s TLS.
- **`mail-auth` with `rust-crypto`.** Rejected: pulls `rsa` 0.9.8, RUSTSEC-2023-0071, unpatched, flagged by upstream as unsafe "over the network" — exactly this role's threat.
- **Hand-rolled DKIM/SPF/DMARC parsing against raw DNS TXT records.** Rejected: [CRYPTO.md §1](../CRYPTO.md#1-goals-non-goals-and-rules) Rule 1 forbids home-made handling of standardised, signature-bearing protocols; SPF/DMARC grammar parsing on untrusted, attacker-reachable input is exactly the hostile-input class [ADR 0010](0010-server-shape.md)'s Context singles `smtp` out for ("Two parts face a different kind of hostile input: `smtp` (M6) accepts mail from anyone on port 25") and [THREAT_MODEL G-11](../THREAT_MODEL.md#13-security-goals) bounds the blast radius of once such a parser has a bug — not [ADR 0016](0016-workspace-layout.md) R3, which is a crate-dependency-graph rule (no route to storage, sqlx, a domain crate or the bus) and says nothing about parsing untrusted input.
- **Leaving verification to rspamd alone.** Rejected for this ADR's purpose: rspamd's checks feed a spam *score*; [ROADMAP §4.8](../ROADMAP.md#48-aliases--email-receiving-m6) and [THREAT_MODEL §6.1](../THREAT_MODEL.md#6-email-ingress-m6) step 4 ask our own role to produce the authentication results shown in the UI. Whether rspamd's own checks are also kept, redundantly, is ADR 0069's call (this batch, Proposed).
- **`dns-doh` instead of `dns-hickory`.** Rejected for the native `smtp` role: it exists for WASM/edge targets `rizzy-smtp-ingress` never is; `dns-hickory` is the fact sheet's own assumption ([ADR 0016](0016-workspace-layout.md) Context).

## Open questions for the owner

1. **Approve `mail-auth` `=0.13.3`, `default-features = false, features = ["ring"]`, verification-only, in `rizzy-smtp-ingress`.** *Recommendation:* approve. No alternative backend avoids either a second C crypto library or the unpatched `rsa` timing side channel.
2. **Accept `rustls-platform-verifier`'s OS-native cert code entering the `smtp` role**, unavoidable with `dns-hickory` (item 7). *Recommendation:* accept. Unlike `rv`'s TLS trust decision ([ADR 0030](0030-client-tls-rv.md)), `smtp` is already an isolated, no-DB-credential, compromise-tolerant boundary (INV-44, G-11); the marginal audit cost is smaller there.
3. **Configure the resolver to attempt DNSSEC validation at runtime?** Not a feature-level choice: mail-auth's `ring` feature already compiles `hickory-resolver/dnssec-ring` in unconditionally (item 7); the only open choice is whether `smtp` constructs its `MessageAuthenticator` with trust anchors set so it actually validates, or with plain, unvalidated lookups. The threat this choice actually bears on is not a *compromised* `smtp` — [THREAT_MODEL §6.3](../THREAT_MODEL.md#63-what-this-means-stated-plainly)'s framing, unaffected either way — but [THREAT_MODEL A4](../THREAT_MODEL.md#a4-network-attacker-mitm), an *honest* `smtp` whose DNS a network or DNS-spoofing attacker forges to manufacture a false authenticated-looking SPF/DKIM/DMARC pass on a phishing mail; A4's own capability list already names DNS as one of the paths such an attacker can modify. *Recommendation:* unvalidated, for M6, accepting that exposure to A4 because the result is UI-informational only and never gates access, decryption or storage ([THREAT_MODEL §6.3](../THREAT_MODEL.md#63-what-this-means-stated-plainly)) — a spoofed pass only makes a phishing mail's badge look authenticated, the same class of trust a user already extends to an unauthenticated "From:" header. DNSSEC also adds resolver complexity for self-hosters whose own domains may not sign, and even the compiled-in path is pinned past RUSTSEC-2026-0118/-0120 regardless (item 4). Revisit if spoofed-pass abuse becomes a real signal.
4. **Who re-runs the mechanical checks** (`cargo deny check` confirming `hickory-proto`/`hickory-net` ≥0.26.1, `cargo xtask check-deps` extended to walk `rizzy-smtp-ingress`'s closure for the `rust-crypto` forbidden-feature check, the exact `unsafe` count) **before the dependency lands.** *Recommendation:* the ADR 0069 implementation PR (this batch, Proposed) that creates `rizzy-smtp-ingress`, mirroring [ADR 0041](0041-p256-crate-approval.md) open question 2.
5. **The proposed invariant's number.** *Recommendation:* the owner assigns it at acceptance, reconciled against any invariant numbers this same ADR batch already claims, to avoid a collision.

## On acceptance

The accepting change adds a dated entry to ADR 0009's `## Amendments`, in the shape of its 2026-09-26 and 2026-10-09 entries; a row to CRYPTO.md §3; and a bullet to THREAT_MODEL §6.2, parallel to its existing RBL/URIBL bullet:

> **2026-MM-DD: `mail-auth` for SPF/DKIM/DMARC verification ([ADR 0070](0070-mail-auth-crate-approval.md)).** Adds to the crate table: `mail-auth` (Stalwart Labs; SPF/DKIM1/DMARC verification, `rizzy-smtp-ingress` only; `=0.13.3`); `hickory-resolver` (its DNS resolver; lockfile-pinned, ≥0.26.3); `ring` (second edge — already approved only in `rizzy-cli` for TLS, [ADR 0030](0030-client-tls-rv.md); here also in `rizzy-smtp-ingress`). Required feature set: `mail-auth` `default-features = false, features = ["ring"]`; never `aws-lc-rs`, `rust-crypto`, `generate`, `arc`, `report`, `rkyv`, `test`. Checklist: this ADR's "The ADR 0009 checklist, answered". `Cargo.lock` must resolve `hickory-proto` and `hickory-net` to ≥0.26.1 (RUSTSEC-2026-0119, -0120).

CRYPTO.md §3 gains a row: "SPF/DKIM1/DMARC verification (`smtp` role), RFC 6376 / RFC 7208 / RFC 9989–9991 | `mail-auth` (`ring`) | =0.13.3 | No public audit found (U)".

THREAT_MODEL §6.2 gains a bullet, after the existing "Blocklist lookups (RBL/URIBL)" one: "**Mail-auth's own SPF/DKIM/DMARC lookups**, which `smtp` makes directly rather than through rspamd, send the configured resolver — and, where that resolver fetches records live, potentially the sending domain's own authoritative nameservers — which domains this instance is receiving mail from, and when. Unlike the blocklist lookups above these run for every accepted message, not only ones rspamd escalates."
