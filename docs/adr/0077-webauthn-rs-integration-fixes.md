# ADR 0077: webauthn-rs integration: deny wrappers, ceremony-state storage, RNG rule and stored credential shape

- Status: Partially superseded by [ADR 0082](0082-security-keys-user-presence-only.md) (§2 in part, §7, §9 entries 4, 5, 6, 9 and 13, §10 in part, owner answers at acceptance in part)
- Date: 2026-10-22 (accepted 2026-10-23)
- Deciders: project owner
- Milestone: M3 (`rizzy-domain-auth`, `rizzy-server`, `deny.toml`, `deploy/Containerfile`, CI images)
- Supersedes: [ADR 0059](0059-webauthn-rs-crate-approval.md) (Decision "Recommendation" in part, checklist item 7 in part, owner answers 1 and 6), [ADR 0009](0009-crypto-dependency-policy.md) ("RNG rules" in part, owner decision 1 in part, Amendments 2026-10-22 entry in part) and [ADR 0058](0058-webauthn-2fa-second-factor.md) (point 1 in part, points 2, 4 and 8, owner answer 3, "Owner answers at acceptance" closing paragraph in part), on acceptance. §9 lists the exact parts and their replacement text.

## Context

[ROADMAP §4.3](../ROADMAP.md#43-cryptography--authentication-m0m1-audited-in-m8) lists "2FA: TOTP, WebAuthn/FIDO2 security keys" as a Must, WebAuthn in M3. [ADR 0058](0058-webauthn-2fa-second-factor.md) (the feature) and [ADR 0059](0059-webauthn-rs-crate-approval.md) (the crate, `webauthn-rs` `=0.5.5`) were both accepted on 2026-10-22, and [CRYPTO.md §11.17](../CRYPTO.md#1117-webauthn-2fa-m3), INV-83, INV-84 and INV-85 ([THREAT_MODEL.md §8](../THREAT_MODEL.md#8-security-invariants)) were written from them. An implementation attempt the same day (`wip/m3-webauthn`) stopped before writing code: probes against the `webauthn-rs`, `webauthn-rs-core` and `webauthn-rs-proto` 0.5.5 sources and a scratch crate with the exact pin and this repository's `deny.toml` showed the accepted text cannot be implemented as written. This ADR re-read each finding against the crate sources in the local cargo registry (V where marked). The ADR gate ([CLAUDE.md](../../CLAUDE.md)) means none of them may be worked around in code; each needs an Accepted decision first.

**B1. The prescribed `deny.toml` wrapper lines fail.** [ADR 0009](0009-crypto-dependency-policy.md) owner decision 1 and ADR 0059 checklist item 7 prescribe `openssl` with `wrappers = ["webauthn-rs-core"]` and `openssl-sys` with `wrappers = ["openssl", "webauthn-rs-core"]`. `webauthn-attestation-ca` 0.5.5 is a third direct parent of both: its manifest declares `openssl ^0.10.75` and `openssl-sys ^0.9.111` (V, crate manifest), and `webauthn-rs-core` depends on it `=0.5.5`, non-optional (V, crate manifest). With the two prescribed lists `cargo deny check` fails; with `webauthn-attestation-ca` added to both, every check passes (V, scratch crate `probe` with the exact pin and the repository's `deny.toml`, as reported by the implementation attempt; the lockfile's dependents of `openssl`/`openssl-sys` re-read for this ADR). Owner decision 1 itself says "keeping only the direct parents M3's lockfile actually shows"; the lockfile shows three, not two.

**B2. Ceremony state cannot be stored in the database.** In the facade, `SecurityKeyRegistration` and `SecurityKeyAuthentication` derive `Serialize`/`Deserialize` only under the feature `danger-allow-state-serialisation`, and their fields are `pub(crate)` (V, `webauthn-rs` 0.5.5 `src/interface.rs`); that feature gates nothing but those derives on the in-progress state types (V, every use of the feature name in the facade's `src/`). ADR 0059 forbids every `danger-*` feature and rejects calling `webauthn-rs-core` directly ("Alternatives considered"). [ADR 0010 §5](0010-server-shape.md#5-short-lived-auth-state-lives-in-the-database) requires every piece of short-lived auth state to live in `auth_` tables, never in process memory, so that a challenge response can land on any `api` replica (profile C) and survive a restart. ADR 0058 points 2 and 3 want DB challenge and second-factor-pending rows. The crate's own documentation names storing state "to a database" as a *safe* use; the danger it guards against is placing state in a cookie or other client-side store, where a client can replay an old state with an old signature (V, `webauthn-rs` 0.5.5 `src/lib.rs` crate docs). Three options exist: (a) enable `danger-allow-state-serialisation`; (b) approve a direct `webauthn-rs-core` dependency, whose `RegistrationState`/`AuthenticationState` are always serializable (V, `webauthn-rs-core` 0.5.5 `src/interface.rs`); (c) keep the state in process memory, which partially supersedes ADR 0010 §5 and makes a multi-replica login fail closed whenever the two requests reach different replicas.

What the state holds matters for how it is stored (V, both crates' `src/interface.rs`). Registration: the UV policy, the excluded credential ids, the 32-byte challenge (`CHALLENGE_SIZE_BYTES = 32`, V, `src/constants.rs`), the requested algorithms, request flags and extensions. Authentication: the full `Credential` record of every allowed credential (credential id, COSE public key, counter, UV and backup flags, any parsed attestation), the UV policy, the challenge, `appid` and one flag. None of it is a secret, and none of it lets anyone finish a ceremony without the authenticator's private key; its *integrity* matters, because a state whose `credentials` list was swapped would accept an assertion from the swapped-in key.

**B3. A deterministic RNG in non-test code.** ADR 0059 owner answer 6 is conditional: no ADR 0009 change is needed "provided the implementation PR confirms that `rand_chacha` is only ever an OS-seeded CSPRNG outside tests". It is not: `webauthn-rs-core` 0.5.5 `src/fake.rs` (`pub mod fake`, re-exported as `webauthn_rs::fake`) builds `ChaCha8Rng::from_seed(seed)` with the seed = HMAC-SHA-256 over the username under an RP-held key, in non-test code (V, crate source). It generates stable fake credential ids for unknown usernames, against enumeration in username-first flows. Our flow never needs it: no credential id is served before KE3 verifies (ADR 0058 point 3, [CRYPTO.md §5.9](../CRYPTO.md#59-account-enumeration)). Everywhere else the crate draws challenges from `rand::rng()` (V, `src/core.rs`), `rand` 0.9's thread-local CSPRNG, which is `rand_chacha`'s ChaCha12 core seeded and reseeded from the OS (V, `rand` 0.9.5 manifest: `thread_rng` → `std_rng` → `dep:rand_chacha`; reseeding behaviour L, rand documentation). Under owner answer 6, ADR 0009's "fails CI" sentence binds only the R1 no-I/O crates, so it is not the closure check that fails; the rule actually offended is ADR 0009 "RNG rules", fifth bullet: "Deterministic RNGs are dev-dependencies only." A third-party crate's normal dependency cannot meet it.

**N1. The stored columns cannot rebuild a credential.** ADR 0058 point 1 stores `credential_id`, `alg`, the COSE-encoded public key and `sign_count`. Building a `SecurityKey` back from parts needs `From<Credential> for SecurityKey`, which exists only under `danger-credential-internals` (V, facade `src/interface.rs`). The facade's `SecurityKey` derives `Serialize`/`Deserialize` unconditionally and is the value the crate documents for persistence (V); its only field is the `Credential`, and its accessors are `cred_id()`, `cred_algorithm()`, `attestation()` and `update_credential()` (V).

**N2. UV is requested, and sometimes enforced.** Without `danger-user-presence-only-security-keys`, `start_securitykey_registration` requests `userVerification = "preferred"` and `credProtect` = `userVerificationRequired` with `enforceCredentialProtectionPolicy = false`; `start_securitykey_authentication` requests `"preferred"`, and the core refuses an assertion without UV from a credential whose `user_verified` flag was set at enrolment (V, facade `src/lib.rs` and core `src/core.rs`, the `Preferred if cred.user_verified && !data.authenticator_data.user_verified` arm). A key with a PIN set will ask for it at enrolment and at every login. ADR 0058 point 4 and CRYPTO.md §11.17 say UP is required and UV is not.

**N3. `openssl-sys` needs a system OpenSSL.** The approved feature set does not enable `openssl`'s `vendored` feature (`vendored = ["ffi/vendored"]` → `openssl-src`, V, `openssl` 0.10.81 and `openssl-sys` 0.9.117 manifests), so the build needs OpenSSL headers and libraries through pkg-config or `OPENSSL_DIR`; `OPENSSL_STATIC` selects static linking (V, `openssl-sys` `build/main.rs`). The builder image (`deploy/Containerfile`, `rust:1.94.1-alpine`, `apk add --no-cache gcc musl-dev`) installs no OpenSSL today and produces a static musl binary for a `distroless/static` runtime ([ADR 0010 §4](0010-server-shape.md#4-one-image-three-deployment-profiles)). The CI `test` job runs `cargo test --workspace` on ubuntu, macOS and Windows runners (V, `.github/workflows/ci.yml`). ADR 0009 owner decision 1 deferred this: "the cost to the server image (OpenSSL built through openssl-sys's `vendored` feature, or linked dynamically) is confirmed in M3".

Two further mismatches this ADR found while re-reading the crate:

**N4. A non-`"none"` attestation statement is verified and kept.** With no CA list the facade requests conveyance `"none"` (V, `start_securitykey_registration`). If an authenticator returns `packed`, `fido-u2f`, `tpm`, `android-key`, `android-safetynet` or `apple` anyway, `register_credential` still runs that format's verification procedure (signature over `authData ‖ clientDataHash`, the format's certificate rules) and refuses a statement that fails, and refuses an unknown format with `AttestationNotSupported`; only the trust-anchor step is skipped without a CA list (V, core `src/core.rs`, the `match attest_format` block and the `if let Some(ca_list)` block). The parsed result (`ParsedAttestationData::Basic`/`AttCa`/`AnonCa` with its X.509 chain, AAGUID metadata) becomes `Credential.attestation` and so part of the serialized `SecurityKey` (V). ADR 0058 point 2 says the enrolment path "does not verify the returned attestation statement, whatever format actually arrives", owner answer 3 "accepted on receipt, without verifying it", its closing paragraph "nothing is verified or stored from it", and CRYPTO.md §14 "the stored credential row holds none of it". How often a browser passes a real statement through when `"none"` is requested is U (WebAuthn Level 3 lets the client replace it, L).

**N5. The offered algorithms are fixed: ES256 and RS256.** `WebauthnBuilder` sets `algorithms: COSEAlgorithm::secure_algs()` and has no setter for it; `secure_algs()` is `[ES256, RS256]`, with EdDSA commented out under "Testing required" (V, facade `src/lib.rs`, proto `src/cose.rs`). A credential whose algorithm is outside the requested set is refused (`CredentialAlteredAlgFromRequest`, V). ADR 0058 point 8 and CRYPTO.md §11.17 offer ES256 and EdDSA, "nothing else". `SecurityKey::cred_algorithm()` is public (V), so the enrolment path can see which algorithm a key chose.

Other facts confirmed by the implementation attempt, needing no new decision (V unless marked): no seam exists for an external ES256 verifier (signature verification is OpenSSL inside `webauthn-rs-core`), so ADR 0058 point 7's no-seam branch applies and `rizzy-core` gains no `verify_es256` entry point; the challenge RNG is `rand::rng()`, OS-seeded and not injectable, the third-party case [ADR 0016](0016-workspace-layout.md) R2 and ADR 0009 "RNG rules" fourth bullet already allow (like `sqlx-postgres`), while `rizzy-domain-auth`'s own code still takes an injected RNG; `rand` resolves to 0.9.5, patched for RUSTSEC-2026-0097 (implementation attempt; L for the advisory text); the core's counter check matches INV-83 (it runs only when either counter is non-zero and refuses `received ≤ stored`, `CredentialPossibleCompromise`); `"none"` attestation registers without any CA list; the scratch lockfile contains no `rsa` crate. `account_id` is 16 random bytes ([CRYPTO.md](../CRYPTO.md) §2 ids), so `user.id` = `account_id` fits the facade's `Uuid` parameter as raw bytes (`Uuid::from_bytes`; no version bits are set or checked, L for the `uuid` crate's behaviour).

Adversaries in play: A1 (passive DB or backup theft) and a live DB reader or writer (the [ADR 0010 §5](0010-server-shape.md#5-short-lived-auth-state-lives-in-the-database) reasoning behind `SERVER_LOGIN_STATE`); the remote attacker who already holds the password and Secret Key, whom the second factor exists to stop ([THREAT_MODEL.md §4](../THREAT_MODEL.md#4-adversaries)).

## Decision

### Owner answers at acceptance (2026-10-23)

The owner accepted this ADR as drafted. The recommendations of the "Open questions for the owner" stand.

### 1. `deny.toml`: three named parents, nothing wider (B1)

The `openssl` and `openssl-sys` bans stay, each with a `wrappers` list of exactly the direct parents the lockfile shows:

```toml
{ crate = "openssl", wrappers = ["webauthn-attestation-ca", "webauthn-rs-core"], reason = "ADR 0009 owner decision 1, ADR 0059, ADR 0077 §1" },
{ crate = "openssl-sys", wrappers = ["openssl", "webauthn-attestation-ca", "webauthn-rs-core"], reason = "ADR 0009 owner decision 1, ADR 0059, ADR 0077 §1" },
```

No wildcard, no `skip`, no `allow`, no lifting of the ban. A fourth parent (for example a new `webauthn-rs` release that splits a crate out) fails `cargo deny check` and needs a new ADR, not a silent edit. `webauthn-attestation-ca` is a Kanidm crate in the same workspace, version-locked `=0.5.5` to `webauthn-rs-core`, MPL-2.0 like the rest of the family (V, crate manifests). The lines land with the implementation PR (ADR 0059 owner answer 3), which is the one change allowed to edit `deny.toml` for this. Reachability is unchanged: INV-85's `cargo xtask check-deps` rule still confines `openssl`/`openssl-sys` to `rizzy-server` and `rizzy-domain-auth`; `webauthn-attestation-ca` is reachable only through `webauthn-rs-core`.

### 2. Ceremony state: `danger-allow-state-serialisation`, stored unsealed in `auth_` rows, single use, 60 s (B2, option a)

`webauthn-rs` is declared with `features = ["attestation", "danger-allow-state-serialisation"]`. No other `danger-*` feature is enabled: `danger-credential-internals`, `danger-user-presence-only-security-keys` and every future one stay off.

**Why (a), not (b) or (c).** (a) changes nothing but two serde derives on types we already hold; the state is the same struct either way (the facade's `SecurityKeyRegistration`/`SecurityKeyAuthentication` wrap the core's `RegistrationState`/`AuthenticationState`). (b) gives exactly the same serializable state but also hands our code the core API, where we would rebuild the facade's security-key policy (`credProtect`, UV policy, hints, `allow_backup_eligible_upgrade = false`, the algorithm list) ourselves, the hand-rolling ADR 0059 rejected. (c) breaks ADR 0010 §5's replica and restart reasoning for a second factor that must fail closed, never fail randomly. The feature's name warns against client-side storage; the rules below make client-side storage impossible.

**Where.** The enrolment state lives in the enrolment challenge row of ADR 0058 point 2, keyed by an enrolment id and `account_id`. The login state lives in the login challenge row that `webauthn_login_challenge(pending_id)` writes under ADR 0058 point 3, keyed by `pending_id` and `account_id`, at most one live per pending row (a new challenge replaces it). The second-factor-pending row itself keeps the shape point 3 gives it (`pending_id`, `account_id`). Each state is `serde_json` of the facade type in a `state` column, next to `state_format` (u16, `1` = `webauthn-rs` 0.5.x) and `expires_at_ms`. A row whose `state_format` the binary does not know, or whose `state` exceeds 64 KiB, is refused on read (bounded input, fail closed); the ceremony restarts. A crate upgrade that changes the state shape costs at most one restarted ceremony, never a migration.

**Rules.** The state must:
1. **be read and deleted once,** in the same transaction as the verification, under [ADR 0011](0011-storage.md)'s per-account lock, whether verification succeeds or fails; a failed attempt needs a new challenge;
2. **expire 60 s after issue,** checked against `expires_at_ms` at read, not only by `worker`'s cleanup; the options sent to the client carry the same 60 s (`WebauthnBuilder::timeout`, V; the crate default is 300 s, V);
3. **never leave the server:** never part of an API response, a cookie, a URL, a log line or an error. The two state types appear only in a private module of `rizzy-domain-auth` and in no `pub` item of the crate; rizzy-server never names `webauthn-rs` (ADR 0059 confines it to `rizzy-domain-auth`);
4. **not be the authority for credentials or counters.** At `webauthn_login_finish`, under the same lock, the asserted credential id (`AuthenticationResult::cred_id()`) must belong to one of the account's current `webauthn_credential` rows, re-read in that transaction (a key deleted after the challenge was issued is refused), and INV-83 is decided against that row's `sign_count`, not against the counter copy inside the state. The crate's own counter refusal also stands; either refusal writes the possible-clone event ([ADR 0058](0058-webauthn-2fa-second-factor.md) owner answer 4).

**Stored, not sealed.** The state is stored unsealed; no `SERVER_*` purpose is added in the 0x0100–0x01FF range ([CRYPTO.md §5.11](../CRYPTO.md#511-server-side-encryption-not-zero-knowledge)). The security argument:
- *Confidentiality.* Sealing protects against a DB reader. The state gives a DB reader nothing: the challenge is sent to the client in the clear anyway, the credentials are public keys and ids already stored unsealed in `webauthn_credential` (ADR 0058 point 1, unchanged on this), and nothing in it lets its reader finish the ceremony, which needs the authenticator's private key. That is exactly the line ADR 0010 §5 draws: `SERVER_LOGIN_STATE` is sealed because it "carries key-confirmation material: a live DB reader who saw it in the clear could complete a login that is in flight"; device-auth challenges and ADR 0058's own challenge rows carry no such material and are unsealed. WebAuthn ceremony state is in the second group.
- *Integrity.* A DB *writer* could swap the `credentials` list, but the same writer can insert a `webauthn_credential` row directly, delete the account's enrolment, or write a session row; sealing the state would not raise the bar against that adversary while the credential table stays unsealed. Rule 4 additionally makes the state unable to admit a credential the table does not hold. A DB writer is not an adversary the server's 2FA claims to stop (ADR 0058 point 1: "integrity comes from the account-locked transaction and from verifying every assertion's signature").
- *Freshness* is what stops replay, and it comes from single use and the 60 s TTL (rules 1 and 2), the property the crate's warning is about.

Open question 2 asks the owner to confirm "stored, not sealed".

### 3. Deterministic RNGs: a reviewed allow-list for never-called third-party items (B3)

ADR 0009 "RNG rules", fifth bullet, second sentence, is replaced (§9 entry 3) by a rule with two halves: our own code constructs a seeded RNG only in tests; a third-party crate may contain one in non-test code only through an allow-list entry that a `clippy.toml` ban backs and that is re-reviewed on every version change. The allow-list is written in Accepted ADRs, starting with this one:

| Crate and version | Item paths (banned in our code) | Seeded from | Why we never reach it |
|---|---|---|---|
| `webauthn-rs-core` `=0.5.5` (re-exported as `webauthn_rs::fake`) | `webauthn_rs_core::fake::WebauthnFakeCredentialGenerator` (type) and its `new`, `new_hmac_key` and `generate` methods | `ChaCha8Rng::from_seed(HMAC-SHA-256(hmac_key, username))`, `src/fake.rs` (V) | It fakes credential ids for unknown usernames in username-first flows; ours serves no credential id before KE3 verifies (ADR 0058 point 3, CRYPTO.md §5.9), so it has no caller |

Enforcement: `crates/rizzy-domain-auth/clippy.toml` lists the type in `disallowed-types` and the three methods in `disallowed-methods`, as defining item paths (clippy 1.94.1 ignores a module path, "found a module", `crates/xtask/src/rules.rs`, V). `cargo xtask check-clippy` already fails when such an entry does not resolve, so a renamed item in a future crate version fails CI instead of silently unbanning. Only `rizzy-domain-auth` may depend on `webauthn-rs` (ADR 0059), so no other crate can name them. A version change of `webauthn-rs-core` re-reviews the entry (Dependabot never auto-merges crypto crates, ADR 0009 "Pinning and updates"); the review is the existing reviewer's checklist item, recorded in the PR.

Not a deterministic RNG for this rule: a CSPRNG seeded and reseeded only from the OS, such as `rand::rng()` over `rand_chacha`. `webauthn-rs-core`'s direct `rand`/`rand_chacha` dependencies are therefore admitted for that use. Unchanged: the "fails CI" sentence (owner answer 6 already fixed it to the R1 no-I/O crates, which `rizzy-domain-auth` is not), `rizzy-core`'s and `rizzy-sync`'s injected-RNG rules, ADR 0019's change to the third bullet, and "The RNG is never seeded from time".

### 4. Stored credential: the facade's `SecurityKey`, plus the counter of record (N1)

The `webauthn_credential` row (ADR 0058 point 1, first sentence, replaced in §9 entry 11) holds `credential_id` (bytes; unique per account), `alg` (`1` = ES256, the value of ADR 0039 §1's enum; no other value, §6), `security_key` (the facade `SecurityKey` as `serde_json`, unsealed: the COSE public key, counter, UV/backup-eligible/backup-state flags, registration policy, extensions and the parsed attestation, §5), `security_key_format` (u16, `1` = `webauthn-rs` 0.5.x JSON), `sign_count` (u32, the counter of record for INV-83), `label` and `created_ms`. The separate COSE-key column is dropped: the key lives in `security_key`, and a second copy could only drift.

**Counter consistency.** After a successful assertion, in one transaction: INV-83 is checked against `sign_count`, then `SecurityKey::update_credential(&result)` is called and both `security_key` and `sign_count = result.counter()` are written. They can only disagree through a DB writer, and then `sign_count` decides.

**Durability.** `security_key` is a long-lived persistent format whose shape the crate's serde derives own. So: the implementation PR commits fixture rows produced by 0.5.5 (enrolments made in tests, for example with a software authenticator built on the ES256 code ADR 0039 already put in `rizzy-core`, a dependency `rizzy-domain-auth` already has), and a test deserializes them and runs an assertion against each. Any `webauthn-rs` version change must keep that test green; a shape change the fixtures cannot absorb is a new `security_key_format` value with a migration, under a new ADR. Unsealed, as ADR 0058 point 1 says: none of it is a secret; INV-8 is untouched.

### 5. Attestation: crate-checked if present, never chained, kept as parsed (N4)

ADR 0058 point 2, its owner answer 3 and its closing sentence are replaced (§9 entries 12, 15 and 16): no CA list is configured, so conveyance is `"none"` and no statement is chained to a root; if a statement in another format arrives, the crate verifies it on its own terms and refuses one that fails or is unsupported, and a valid one is accepted whatever its format; what the crate parsed stays inside `security_key` (stripping it would need `danger-credential-internals`). This keeps 0058's reason (a legitimate key is not refused merely for attesting): a statement that fails its own signature check comes from a broken authenticator or a tampering client, which fail closed (CRYPTO.md §1 rule 6) refuses anyway. The stored data identify the key's make and model (with batch attestation, one batch, not one user, L), which the server saw at enrolment in any case; the CRYPTO.md §14 line is corrected on acceptance. Open question 6 offers the alternative of refusing every non-`"none"` statement so that nothing is stored.

### 6. Algorithms: the crate's set is offered, only ES256 is stored (N5)

`pubKeyCredParams` is the facade's fixed `[ES256, RS256]`; EdDSA is not offered, because the facade cannot offer it. At `webauthn_enrol_confirm`, a credential whose `cred_algorithm()` is not ES256 is refused before the row is written, with a typed error telling the user the key chose an unsupported algorithm. Reasons: an authenticator picks the first entry it supports, ES256 comes first, and FIDO2 security keys implement ES256 (L, CTAP 2.x), so RS256 is chosen essentially only by TPM-backed platform authenticators, which are outside "security keys"; the rule keeps the stored set a subset of what ADR 0058 accepted without a new `alg` value; and no RSA verification path is ever exercised at login. (RS256 verification would be OpenSSL, not the `rsa` crate, so RUSTSEC-2023-0071, which concerns `rsa`'s private-key timing, would not apply either way, L.) Open question 7 asks whether to accept RS256 as `alg` = `3` instead.

### 7. User verification: the facade's default, no `danger-*` (N2)

ADR 0058 point 4 is replaced (§9 entry 13): UP is required on every ceremony; enrolment requests UV `"preferred"` with `credProtect` = `userVerificationRequired` (not enforced); an assertion needs UV exactly when the credential performed UV at enrolment. `danger-user-presence-only-security-keys` stays off. This is at least as strong as 0058's floor (UP only): a PIN-protected key adds the PIN as a third proof, and a key with no PIN still works with UP alone. The cost is a PIN prompt for users who set one. Whether a browser asks a user to *create* a PIN at enrolment because of the `credProtect` request is U; the implementation PR checks it with at least one CTAP 2.1 key on Chromium, Firefox and Safari and records the result. Open question 4 holds the alternative.

### 8. OpenSSL in the build: static from the builder image's system package (N3)

ADR 0009 owner decision 1, third sub-bullet, is replaced (§9 entry 2). The `build` stage of `deploy/Containerfile` adds `openssl-dev`, `openssl-libs-static` and `pkgconf` to its `apk add` and sets `OPENSSL_STATIC=1`, so `openssl-sys` links `libssl.a`/`libcrypto.a` into the musl binary (package names and static archives L, Alpine packaging; to verify in the image job). The binary stays static, the runtime stays `distroless/static` with no shared OpenSSL, and TLS stays rustls-only (our code never names `openssl`; `webauthn-rs` uses it only for its WebAuthn cryptography: hashing, signature verification, X.509 parsing and HMAC). The image job checks the binary has no dynamic section, and the build prints the installed OpenSSL package version (`apk info -v`); that version is a component of the image's SBOM once [ADR 0073](0073-signed-images-sbom-provenance.md)'s SBOM lands (whether its generator sees a statically linked C library without help is U, so the entry may have to be added explicitly). An OpenSSL security release is a rebuild-and-release trigger, like Alpine and distroless base updates. The implementation PR measures and records the image-size cost owner decision 1 asked M3 to confirm.

Developers and CI: every workspace build now needs OpenSSL headers and pkg-config (Linux: the distribution's dev package; macOS: Homebrew `openssl@3` via `OPENSSL_DIR`; Windows: an OpenSSL installation via `OPENSSL_DIR` or vcpkg; which of these GitHub runners already ship is U). The implementation PR adds what the `lint`, `test` (all three OSes), `doc` and `image` jobs need; that is the one `.github/workflows/` change it is allowed, and it must be named in its task. CONTRIBUTING.md gains the prerequisite.

Why not `vendored`: enabling it needs one of our crates to declare `openssl` directly with `features = ["vendored"]`, which makes that crate a fourth, first-party direct parent in §1's wrapper lists; it adds `openssl-src` (the OpenSSL C sources) as a new build dependency needing its own ADR 0009 checklist, and `perl` and `make` in every builder. Its advantages (a Cargo.lock-pinned OpenSSL version, RustSec coverage of `openssl-src`, L, identical builds on every OS) are real; open question 5 asks the owner to choose.

## Consequences

### Positive

- ADR 0058 becomes implementable on the approved crate with one `danger-*` feature whose effect is two serde derives, no direct `webauthn-rs-core` dependency, and no change to ADR 0010 §5: every replica can finish any ceremony, and ceremonies survive a restart.
- The `deny.toml` exception stays an exact list of named parents, now matching the lockfile.
- The deterministic-RNG rule becomes precise and checkable: "never called" is enforced by clippy and the allow-list is reviewed, instead of a blanket sentence a third-party crate breaks by existing.
- The stored credential is the crate's own persistence type, so we never rebuild a credential from parts; the counter of record stays in our column, under our lock.
- UV is at least as strong as accepted: PIN-protected keys add their PIN.

### Negative

- `danger-allow-state-serialisation` is enabled, a feature the crate names as dangerous; its safety rests on §2's rules (server-side only, single use, 60 s, never in a response), which code structure and tests enforce, not the type system.
- `security_key` ties a long-lived persistent format to a third-party serde shape; every crate bump carries a fixture test, and a breaking shape change costs a migration ADR.
- Every developer machine and CI runner now needs OpenSSL headers and pkg-config; the builder image grows by three packages, and the release binary links a C crypto library whose version comes from Alpine, not from Cargo.lock, so `cargo deny` does not see its advisories.
- Users with a PIN on their key type it at every login. RS256-only authenticators cannot enrol. A stored attestation names a key's make and model to a DB reader.

### Risks

- Browsers prompting for PIN *creation* because of `credProtect` (U). Signal: the hardware check in the implementation PR or user reports; response: open question 4's alternative, by a new ADR.
- A `webauthn-rs` release that changes serde shapes, adds a parent of `openssl`, renames the `fake` items or changes `secure_algs()`. Signal: the fixture test, `cargo deny check` and `cargo xtask check-clippy` fail on the bump, by design.
- Alpine's OpenSSL lagging a security release, or the SBOM missing the static OpenSSL. Signal: OpenSSL advisories; ADR 0073's SBOM review in M8.
- Clients that pass a real attestation statement through and fail the crate's certificate-shape rules for an otherwise working key (U). Signal: enrolment error reports naming `fmt`.
- The 60 s TTL may be tight for a user who must plug in a key and type a PIN. Signal: expired-state refusals in logs; changing it is a CRYPTO.md §11.17 change.

## Alternatives considered

- **B2 (b), `webauthn-rs-core` as a direct dependency.** Same serializable state, a larger API surface, and the facade's security-key policy re-implemented by us; ADR 0059 rejected this. Lost.
- **B2 (c), process-memory state.** Partially supersedes ADR 0010 §5, fails logins across replicas in profile C, loses ceremonies on restart. Lost.
- **Sealing the state under a new `SERVER_*` purpose.** Protects nothing a DB reader could use, and adds nothing against a DB writer while `webauthn_credential` is unsealed (§2); it would add a purpose id, a context layout and a construction to audit target 10. Lost (open question 2 lets the owner choose it anyway).
- **Client-held state (signed or encrypted token).** The replay risk the crate warns about, and contrary to ADR 0010 §5. Not taken.
- **B1: lifting the `openssl` ban or a wildcard wrapper.** Wider than owner decision 1's "narrowly scoped". Lost to the three named parents.
- **B3: forbidding any deterministic RNG in the closure.** Rules out `webauthn-rs` entirely, and with it M3's WebAuthn 2FA, for an item we never call. Lost.
- **B3: patching or forking `webauthn-rs-core` without `fake.rs`.** A git or path dependency breaks the crates.io-only policy, and we would own a fork of a crypto crate. Lost.
- **N1: enabling `danger-credential-internals`** to rebuild `SecurityKey` from ADR 0058's columns. A second `danger-*` feature, and our code would assemble credential internals, the hand-rolling ADR 0059 avoided. Lost.
- **N1: storing the COSE key column next to `security_key`.** Two copies of one key can drift, and nothing reads the column. Lost.
- **N2: enabling `danger-user-presence-only-security-keys`.** Matches 0058 point 4 literally, but switches the policy to the crate's `Discouraged_DO_NOT_USE` and weakens PIN keys. Open question 4's alternative.
- **N3: the `vendored` feature.** See §8. Open question 5's alternative.
- **N4: refusing every non-`"none"` statement.** Nothing stored, but legitimate keys turned away, against 0058's own reason. Open question 6's alternative.
- **N5: accepting RS256 too** (`alg` = `3`). Open question 7's alternative.
- **Another crate.** `webauthn_rp` pulls `rsa` 0.9 with RUSTSEC-2023-0071 (ADR 0009 fact sheet); a hand-rolled ceremony breaks CRYPTO.md rules 1 and 2. Not reopened.

## Open questions for the owner

1. **Approve `danger-allow-state-serialisation` (B2 option a)?** *Recommendation:* yes, with §2's rules. Option (b) has the same state and more of our own code; (c) breaks ADR 0010 §5.
2. **Ceremony state: stored unsealed, or sealed under a new server purpose?** *Recommendation:* stored unsealed. It holds no key-confirmation material and no secret, and sealing does not stop the only adversary who could tamper with it while credential rows stay unsealed (§2); freshness comes from single use and the 60 s TTL. If the owner wants sealing anyway: a new `SERVER_WEBAUTHN_STATE` purpose with the next free id in 0x0100–0x01FF and ctx `row_id ‖ account_id ‖ u64 expires_at_ms`, written into CRYPTO.md §5.11 by the accepting change.
3. **Deterministic-RNG rule (B3): the reviewed allow-list with clippy bans, or an outright ban?** *Recommendation:* the allow-list; an outright ban drops WebAuthn 2FA from M3.
4. **UV (N2): the facade default (UV preferred, `credProtect` UV-required not enforced, UV enforced for keys that enrolled with it), or `danger-user-presence-only-security-keys` (UP only, as 0058 point 4 reads)?** *Recommendation:* the facade default. Stronger, no `danger-*` feature, and the cost is a PIN prompt only for keys that have a PIN. Revisit if the hardware check finds browsers forcing PIN creation.
5. **OpenSSL (N3): static link against the builder's system OpenSSL, or the `vendored` feature?** *Recommendation:* system OpenSSL, statically linked: no first-party parent in the wrapper lists and no new `openssl-src` approval, at the cost of OpenSSL updates arriving with image rebuilds and being tracked outside `cargo deny`. Sub-question: keep macOS and Windows in the CI `test` job for these crates by installing OpenSSL there? *Recommendation:* yes, so the checks list stays the same on every OS.
6. **Attestation (N4): keep the crate's check-if-present and store what it parsed, or refuse every non-`"none"` statement so that nothing is stored?** *Recommendation:* keep and store; it honours 0058's "do not refuse legitimate keys", and the data are non-secret metadata the server already saw.
7. **Algorithms (N5): store ES256 only, or also RS256 (`alg` = `3`)?** *Recommendation:* ES256 only; security keys implement it, and the stored set stays inside what ADR 0058 accepted.
