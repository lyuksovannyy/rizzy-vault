# ADR 0029: KeePass KDBX import: legacy primitives in `rizzy-import`

- Status: Proposed
- Date: 2026-09-30
- Deciders: project owner
- Milestone: M1

## Context

[ROADMAP §4.2](../ROADMAP.md#42-core-vault-m1) has the M1 **Must** row "Import: Bitwarden JSON, 1Password (1PUX), KeePass (KDBX/XML), generic CSV, Chrome/Firefox CSV, our plaintext JSON export", and §7 wants KeePass import "verified on real exports". [ADR 0002](0002-own-protocol.md) point 2 lists "KeePass KDBX and XML" and says where the cryptography goes: "Legacy primitives that an importer needs, for example KDBX's own KDF and cipher, live in `rizzy-import`, never in `rizzy-core`, and go through ADR 0009's approval procedure." That procedure has not run, so today `rizzy-import` reads KeePass XML only, refuses a KDBX file by its signature (`ImportError::KdbxNotSupported`) and drops every `Protected="True"` value with a warning. The XML route makes the user write every password to disk in plaintext first.

**What a KDBX file needs** (L throughout: the KeePass format documentation and the KeePassXC reader as recalled, not re-read for this ADR; the fixtures of point 7 are what prove each line):

- **Composite key:** SHA-256 over SHA-256(password) and, if used, the 32-byte key-file key.
- **KDBX 3.1:** AES-KDF (the composite key encrypted N times with AES-256-ECB under a seed from the header, then SHA-256); outer cipher AES-256-CBC with PKCS#7 padding (KeePassXC also offers Twofish-CBC); a 32-byte start-bytes check; a stream of SHA-256-hashed blocks; optional gzip; inner stream cipher Salsa20 over the `Protected` XML values. No MAC: the header, which carries the inner-stream key and the compression flag in the clear, is covered only by a SHA-256 inside the encrypted XML (`Meta/HeaderHash`).
- **KDBX 4.0 and 4.1:** KDF named in the header: AES-KDF, Argon2d or Argon2id (version 0x13); header SHA-256 and header HMAC-SHA-256; the body as HMAC-SHA-256 blocks with per-block keys from SHA-512, ended by an empty block; outer cipher AES-256-CBC or ChaCha20 (12-byte nonce); optional gzip; a binary inner header carrying the inner stream cipher (ChaCha20, or Salsa20), its key and the attachments; then the XML. 4.1 changes only the XML.

**Forces.** [ADR 0009](0009-crypto-dependency-policy.md): no home-made crypto, the approval checklist and exact pins for every crypto crate, constant-time decoding of secrets. [ADR 0016](0016-workspace-layout.md) R1: `rizzy-import` does no I/O, builds for wasm32, and its external closure is allow-listed by `cargo xtask check-deps` (its own list is empty today). [THREAT_MODEL A16](../THREAT_MODEL.md#a16-malicious-import-files-and-shared-content): the file is hostile, and here it also names the cost of a KDF. [THREAT_MODEL §5.2](../THREAT_MODEL.md#52-envelope-and-algorithm-downgrade): a legacy format must never become a decrypt path for our own data. [CRYPTO.md §12.2](../CRYPTO.md#122-memory-hygiene): plaintext in zeroizing buffers of final size. [CRYPTO.md §16](../CRYPTO.md#16-open-questions-for-the-owner): no test or fuzzing hook that weakens a check.

## Decision

1. **Scope: read KDBX 3.1, 4.0 and 4.1, in M1.** A new `Format::KeePassKdbx` and a `kdbx` module in `rizzy-import`.

   | Part | Read | Refused, each with its own `ImportError` kind |
   |---|---|---|
   | Version | 3.1, 4.0, 4.1 | KDB 1.x, KDBX 2.x pre-releases, any other major or minor |
   | KDF | AES-KDF; Argon2d and Argon2id, version 0x13 | Argon2 0x10; an Argon2 secret key or associated data in the header; any other KDF id |
   | Outer cipher | AES-256-CBC (PKCS#7), ChaCha20 | Twofish-CBC, any other id |
   | Inner stream | Salsa20, ChaCha20 | ARC4-variant, none, any other id |
   | Integrity, 4.x | header SHA-256, header HMAC and every block HMAC, all before any decryption; the stream must end with the empty block under a valid HMAC, with no byte after it | any check failing, a missing end block (truncation), trailing bytes: all `KdbxKeyOrIntegrity` |
   | Integrity, 3.1 | start bytes; every block's SHA-256 and the empty end block; `Meta/HeaderHash`, which is **required** and compared with the SHA-256 of the outer header | any check failing; a file without `Meta/HeaderHash` (`KdbxHeaderHashMissing`) |
   | Compression | none, gzip (one member; CRC-32 and ISIZE checked) | any other flag |
   | Credentials | password, key file, or both | Windows user account, challenge-response, plugin key providers |

   - **Every 3.1 import carries a dedicated warning** (`KdbxUnauthenticated`): the format has no MAC, so the file's integrity rests on hashes an attacker who knows nothing secret can recompute for the parts outside the encrypted XML. Requiring `Meta/HeaderHash` closes the one cheap attack (changing the clear-text inner-stream key so that every protected value decrypts to other bytes).
   - **Key file** (L for the forms and their order, fixtures decide): XML 2.0 (hex key; its `Hash` attribute, the first four bytes of the key's SHA-256, is checked with `subtle`, and a mismatch is `KdbxKeyFileCorrupt`, not the wrong-key error), XML 1.0 (Base64 key), exactly 32 raw bytes, exactly 64 hex digits, else SHA-256 of the file.
   - Attachments (3.1 `Meta/Binaries`, the 4.x inner header) are skipped with the XML importer's warning (attachments are M3). After decryption the existing `keepass` XML mapping runs unchanged, plus two decoders that need the KDBX context: `Protected` values (Base64, then XOR with the inner stream, consumed in document order over **every** protected value, including the ones in skipped entries and history) and KDBX 4's Base64 times.
2. **Crates.** Admitted for `rizzy-import` only, exact pins in `[workspace.dependencies]`, `default-features = false`: `aes = "=0.9.3"` with `["zeroize"]` (never `hazmat`); `cbc = "=0.2.1"` with `["zeroize"]` (not `block-padding`: `decrypt_blocks` is in place, and the PKCS#7 check is ten lines of ours); `salsa20 = "=0.11.0"` with `["zeroize"]`. `cpubits` stays lockfile-pinned. `rizzy-import` also takes direct normal dependencies on the pinned `argon2`, `sha2`, `hmac`, `subtle`, `base64ct`, and `chacha20` with `["cipher", "zeroize"]`. The workspace entry for `chacha20` carries **no** feature: `rizzy-import`'s entry adds `cipher` and `zeroize`, and the `[dev-dependencies]` entries that need the test RNG add `rng` themselves. No Twofish, no DEFLATE, XML or gzip crate. Stream ciphers are called through `try_apply_keystream` only (an error, never a panic, at the end of the keystream: `cipher` 0.5, V).
3. **Boundary (ADR 0002 point 2, THREAT_MODEL §5.2).**
   - **Decrypt-only and import-only.** `rizzy-import` never writes KDBX and exposes no cipher, KDF or key type. Nothing of ours (envelope, export, cache, backup) may be encrypted or decrypted with these primitives.
   - **Public surface of `kdbx`.** `probe` and the importer, plus five decoders that are public only so that `fuzz/` reaches them, as `item_value` and `padding_unframe` are reached today: the 3.1 hashed-block reader, the 4.x HMAC-block reader, the key-file decoder, the gzip reader (beside the already public `inflate`), and the decoder of the decrypted payload (gzip, inner header, XML mapping with protected values and times), which takes the inner keystream as a caller-supplied byte source instead of a cipher. None of them performs a cipher or KDF operation or derives a key: the HMAC-block reader takes the 64-byte HMAC key and only verifies (SHA-512, HMAC-SHA-256), and the key-file decoder returns only the 32 bytes it decoded or hashed from its own input, in a zeroizing type. **No `cfg(fuzzing)`, feature or test switch changes what any check does** (CRYPTO.md §15 item 1, §16).
   - **Enforced by `cargo xtask check-deps`,** with rules that do not exist yet (today's `FEATURE_RULES` is keyed on `rizzy-core`'s closure and its own entries, so it cannot carry them):
     - *dependency rule* (like `RUSTIX`): only `rizzy-import` declares `aes`, `cbc` or `salsa20`, in any dependency kind, and only `rizzy-import` declares `chacha20` as a normal dependency (every other member: `[dev-dependencies]` only). The three new crates are in the normal and build closure of `rizzy-import` and its dependents only, never in that of `rizzy-core`, `rizzy-sync`, `rizzy-proto` or a server-side crate (`rizzy-server` reaches them only through its dev-dependency on `rizzy-client`, ADR 0016 owner decision 4). `rizzy-import`'s and `rizzy-client`'s R1 allow-lists gain `aes@0.9`, `cbc@0.2`, `salsa20@0.11` and `cpubits@0.1`;
     - *feature rule, keyed on `rizzy-import`:* its own `[dependencies]` entries turn on `zeroize` for `aes`, `cbc` and `salsa20` and `cipher` and `zeroize` for `chacha20`; `aes`'s `hazmat` is off on the workspace-unified graph; every declaration has default features off; no normal or build dependency entry turns on `chacha20`'s `rng`;
     - *source rule* (the token scan that finds `unsafe` today): the identifier `Argon2d`, any path into `aes`, `cbc` or `salsa20`, and any item of `chacha20` other than `ChaCha20Rng` appear in first-party Rust only under `crates/rizzy-import/src/kdbx/`. `rizzy-core` can name `argon2::Algorithm::Argon2d` today, and a clippy `disallowed-types` entry cannot name an enum variant or a crate the linted member does not depend on (U for clippy 1.94.1), hence a scan.
   - **No I/O, wasm-clean.** The file, the password and the key file arrive as bytes; nothing is read, and no randomness is used beyond the injected RNG the XML mapping already takes for element ids.
4. **Two steps, and the caller accepts the cost before paying it.** `kdbx::probe(input)` parses only the outer header and returns version, KDF, cipher and a `KdbxCost` (AES-KDF rounds, or Argon2 memory, iterations and parallelism), with no secret involved. `import` takes the credentials, a `KdbxLimits` (the caller may lower the caps of point 5, never raise them), an **accepted `KdbxCost`** and a `keep_going` callback. `KdbxCost` has no `Default`; a header whose KDF or any cost figure exceeds the accepted value is refused (`KdbxCostNotAccepted`) before any KDF work, so the caps can never be used blindly. AES-KDF consults `keep_going` every 65,536 rounds. **Argon2 cannot be cancelled** (one blocking call in `argon2` 0.6.0): the caller runs `import` where it can be killed, a Web Worker in the browser and a worker thread or process natively, and the product cap of point 5 bounds the wait. The password is the UTF-8 the user typed, **not** NFC-normalised (KeePass does not normalise: U, a fixture with a non-ASCII password decides).
5. **Limits against hostile files** (in `limits.rs`, each checked before the work it bounds):
   - input ≤ 128 MiB; outer header ≤ 1 MiB and ≤ 64 fields; KDF dictionary ≤ 32 entries; unknown header fields skipped, duplicate or missing required fields and wrong fixed lengths (seeds, IV, nonce, keys) are `Malformed`;
   - key file ≤ 16 MiB (`TooLarge` above); it is tried as XML only when ≤ 64 KiB, under the existing XML caps, and no DTD;
   - Argon2: memory ≤ 1 GiB, iterations ≤ 100, parallelism ≤ 64 (lanes run sequentially: no threads, the same output), memory ≥ 8 × parallelism KiB, **and memory × iterations ≤ 16 GiB-passes** (about 20 s at the 0.8 GiB/s of the M0 measurement; L). On wasm32: memory ≤ 256 MiB and the product ≤ 4 GiB-passes. AES-KDF: ≤ 100,000,000 rounds. Above a cap is `TooLarge`, never clamped. There is **no floor**: a weak KDF in someone else's file is not a downgrade of ours;
   - **every large allocation is fallible:** the Argon2 block buffer, the ciphertext copy and the gzip output are reserved with `try_reserve_exact`, and a failure is `ImportError::OutOfMemory`, never `handle_alloc_error` (an abort, or a trap of the wasm instance that holds the unlocked vault). `inflate` gets the same treatment for this path;
   - block streams: each block's length is checked against the bytes left in the input before anything is copied; the ciphertext is copied once into one zeroizing buffer no larger than the input and decrypted in place. gzip: the output buffer is reserved once at the trailer's ISIZE, which must be ≤ 128 MiB (`MAX_XML_LEN`), and `inflate` stops at that size; header flags (`FEXTRA`, `FNAME`, `FCOMMENT`, `FHCRC`) are parsed with bounds;
   - inner header ≤ 100,000 fields, attachment bytes skipped without a copy; then the existing XML caps (`MAX_DEPTH`, `MAX_NODES`, `MAX_ENTRIES`, no DTD);
   - peak memory is the input, two buffers of at most 128 MiB, and the Argon2 block buffer, which is wiped and dropped before the payload buffers are reserved.
6. **Secrets and errors.** The composite, transformed, cipher, HMAC and inner-stream keys, the Argon2 block buffer (caller-owned by `hash_password_into_with_memory`, as ADR 0009 requires) and every plaintext buffer are `Zeroizing`; cipher states wipe through the crates' `zeroize` features. **Decoding of secrets is constant time** (ADR 0009 "Constant-time rules"): key-file Base64 and protected values go through `base64ct`, key-file hex through a branch-free decoder of ours, the key into a `Zeroizing<[u8; 32]>`. HMACs, the start bytes and hashes are compared with `subtle`. A wrong password, a wrong key file and a corrupt file give the same error kind (`KdbxKeyOrIntegrity`); in 3.1 that includes a PKCS#7 failure, which there happens on unauthenticated data, before the start bytes can be read (in 4.x the padding check runs after the HMACs). No error, warning or `Debug` output carries a byte of the file or of a key. Nothing derived from the KeePass credentials leaves the call.
7. **Tests.**
   - **Known answers for each primitive as `kdbx` calls it:** FIPS 197 Appendix C.3 (AES-256), NIST SP 800-38A F.2.6 (CBC-AES256 decrypt), Wycheproof AES-CBC-PKCS5 (padding), RFC 8439 §2.4.2 (ChaCha20), the eSTREAM Salsa20 256-bit set (L), RFC 9106 §5.1 (Argon2d), RFC 4231 (HMAC-SHA-256), RFC 1952 gzip members written by the test encoder.
   - **Fixtures,** committed under `crates/rizzy-import/tests/fixtures/kdbx/` with a README naming the application, its version, the date, the settings and the **throwaway** password and key file of each: written by KeePass 2.x and by KeePassXC, covering 3.1 (AES-KDF, AES, Salsa20), 4.x with AES-KDF, Argon2d and Argon2id, AES and ChaCha20 outer ciphers, gzip on and off, password only, each key-file form, both, a non-ASCII password, protected custom fields, history, the recycle bin and an attachment. Each has the XML export of the same database beside it; the test asserts that both imports give the same items. Refusals (Twofish, wrong password, a flipped byte in every region, truncation at a block boundary, trailing bytes, a 3.1 file without `Meta/HeaderHash`, an unaccepted cost, each cap, a failed reservation) have their own tests.
   - **Fuzz targets** in `fuzz/`, over the unchanged production code: `import_kdbx` (whole path, fixed password, `KdbxLimits` and accepted cost at a few KiB and rounds), `kdbx_header` (`probe`), `kdbx_blocks` (the harness computes each block's SHA-256, or its HMAC under a fixed key, over the fuzzer's bytes with `sha2` and `hmac`, so the readers' accepting paths are reached; raw input covers the refusing paths), `kdbx_payload` (the decrypted-payload decoder with a fixed byte pattern as keystream), `kdbx_keyfile`, `gzip`.
8. **Documents.** ADR 0009 changes in two ways, and neither is by implication. Its `chacha20` row is superseded by this ADR (below); nothing in ADR 0009 is edited for it but the status line, which the owner sets. The rows and "Required feature sets" lines for `aes`, `cbc` and `salsa20` are a dated `## Amendments` entry, which ADR 0009 provides for. It is its own owner-approved change ([ADR 0020](0020-partial-supersession.md) point 4) and is also the change that adds the three crates to the manifests, both lockfiles and the xtask rules, so that ADR 0009's "The PR that adds the dependency must update this ADR" holds too. The `kdbx` code follows it. In the `kdbx` change: CRYPTO.md §3 gains a separate "Import-only legacy primitives" table that says these are not part of the protocol; CRYPTO.md §12.1 ("`ChaCha20Rng`, a dev-dependency only") is reworded to the replacing row; `rizzy-import`'s crate documentation, `docs/README.md` and THREAT_MODEL A16 are updated to match; `KdbxNotSupported` goes away.

### What this ADR supersedes

- **[ADR 0009](0009-crypto-dependency-policy.md), "Allowed crate families for cryptography", the table row "`chacha20` (RustCrypto), feature `rng`, **dev-dependency only**".** Replacing row: first cell "`chacha20` (RustCrypto)"; use "Two uses. (a) Feature `rng`, in `[dev-dependencies]` only: `ChaCha20Rng`, the seeded test RNG for the transcript vectors (CRYPTO.md §15 item 1). It implements rand_core 0.10 and is the crate `chacha20poly1305` 0.11 already depends on. (b) Features `cipher` and `zeroize`, as a normal dependency of `rizzy-import` only and called only in its `kdbx` module: the ChaCha20 outer cipher and inner stream cipher of KeePass KDBX 4 files, decrypt-only and import-only (ADR 0029). No other crate declares it as a normal or build dependency"; pin "`=0.10.2`".
- **Status line the owner sets on ADR 0009 at acceptance:** `Partially superseded by [ADR 0019](0019-native-clients.md) ("RNG rules" in part); [ADR 0029](0029-kdbx-import.md) ("Allowed crate families for cryptography" in part)`. Every other part of ADR 0009 stays binding, "Deterministic RNGs are dev-dependencies only" included.

**Checklist record ([ADR 0009](0009-crypto-dependency-policy.md#approving-a-new-crypto-crate) items) for `aes` 0.9.3, `cbc` 0.2.1 and `salsa20` 0.11.0, and for the new uses of `chacha20` 0.10.2 (`cipher`, `zeroize`) and of `argon2` 0.6.0 (Argon2d):**

1. **Need.** No construction of ours. They implement KeePass's file format, read-only (point 1, ADR 0002 point 2). `chacha20` is the raw IETF stream cipher on a key from the file's KDF, with the file's nonce: KDBX 4's outer cipher and inner stream.
2. **Provenance.** RustCrypto, the organisation behind `sha2`, `hmac`, `argon2` and `chacha20` (V, manifests). These are the newest releases on crates.io (V, `cargo info`, 2026-09-30) and the `cipher` 0.5 generation already in `Cargo.lock`. Cadence, downloads, bus factor: U.
3. **Audit history.** None found for these versions (U). NCC Group's 2020 review of the RustCrypto AEADs covered older `aes` and `chacha20` code through `aes-gcm` and `chacha20poly1305` (L).
4. **Advisories.** None for `aes`, `cbc`, `salsa20`, `cipher`, `cpubits` or `argon2` in the advisory-db checkout (V). The predecessors `aes-soft` and `aesni` carry only "unmaintained, merged into `aes`" notices (RUSTSEC-2021-0060, -0059; V). **`chacha20`: RUSTSEC-2019-0029** (2019-10-22, CVE-2019-25005): releases before 0.2.3 let the 32-bit block counter wrap and repeat the keystream after 256 GiB; patched in 0.2.3, so 0.10.2 is unaffected (V). How quickly it was fixed: U. Our input cap of 128 MiB is far below the limit, and point 2's `try_apply_keystream` returns an error there.
5. **`unsafe`.** `cbc`, `salsa20`, `cpubits`: none (V). `aes` (60 lines): the AES-NI, VAES and ARMv8 backends and their construction and dispatch in `lib.rs`; `hazmat.rs` (feature off); **and, on every target including the software path wasm32 uses, the backend-union reads in `lib.rs`** (`Inner`, `InnerEnc` and `InnerDec` are unions everywhere; `unsafe { &self.inner.soft }` on each encrypt and decrypt call and in the encryptor-to-decryptor conversion). **Our `zeroize` feature switches on one more block:** each type's `Drop` calls `zeroize::zeroize_flat_type`. Only `backends/soft.rs` itself is under `#![deny(unsafe_code)]` (V, source). `chacha20` (73 lines): the SSE2, AVX2, AVX-512 and NEON backends and their dispatch in `lib.rs`, all behind x86, x86_64 or aarch64 `cfg`s, and `rng.rs` (feature `rng`, tests only). wasm32 takes the portable backend, which has none; the `zeroize` feature adds none (`self.state.zeroize()`) (V, source).
6. **Constant time.** `aes`: hardware instructions, or the bitsliced fixslice backend, which has no secret-indexed tables (L, upstream's claim; not tested by us). Salsa20 and ChaCha20 are add-rotate-xor. **Argon2d is data-dependent by design:** its memory addressing depends on the password, which RFC 9106 accepts for settings without side-channel observers; it runs once, locally, on a KeePass password and never on ours. The PKCS#7 check is not constant time and need not be: it runs on a local file whose result goes to nobody but the user, and its failure is indistinguishable from a wrong key (point 6).
7. **Builds and hygiene.** Licenses on the allow-list, `cargo deny check` and `cargo check-wasm` pass, four new packages (V, Context). The implementing change re-runs the full gate, the fuzz workspace's `cargo deny` included. Whether `chacha20` builds with no feature on (point 2's workspace entry): U, the same change shows it.
8. **Test vectors.** Point 7.

## Consequences

### Positive
- A KeePass user imports the database file itself; no plaintext XML on disk, and protected values and KDBX 4 times are no longer dropped.
- ADR 0002 point 2 and the ROADMAP row are met in full, with three small, exactly pinned RustCrypto crates. Only `aes` brings `unsafe` onto the wasm32 path: its union reads and its `zeroize` drop.

### Negative
- AES, CBC, Salsa20 and Argon2d enter the client bundle and the M8 audit scope, for one format.
- About 1,500 lines of new parsing over hostile input, six fuzz targets, five fuzz-only public decoders, three new xtask rules, and binary fixtures in the repository.
- AES-KDF on wasm32 uses the portable backend; a file with tens of millions of rounds takes a long time there (U, not measured), hence `probe` and `keep_going`. Argon2 has no such hook: a file at the cap blocks its worker for the whole product.
- **wasm32 memory high-water mark.** Linear memory never shrinks: after an import the instance keeps the peak of point 5 (up to 256 MiB of Argon2 blocks, or the input plus two payload buffers) until it is dropped. The buffers are wiped, but the pages stay; the client decides whether to import in an instance it then discards (ADR 0013's concern, not decided here).
- A KeePass database whose Argon2 cost is above the product cap, or a 3.1 file with no `Meta/HeaderHash`, is refused; the user re-saves it in KeePass or exports XML.

### Risks
- **KDBX 3.1 is unauthenticated.** A modified 3.1 file that still passes its hashes imports modified entries; point 1 warns on every such import and cannot fix it. A format fact above being wrong shows as a failing fixture.
- The legacy primitives are one `use` away from misuse. The three xtask rules of point 3 are the guard, and they are new code that must itself be tested (a violating fixture per rule); a request to use AES anywhere else is a new ADR. The fuzz-only public decoders widen `rizzy-import`'s API. They take no credentials and run no cipher, so misuse gains nothing, but they must stay that way in review.
- A future KDBX 5 or a new KeePassXC cipher is refused until an ADR admits it.

## Alternatives considered

- **M1 ships XML only; KDBX moves to M3** (a ROADMAP edit: the §4.2 row becomes "KeePass (XML)" and a Should row "KeePass KDBX import" is added for M3). No legacy crypto in M1 and nothing to audit yet, but every KeePass user exports plaintext to disk, and protected values stay dropped unless the export was made with protection off. Kept as the fallback of question 1.
- **KDBX 4 only.** Saves `salsa20` and the unauthenticated path; refuses the files of users who never changed KeePass's older defaults (L). Question 2.
- **No new crate: KDBX 4 with Argon2 and ChaCha20 only.** Refuses AES-256, the default outer cipher of KeePass and KeePassXC (L), so it reads almost no real file.
- **The `keepass` crate** (0.15.0, MIT, one maintainer; V, `cargo info`). Its manifest lists 34 dependencies, among them `getrandom`, `flate2`, `quick-xml`, `twofish`, `rust-argon2` and `chrono` (V): it breaks R1's allow-list, and its buffers are not ours to size or wipe.
- **CBC or AES-KDF's ECB loop over `aes` by hand, without `cbc`.** CBC is a mode, and ADR 0009 forbids writing one; the ECB loop is KeePass's KDF itself and has no crate, so it is written in `kdbx` over `aes`'s block API and tested by fixtures.
- **Integrity checks skipped under `cfg(fuzzing)`,** so the fuzzer gets past the HMACs. A compiled-in bypass in the shipping crate, which no fuzz run would then exercise; CRYPTO.md §16 already refuses such hooks. The harness computes valid hashes instead (point 7).
- **An ADR 0009 amendment for the `chacha20` use.** It widens a row that says "dev-dependency only", which ADR 0020 point 4 does not allow as an amendment; hence the supersession above.
- **Twofish-CBC** (`twofish` 0.8.0 exists, V). A fourth crate for a non-default KeePassXC option; the user re-saves with AES or ChaCha20.
- **A separate `rizzy-import-kdbx` crate.** A cleaner audit line and a simpler dependency rule, but a new crate needs an ADR 0016 change.

## Open questions for the owner

1. **KDBX in M1, or XML only in M1?** Recommendation: accept this ADR and keep KDBX in M1, as the last item of step 4, after the web vault's blockers. If M1 must shrink, take the first alternative instead: that is your ROADMAP edit, and this ADR then stays Proposed for M3.
2. **Read KDBX 3.1?** Recommendation: yes, with the warning and the required `Meta/HeaderHash` of point 1. `salsa20` is small and safe code, and old databases are the ones people migrate. **And a 3.1 file without `Meta/HeaderHash`: refuse, or import with a second warning?** Recommendation: refuse, the conservative reading. Whether KeePass 2.x and KeePassXC always write it is U; if a fixture lacks it, this comes back to you.
3. **Key files in M1?** Recommendation: yes. No new primitive, only SHA-256, `base64ct` and the XML reader.
4. **The caps of point 5** (1 GiB, 100 iterations, 16 GiB-passes, 256 MiB and 4 GiB-passes on wasm32, 10^8 rounds, 128 MiB, 16 MiB key file). Recommendation: as written; KeePass's and KeePassXC's real defaults are U and the fixtures will show them.
5. **ADR 0009.** Accepting this ADR supersedes its `chacha20` row and sets the status line written above. Recommendation: also approve the amendment of point 8 as the separate change that adds the three crates without code. If a dependency with no caller fails a gate command (U), the alternative is one change for both, which ADR 0009's sentence asks for and ADR 0020 point 4's "its own PR" does not: that conflict is then yours to settle.
6. **Who makes the fixtures?** They need KeePass 2.x and KeePassXC run by a person; an agent must not invent them. Recommendation: you create the point 7 matrix once with throwaway passwords; implementation starts from primitives and known answers and is not called done without them.
