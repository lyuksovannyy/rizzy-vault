# ADR 0045: Server-side notification of pending and completed account recovery

- Status: Proposed
- Date: 2026-10-11
- Deciders: project owner
- Milestone: M1

## Context

[ROADMAP §4.3](../ROADMAP.md#43-cryptography--authentication-m0m1-audited-in-m8) makes the Emergency Kit recovery flow a Must for M1. [ADR 0008](0008-account-recovery.md) decision 5 (Partially superseded by [ADR 0022](0022-server-mode-only.md) only at point 7, which parks On-device mode; decision 5 itself stands) requires: "every enrolled device and the account email are notified" when a recovery opens, a server-enforced wait (default 72 h, admin-configurable 0–30 days), and "any enrolled device can cancel the pending recovery." [CRYPTO.md §11.9](../CRYPTO.md#119-recovery-with-the-emergency-kit) (normative, V) repeats this at steps 2 and 6 but names no mechanism; [ADR 0010](0010-server-shape.md)'s `notify` role, the only push channel, is M3. [docs/HANDOFF.md](../HANDOFF.md) gap 10 records the result: no M1 channel exists. [docs/ROADMAP.md](../ROADMAP.md) §4.3's recovery row is otherwise implemented.

The server already tracks the gap, just not visibly. `crates/rizzy-domain-auth/src/recovery.rs` (V) stores a `pending_recovery` row (`account_id, recovery_epoch, opened_at_ms, available_at_ms`) across `recovery_start`/`recovery_cancel`/`recovery_complete`, and its module doc says outright: "Notification … has no M1 channel: `RecoveryPending` tells the server which account to notify when a notifier exists." `recovery_cancel` already requires a device session and `Devices::usable_durable` (kind 1–3 only; V) — cancellation is built. What is missing is purely visibility: nothing in `AccountView` tells even a device that does query `account/state` that the row exists. (Whether every enrolled device's client actually queries `account/state` often enough to see it is a separate question — see Decision point 9.)

**The account-state object cannot carry this field.** [CRYPTO.md §10.2](../CRYPTO.md#102-ed25519-signatures-and-signed-statements) fixes `account-state`'s body and says it is signed by the account's own identity key (`E_id`). In code, `AccountStatement = Bytes<MAX_ACCOUNT_STATEMENT_LEN>` (`rizzy-proto/src/objects.rs`, V) — raw signed wire bytes the server stores but never produces. During a pending recovery nobody can re-sign it: the recoverer has no account key yet (that is the point of `recovery/complete`), and no enrolled device knows to sign anything. What the task framing describes as "a field on the signed account-state" is not buildable without a new §10.2 construction — exactly what the ADR gate forbids. The response that already wraps `account_state` alongside other unsigned, separately-trusted fields is `AccountView` (`rizzy-proto/src/account.rs`, V): `bundles`, `device_certificates`, `account_settings`, `identity_secret_keys`, `vault_self_grants` all travel beside the signed statement, not inside it, and its doc states "A response type: unknown fields are ignored." That is where this ADR adds a field.

## Decision

1. **Add `pending_recovery: Option<PendingRecoveryNotice>` to `AccountView`** (`rizzy-proto/src/account.rs`), `#[serde(default, skip_serializing_if = "Option::is_none")]`, matching the existing `account_settings` field's style:
   ```rust
   pub struct PendingRecoveryNotice {
       pub opened_at_ms: u64,
       pub available_at_ms: u64,
       pub last_recovery_at_ms: Option<u64>,
   }
   ```
   This is purely additive: `AccountView`'s own doc already states "A response type: unknown fields are ignored" (`rizzy-proto/src/account.rs` line 38, V); `rizzy-proto/src/objects.rs`' module doc (lines 19–21, V) states the general convention this follows — request types reject unknown fields, so "a field added to one of these types is not an additive change for old clients; add it next to the object in the response instead," which is exactly what this field does; and [ADR 0028](0028-api-v1-http-conventions.md) item 14 states the same rule at the API level for `GET /api/meta` ("unknown members ignored by clients") as a precedent elsewhere in the API. No version bump, no new endpoint, no change to any signed statement.
2. **No requesting-device identity.** `recovery_start`/`recovery_complete` take `{login_name, recovery_auth_token}` (`rizzy-proto/src/recovery.rs::RecoveryRequest`, V) — the request is anonymous by design, because the person recovering has lost every device. There is no device id to report, and the rate-limit `source` (the peer address or its /64, [ADR 0028](0028-api-v1-http-conventions.md) item 11) stays server-internal, as it already is for every other bucket. `available_at_ms` is exactly `RecoveryPending`'s existing field (`account_id`, `available_at_ms`, `opened`; `crates/rizzy-domain-auth/src/recovery.rs`, V); `RecoveryPending` has no `opened_at_ms` field. `opened_at_ms` instead comes from the private `recovery::pending()` function's `(recovery_epoch, opened_at_ms, available_at_ms)` tuple, as point 3 already says. Nothing new is computed.
3. **Source and clearing.** `opened_at_ms`/`available_at_ms` come from the server's existing `pending_recovery` row (`recovery::pending()`, reusing `sql::PENDING_RECOVERY_GET`). The field clears exactly when that row clears: `recovery_cancel` (already implemented) or the write that commits the recovery's rotation (CRYPTO §11.9 step 6, which already closes `H_rec` and the row). No new clearing path.
4. **Who sees it.** Populate the field only when the caller already holds a device session for the account — the same gate `recovery_cancel` uses (`SessionKind::Device` plus `Devices::usable_durable`). Leave it `None` for an OPAQUE session (web-vault login or password re-authentication) and for the recovery-only session. Rationale: a kind-4 (web) certificate is never part of the signed device set (CRYPTO §10.2, "Web-vault certificates … are never in the device set") and cannot cancel a recovery either, so showing it the notice is unactionable disclosure for no gain; and the recovering client's own `RecoveryCompleteResponse.account` (built by the same `view::build`, V) already knows about its own recovery from `RecoveryStartResponse`/`RecoveryCompleteResponse` — repeating it there adds nothing. *(L: `account_view`'s doc names three session kinds — device, OPAQUE, recovery-only — and `view::build`'s signature was read; the exact session kind on the login-finish path was not traced for this ADR and the implementer confirms it before coding.)*
5. **Implementation note.** `recovery::pending()` runs against a `&mut WriteTx` (V); `account_view` and `view::build` run on a read transaction (`self.db.begin_read()`, V). This needs a read-path query using the same SQL statement against the `Conn` the read path already holds, not a second write transaction opened from a read call.
6. **"Completed" needs no new signed statement.** A device offline through the whole recovery already learns *that* something changed through the unchanged, Accepted mechanism of CRYPTO §11.3 steps 4–5: `account_key_epoch` and `password_epoch` both increase (CRYPTO §11.9 step 5's default rotation), which already drives the existing re-grant/re-authenticate flows. What that mechanism cannot say is *which* event caused it: recovery (§11.9) and an SK change with its default rotation (§11.5) are the two triggers that move `password_epoch`, `account_key_epoch` **and** `recovery_epoch` together (§11.6 step 5 issues a new code on any rotation unless `recovery_enabled = 0`), so no single epoch tells a device which one happened. `last_recovery_at_ms`, set to the commit time only by the recovery commit and left untouched by every other rotation, gives the client a specific label instead of a generic "something changed."
7. **Trust class — proposed INV-70.** Provisional: the allocation was made across the 2026-10-11 batch in ADR-number order; if ADRs are accepted out of order, the owner renumbers at acceptance. *Every field of `PendingRecoveryNotice` is advisory, unsigned and server-set. A client treats its presence, absence or content as UI input only — never as proof that a recovery is, or is not, pending or occurred — and never as a substitute for the `account-state` verification of INV-25.* This is the same trust class CRYPTO §11.4 already accepts for the web-vault-session notice ("It is not signed, so a malicious server can suppress it", citing AR-9): a malicious server can suppress a real pending recovery exactly as it can suppress that notice, or fabricate a false one. Neither is new; both are already-accepted non-cryptographic controls (AR-9).
8. **No new disclosure.** `account_view` already requires an authenticated session for that account (`session::reload`, V); nothing here is served to an unauthenticated caller, so [CRYPTO.md §5.9](../CRYPTO.md#59-account-enumeration) (account enumeration) is untouched.
9. **Scope fence, and the pull mechanism's real reach.** This ADR adds no field to `device_state` and touches no client-persisted record ([ADR 0026](0026-client-device-state-and-cache.md) unchanged); caching this notice so a pure offline read could warn would itself be an ADR 0026 persistent-format change, so it stays out of this ADR's scope and is an open question for the owner (Open question 4), not a decision made here. The client-side crash-safe pending stage for `rv recovery complete` itself is [ADR 0046](0046-recovery-pending-device-stage.md) (same batch); the eventual M3 `notify` push role's connect auth and envelope is [ADR 0061](0061-notify-websocket-protocol.md) (same batch, M3) — this ADR deliberately does not wait for either to be accepted.

   The mechanism's reach is narrower than "every `rv` invocation." `rv`'s own module doc (`crates/rizzy-cli/src/commands.rs` lines 10–19, V) and ROADMAP §4.2 ("Offline read access") are explicit: `Command::ItemList`/`ItemShow`/`Totp` call only `Device::open` (lines 154–191, V) — no network at all — and `Command::Generate` does not even open a device (line 187, V). Only `Command::Sync` (→ `device.sync()` → `device.online()`), `unlock()` (→ `device.online()`, line 383, V), a write command after it commits (`sync_after_write`, called from `item_create`/`item_edit`/`lifecycle`, V), and `export` (module doc lines 13–14: re-authenticates before reading the cache) ever reach `Device::account_view()` → `account_state_query` (`crates/rizzy-cli/src/device.rs` line 830, V) and so ever see `pending_recovery`. A user whose `rv` usage is exactly the offline-read commands ADR 0026 built — `item list`/`show`/`totp`/`generate` — never queries `account/state`, no matter how often they run `rv`, and never sees this field. Measured against [ADR 0008](0008-account-recovery.md) decision 5's "every enrolled device … is notified": this ADR supplies the server-side data and a delivery point for the device half, for the commands that do reach the server. It does **not**, by itself, guarantee that a device whose owner only ever runs offline-read commands during the wait window is notified at all. A persistent client (M2 extension, M3 desktop) that stays unlocked across many syncs must still add its own periodic `account/state` poll for timely visibility; `rv`'s own residual gap for its offline-read commands is Open question 4, not solved here.

## Consequences

### Positive
- Gives ADR 0008 decision 5's device-notification half a concrete, zero-new-infrastructure delivery point for M1, closing HANDOFF gap 10 for `rv sync`, `rv unlock`, every write command and `export` — but not for `rv`'s offline-read commands (`item list`/`show`/`totp`/`generate`; Decision point 9) — with one optional response field, zero new endpoints, zero new signed objects, zero client-persisted state.
- Reuses data the server already computes and stores (`RecoveryPending`), and a cancellation path already shipped.
- Every M1 instance gets it regardless of whether mail is configured — the email half of ADR 0008 decision 5 stays a separate, unbuilt channel this ADR does not touch.

### Negative
- Visibility is bounded by which commands reach the server, not just by elapsed time: `rv sync`, `rv unlock`, any write command and `export` reach `account/state` and so can surface this field; `item list`, `item show`, `totp` and `generate` never do, however often or recently they run. A user whose `rv` routine is read-only sees nothing for the entire wait window regardless of frequency, and the admin-configured wait can be shorter than the gap between their writes, syncs or unlocks.
- One more server read on every `account_view`/login-finish call (a single indexed row lookup); unmeasured but expected negligible (U).
- `last_recovery_at_ms` needs the recovery-commit write path to also stamp it — a small, additive change next to the existing `PENDING_RECOVERY_DELETE`.

### Risks
- **A malicious server suppresses or forges the notice** (point 7, AR-9). Mitigation: documented as advisory only; no check anywhere may depend on it; the signed-state verification of INV-25 is unaffected and remains the actual security boundary.
- **Epoch ambiguity survives partially.** Even with `last_recovery_at_ms`, a device that was offline across *two* qualifying events (a recovery, then later an SK change with rotation, or the reverse) only ever sees the newer one's timestamp. Accepted as a residual gap; a full per-event log is out of scope for one advisory field.
- **Session-kind gate (point 4) is underspecified** until the implementer traces the login-finish path (L, flagged). Signal: a session kind other than Device or OPAQUE reaching `view::build` unaccounted for.
- **Offline-read commands never see it** (point 9). `item list`/`show`/`totp`/`generate` give no visibility at all for the duration of a wait window spent entirely on those commands; this is accepted as the M1 shape, flagged to the owner as Open question 4, not silently absorbed into "bounded by frequency."

## Alternatives considered

- **A server-signed "recovery-pending" statement**, verified like `account-state`. Rejected: needs a new CRYPTO §10.2 statement type and a signing authority the server does not have — the server cannot assert anything on behalf of an account it cannot unlock, and this is exactly the new construction the ADR gate forbids.
- **A dedicated endpoint** (e.g. `GET recovery/status`). Rejected: duplicates the session-authenticated read `account/state` already performs, for one extra field; every M1 client already calls `account/state` on the commands that go online.
- **Wait for the M3 `notify` push role.** Rejected for M1: leaves ADR 0008 decision 5 unimplemented for two more milestones at zero infrastructure saved, when the pull mechanism costs one field.
- **Email-only notification.** Rejected as the sole M1 mechanism: mail is M3/M6 and optional per instance; this field works on every instance today.

## Open questions for the owner

1. **Ship `last_recovery_at_ms` now, or defer it and accept the recovery-vs-rotation ambiguity (point 6)?** *Recommendation:* ship it now. One extra advisory `u64`, same trust class as the rest of the field, and avoids a second ADR once a client needs to tell them apart.
2. **Show `pending_recovery` to OPAQUE (web-vault) sessions too, even though the web vault cannot cancel a recovery and is never in the signed device set?** *Recommendation:* no, per Decision point 4. A notice the viewer cannot act on is noise, not a safeguard.
3. **For the commands that do reach the server (`rv sync`, `rv unlock`, write commands, `export`): should `rv` treat a non-empty `pending_recovery` as a loud, repeated warning on every one of those commands while it stays set, or a quiet one-time notice?** *Recommendation:* loud, every such command, for as long as it is set. The mechanism exists so the account owner notices inside the wait window; a quiet notice a user can miss defeats the point of decision 5's 72 h-by-default window.
4. **Should `rv`'s pure offline-read commands (`item list`, `item show`, `totp`) get their own visibility path — for example, caching this notice into the ADR 0026 client-persisted `device_state` the next time a command that does reach the server sees it — given that itself needs an ADR 0026 change and its own ADR?** `generate` never opens a device, so no scheme reaches it. *Recommendation:* no decision here; this ADR does not propose the ADR 0026 change. Flag it as a candidate follow-on if the owner wants offline reads covered too.
