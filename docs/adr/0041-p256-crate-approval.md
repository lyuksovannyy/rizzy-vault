# ADR 0041: Approving the `p256` crate for ES256 (ECDSA P-256) in passkeys

- Status: Proposed
- Date: 2026-10-08
- Deciders: project owner
- Milestone: M2

## Context

[ADR 0039](0039-passkeys-vault-and-extension.md) (Accepted, M2) moved passkey storage and browser-extension use from M7 to M2. Its [§3](0039-passkeys-vault-and-extension.md#3-signature-algorithms-and-the-new-dependency-gate) found that COSE alg `-7` (ES256, ECDSA over P-256 with SHA-256) is **not** in [ADR 0009](0009-crypto-dependency-policy.md)'s allowed-crate table, and that essentially every relying party requires ES256 ([ADR 0039](0039-passkeys-vault-and-extension.md#3-signature-algorithms-and-the-new-dependency-gate), **L**, general WebAuthn ecosystem knowledge). EdDSA (`-8`) is already approved (`ed25519-dalek` 3.0.0), but is not sufficient alone. ADR 0039's own acceptance explicitly left this unanswered: "Question 1, approving a P-256 (ES256) crate, is **not** answered by this acceptance: it needs the completed [ADR 0009](0009-crypto-dependency-policy.md) checklist in its own change, and passkey code waits for it." ADR 0039 §3 also gave an intentionally incomplete best-effort pass at the checklist, marking almost every item **U**, and said that pass was "a starting point, not a substitute for actually running it."

This ADR runs [ADR 0009](0009-crypto-dependency-policy.md#approving-a-new-crypto-crate)'s approval checklist properly, item by item, for the crate it recommends. **No code is added by this ADR.** Per the ADR-first rule ([docs/adr/README.md](README.md#the-adr-first-rule)) and ADR 0009's own text ("the PR that adds the dependency must update this ADR, or supersede it... the owner approves"), the dependency may be added only after the owner accepts this ADR (or a successor), and the acceptance PR then amends ADR 0009 and [CRYPTO.md](../CRYPTO.md) §3 as ADR 0009's own Amendments mechanism provides for.

**Constraints that apply to the candidate crate:**

- [ADR 0016](0016-workspace-layout.md) R1: key generation and signing live in `rizzy-core` ([ADR 0039](0039-passkeys-vault-and-extension.md#5-crate-and-module-boundaries) §5), a no-I/O crate. No `rand` or `getrandom` in its direct dependency closure, for any target; it must build for `wasm32-unknown-unknown`.
- Workspace lint `unsafe_code = "forbid"` ([ADR 0009](0009-crypto-dependency-policy.md#our-code) "Our code") applies to **our** code, not to the dependency, but ADR 0009 checklist item 5 still requires recording where and why a candidate crate uses `unsafe`.
- [CRYPTO.md](../CRYPTO.md#1-goals-non-goals-and-rules) §1 Rule 1: standardised algorithms only, as their specifications intend. ES256 is fixed by the WebAuthn/COSE registries, not chosen by us ([ADR 0039](0039-passkeys-vault-and-extension.md#3-signature-algorithms-and-the-new-dependency-gate) item 1).
- [CRYPTO.md](../CRYPTO.md#15-testing) §15 item 2 ("Upstream vectors. Run against our pinned crates, not just trusted from their CI") requires a named upstream test suite for the new primitive.
- RNG rules ([ADR 0009](0009-crypto-dependency-policy.md#rng-rules)): key generation takes the injected `rand_core::CryptoRng` (0.10); signing must not call `rand::rng()`/`thread_rng`.

## Decision

### Recommendation: `p256` (RustCrypto), pinned `=0.14.0`

`p256` is the only RustCrypto P-256 implementation and the natural sibling of the already-approved `ed25519-dalek`/dalek-cryptography family and the AEAD/KDF crates ADR 0009 already pins. No viable alternative exists in an approved or approvable family (see [Alternatives considered](#alternatives-considered)). This matches ADR 0039 §3's own recommendation.

**Recommended workspace declaration:**

```toml
p256 = { version = "=0.14.0", default-features = false, features = ["ecdsa", "alloc"] }
```

**Feature choice, traced through `p256` 0.14.0's own feature graph (V, crate manifest at tag `p256/v0.14.0`, fetched from `github.com/RustCrypto/elliptic-curves`, 2026-10-08):**

- `ecdsa = ["arithmetic", "ecdsa-core/algorithm", "sha256"]`, and `sha256 = ["digest", "sha2"]`. So the single feature `"ecdsa"` already pulls in curve arithmetic (`primefield`, `primeorder`), the optional `ecdsa` crate (renamed `ecdsa-core` in `p256`'s manifest) with its `algorithm` feature (`SigningKey`/`VerifyingKey`, RFC 6979 and randomized signing), and the optional `sha2` dependency for the SHA-256 digest ES256 requires. **No separate `sha2` feature needs to be named**; it comes along with `ecdsa`.
- `alloc` is added because DER signature encoding (`ecdsa::Signature::to_der()`, which WebAuthn's assertion/attestation signature format requires) goes through the `der` crate's allocation path (**L**, not independently re-verified against `ecdsa` 0.17.0's exact source for this ADR; the implementer must confirm whether `Signature<NistP256>`'s fixed-size byte form is enough or `to_der()` is actually called, and drop `alloc` if it is not needed). `alloc` without `std` matches the pattern ADR 0009 already uses for `hpke` and `chacha20poly1305`.
- **Never** `getrandom` (p256's own opt-in feature, `getrandom = ["elliptic-curve/getrandom"]`): leaving it off is what keeps `getrandom` out of `rizzy-core`'s closure (R1). We call only `SigningKey::random(&mut rng)` with the injected `rand_core::CryptoRng`, never `elliptic_curve::rand_core::OsRng` or any `_os_rng` convenience constructor.
- **Never** `std`, `pem`, `pkcs8`, `serde`, `precomputed-tables`, `hash2curve`, `group-digest`, `oprf`, `test-vectors`: none are needed for ES256 key generation and signing, and `std` is unnecessary for a crate that already supports `no_std` (R1 favors the smallest closure, not merely "builds for wasm").

### The ADR 0009 checklist, answered

1. **Need.** COSE alg `-7` / ES256 (ECDSA over P-256, SHA-256) for WebAuthn credential creation and assertion signing ([ADR 0039](0039-passkeys-vault-and-extension.md#2-webauthn-registration-and-assertion-in-the-extension) §2). No construction of ours: algorithm, curve and hash are fixed by the WebAuthn Level 3 and COSE (RFC 9053) specifications. **V** (ADR 0039, the specs themselves).
2. **Provenance.** `p256`, maintained by "RustCrypto Developers" in the `RustCrypto/elliptic-curves` monorepo on GitHub, the same organisation that ships `ed25519-dalek`'s sibling `curve25519-dalek`, and the already-pinned AEAD/KDF/hash crates (`chacha20poly1305`, `sha2`, `hmac`, `hkdf`). Dual-licensed `Apache-2.0 OR MIT` (**V**, crate manifest). Latest published version on crates.io as of 2026-10-08: **`0.14.0`** (**V**, `crates.io` registry API, `newest_version` / `max_stable_version`). Release cadence, exact download count over 90 days and bus factor beyond "same org as crates we already trust": **U**, not pulled from crates.io's download endpoint for this ADR; the approval PR should record the number.
3. **Audit history.** **None found.** No public third-party audit report (NCC Group, Trail of Bits, Cure53, Quarkslab) naming `p256`, `elliptic-curve`, `ecdsa` or `crypto-bigint` specifically was located by this ADR's research (**U** as a negative — absence of evidence, not a confirmed "never audited" from the maintainers themselves). This is the same position ADR 0009 already documents for `hpke` ("no paid audit") and for `sha1`/`blake2`/`poly1305` ("none found"): an established, widely-depended-on crate with no dedicated audit.
4. **Advisories.** **None**, for any of the five crates this pulls in. Verified by requesting the RustSec advisory-db's per-crate directory listing (`api.github.com/repos/rustsec/advisory-db/contents/crates/<name>`) on its default branch for `p256`, `elliptic-curve`, `ecdsa`, `rfc6979` and `primeorder`: all five returned HTTP 404 (no directory, meaning no advisory has ever been filed for that crate name). The same method against a crate **known** to have an advisory (`rsa`, RUSTSEC-2023-0071, the one ADR 0009 already cites) correctly returned that file, and against a crate ADR 0009 already treats as "none known" (`sha1`) correctly returned 404 too — confirming the method. **V** (direct query against the advisory-db repository, 2026-10-08). The approval PR should re-run `cargo deny check` with the crate actually in the lockfile, which is the authoritative check.
5. **`unsafe` in the crate.** `crypto-bigint` and `p256` are both `#![no_std]`; `p256`'s top-level `arithmetic.rs` contains only module declarations (`field`, `scalar`, optionally `hash2curve`, `tables`) with no architecture-specific backend split, unlike `curve25519-dalek` (which ships separate `u32`/`u64`/SIMD backends) or `sha2`/`poly1305` (hardware-intrinsic backends with their own `unsafe`) (**L**, inspection of the crate's module structure on GitHub `master`, 2026-10-08; this ADR did not read every source file of `p256`, `ecdsa`, `elliptic-curve`, `crypto-bigint` and `primeorder` line by line, so a buried `unsafe` block, e.g. for constant-time array transmutes in `crypto-bigint`'s const-generic limb arithmetic, cannot be ruled out). **U** for an exact count. The approval PR must run `cargo geiger` (already used nowhere else in this repo, or acceptable to substitute a plain `grep -rn unsafe` across the five crates' vendored sources) and record the result, the way ADR 0009's `blake2`/`poly1305` entries cite exact file and function names.
6. **Constant-time claims.** RustCrypto's `elliptic-curve`/`crypto-bigint` stack aims for constant-time scalar and field arithmetic by construction (fixed-width const-generic limbs, no secret-dependent branching in the documented design) (**L**, general RustCrypto design reputation, consistent with what ADR 0009 already says about this same stack arriving transitively through `opaque-ke`). `ecdsa`'s RFC 6979 nonce derivation is deterministic and HMAC-based, which avoids the nonce-reuse/bias class of ECDSA timing bugs but is not itself a timing proof. No independent constant-time test (e.g. `dudect`) was found for these crates (**U**). This project has no constant-time test of its own either; [CRYPTO.md §12](../CRYPTO.md#12-randomness-memory-hygiene-and-side-channels)'s `subtle::ConstantTimeEq` rule applies to *our* comparisons, not to upstream scalar arithmetic.
7. **Builds and hygiene.**
   - **wasm32.** With `default-features = false, features = ["ecdsa", "alloc"]`, no feature in the dependency graph above reaches `getrandom` (confirmed from the feature-flag definitions themselves: `getrandom` is `p256`'s own opt-in feature and is never implied by `"ecdsa"` or `"alloc"`) (**V**, manifest inspection, 2026-10-08). Whether `cargo check-wasm` actually passes with the crate physically in the tree is **U**: this ADR adds no code and runs no build, per its scope. The approval PR must run it and extend the R1 `clippy.toml`/`cargo xtask check-deps` allow-list the same way the client-TLS and `blake2`/`poly1305` amendments did.
   - **License.** `Apache-2.0 OR MIT` for `p256`, `elliptic-curve`, `ecdsa`, `primeorder` and `crypto-bigint` (**V**, each crate's own `Cargo.toml`), already on `deny.toml`'s allow-list (the same license pair every other RustCrypto crate in the workspace uses).
   - **Transitive dependencies, new to the workspace.** `p256` 0.14.0 depends on a **newer** RustCrypto generation than the one already in `Cargo.lock`: `elliptic-curve` **0.14.1** (current lockfile has only 0.13.8, pulled in by `opaque-ke`'s `voprf` stack per ADR 0009's own context), plus the new packages `ecdsa` **0.17.0**, `primeorder` **0.14.0**, and (not directly confirmed by version number, **U**) a newer `crypto-bigint` than the `0.5.5` already locked — crates.io's newest `crypto-bigint` is **0.7.5**, but the exact version `elliptic-curve` 0.14.1 actually resolves to is unconfirmed without running `cargo update` (**U**, this ADR does not touch `Cargo.lock`). `digest` is likely satisfied by the `0.11.3` already in the lockfile (the new-generation digest line `ed25519-dalek`/`hmac`/`sha2` 0.11 already use), avoiding a third `digest` generation; this is **L**, not confirmed by resolving the dependency.
   - **New cargo-deny duplicates.** Because the workspace already carries the *old* RustCrypto generation (`elliptic-curve` 0.13.8, `crypto-bigint` 0.5.5, `ff`/`group` 0.13.x, transitively through `opaque-ke`/`voprf`), adding `p256` 0.14.0's *new* generation will add **new entries** to ADR 0009's cargo-deny duplicate warn-list: at minimum a second `elliptic-curve` version and a second `crypto-bigint` version, and possibly second `ff`/`group` versions if `elliptic-curve` 0.14.1 bumped them too (**U**, exact versions unconfirmed without resolving). This is expected debt of the same shape ADR 0009 already accepts for `digest` and `curve25519-dalek` ("stay until opaque-ke catches up"), not a new category of risk, but the acceptance PR's ADR 0009 amendment must add these names to the existing duplicate list and must actually run `cargo deny check` to get the real list cargo-deny 0.20.2 (or whatever version is current then) reports, the way the 2026-09-26 amendment did for `blake2`/`poly1305`.
8. **Test vectors.**
   - **NIST CAVP / FIPS 186-5.** The NIST Cryptographic Algorithm Validation Program publishes ECDSA P-256 key-pair, signature-generation (`SigGen`) and signature-verification (`SigVer`) test vectors for P-256/SHA-256, covering both randomized and (with RFC 6979) deterministic signing.
   - **RFC 6979 Appendix A.2.5.** The deterministic-ECDSA test vector for curve P-256 with SHA-256, the exact algorithm/curve/hash triple ES256 uses. `rfc6979` (the crate `ecdsa` depends on for deterministic nonces) ships its own test suite against this; running the same vector against our pinned `p256`/`ecdsa` build is still worth doing directly, per CRYPTO.md §15 item 2's "not just trusted from their CI" rule.
   - **Project Wycheproof.** Google's Wycheproof suite publishes `ecdsa_secp256r1_sha256_test.json`, which exercises malformed/edge-case signatures (wrong-curve points, zero/negative `r`/`s`, truncated DER) beyond the positive KATs above, the same category of suite ADR 0009 already names for `sha1`/HMAC.
   - **WebAuthn-shaped vectors.** Per [ADR 0039 §4](0039-passkeys-vault-and-extension.md#4-webauthn-message-assembly-no-new-cbor-dependency)'s own note, the hand-written CBOR (`attestationObject`, the COSE `EC2` key map) needs vectors checked against real browser output, not just against our own encoder/decoder round-trip; those vectors should sign with this same `p256` build so the two concerns (CBOR correctness and ES256 correctness) are exercised together, not just independently.
   - These join [CRYPTO.md §15](../CRYPTO.md#15-testing) item 2's upstream-vector list and get their own committed fixture files under `crates/rizzy-core/tests/vectors/`, matching tier (A)'s existing convention.

## Consequences

### Positive

- Unblocks the M2 critical path ADR 0039 flagged as blocking: "without it the feature is not useful for most real sites" ([ADR 0039](0039-passkeys-vault-and-extension.md#negative) Negative).
- Stays inside the dalek/RustCrypto family already trusted for every other signature and AEAD primitive in this project; no new maintainer, license family or review relationship to establish.
- The feature set (`["ecdsa", "alloc"]`, no `getrandom`, no `std`) keeps `rizzy-core`'s R1 no-I/O and wasm32 contracts intact by construction, the same way the existing `hpke`/`chacha20poly1305` feature choices do.

### Negative

- Introduces a **second, newer** RustCrypto elliptic-curve generation (`elliptic-curve` 0.14.x, `crypto-bigint` 0.6/0.7.x) alongside the one `opaque-ke`'s `voprf` stack already pins (0.13.8 / 0.5.5), growing ADR 0009's documented cargo-deny duplicate debt rather than shrinking it.
- Zero public third-party audit, same as several crates ADR 0009 already accepts (`hpke`, `blake2`, `poly1305`); the M8 audit budget must now also cover `p256`, `elliptic-curve`, `ecdsa`, `rfc6979`, `primeorder` and whatever `crypto-bigint` version lands.
- `unsafe` usage across the five crates is only spot-checked here (module structure, not a full source read); the approval PR, not this ADR, must produce the exact answer.

### Risks

- **A P-256 implementation bug or timing leak**, exactly as ADR 0039's own Risks section already names, "would be a real vulnerability in a primitive this project did not need before." Mitigation: this checklist run for real in the approval PR (not just this best-effort pass), plus M8 audit scope growth.
- **The unresolved transitive-version question** (item 7 above) could, in the worst case, surface a real version conflict only `cargo update` reveals — for example if `elliptic-curve` 0.14.1 requires a `digest` major version the workspace's new generation does not already satisfy. Signal: `cargo check`/`cargo deny check` failing in the approval PR; mitigation is the same "resolve it there, note it in the PR" path every other dependency bump uses.
- **DER signature encoding's `alloc` need is unconfirmed** (item 7, `alloc` feature note). If it turns out unnecessary, the approval PR should drop it; if something *else* turns out to need it that this ADR did not anticipate, the PR records that instead of silently diverging from this ADR's recommended feature set.

## Alternatives considered

- **`ring`.** Rejected: brings a C/assembly (BoringSSL-derived) backend into `rizzy-core`, which conflicts with the workspace's `unsafe_code = "forbid"` lint and ADR 0016 R1's "no FFI, no hand-written C ABI" posture (already the reasoning ADR 0009's own "Alternatives considered" gives for ruling out `ring`/libsodium project-wide), and `ring` has no first-class `wasm32-unknown-unknown` story without further patching (**L**, not independently re-verified for this ADR). `ring` is already approved, but only in `rizzy-cli` for TLS ([ADR 0030](0030-client-tls-rv.md)), a leaf crate outside R1's scope — a fundamentally different trust boundary than `rizzy-core`.
- **`aws-lc-rs`.** Same category of rejection as `ring`: a C/assembly-backed crate, wrong trust boundary for an R1 crate, not evaluated further.
- **`p256` without the `arithmetic`/`ecdsa` features, hand-rolling ECDSA ourselves on top of raw curve points.** Rejected: [CRYPTO.md §1](../CRYPTO.md#1-goals-non-goals-and-rules) Rule 1 requires "standardised algorithms... implemented by established crates, and we use them as their specifications intend" — assembling ECDSA signing by hand from lower-level primitives is exactly the kind of home-made construction ADR 0009 and CRYPTO.md forbid without its own ADR, and `ecdsa` already implements RFC 6979 correctly.
- **A FIDO/CTAP "passkey-rs" crate family that bundles its own P-256.** Already rejected by [ADR 0039 §5](0039-passkeys-vault-and-extension.md#5-crate-and-module-boundaries) and [ADR 0016](0016-workspace-layout.md) §3–4's "Known conflict ahead" note: these pull `getrandom` 0.2 non-optionally and target CTAP authenticators we do not need.
- **Waiting for a published audit before approving `p256`.** Rejected as impractical: ADR 0009's own M0 fact sheet already establishes that "almost none of the crate versions we will ship have been audited in that exact version," and the project's working rule (CRYPTO.md §1 Rule 3) is a pinned, reviewed integration plus an M8 external audit, not a precondition of upstream audit coverage.

## Open questions for the owner

1. **Approve `p256` `=0.14.0` with `default-features = false, features = ["ecdsa", "alloc"]`, per the checklist above.** *Recommendation:* approve. No viable alternative exists in an approvable family (see [Alternatives considered](#alternatives-considered)), the feature set keeps R1 and wasm32 intact by construction, and the open **U** items (exact download/bus-factor numbers, exact new transitive versions, exact `unsafe` byte-for-byte count, whether `alloc` is strictly required) are the kind of detail ADR 0009 already accepts resolving in the approval PR itself (its own checklist text: "the PR that adds the dependency must update this ADR... the owner approves" — the owner's approval is of the *shape* of the dependency, with the PR confirming the mechanical facts a `cargo add` and `cargo deny check` settle automatically).
2. **Who re-runs the mechanical checks before the dependency actually lands.** This ADR was produced without adding the crate to any `Cargo.toml` (out of scope for this change). *Recommendation:* the implementation PR that adds `p256` is also the PR that runs `cargo check-wasm`, `cargo deny check`, `cargo xtask check-deps`, and amends ADR 0009's crate table, feature-set list and cargo-deny duplicate-debt note, and CRYPTO.md §3, exactly as ADR 0009's `blake2`/`poly1305` and client-TLS amendments already model.
