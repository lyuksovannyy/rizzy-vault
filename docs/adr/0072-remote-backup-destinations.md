## Context

[ADR 0071](0071-encrypted-db-backup-format.md) fixes what the scheduled backup's bytes are (a new format version of [ADR 0023](0023-logical-backup-format.md)'s dump, sealed under a new CRYPTO.md §5.11 purpose). (Corrected in this cross-batch review pass, 2026-10-11, **V**: ADR 0071 is filed in this same review batch, as `0071-encrypted-db-backup-format.md`, not `0071-server-db-backup-format.md` as an earlier draft of this ADR had it, and was not unreadable as this Context previously assumed.) This ADR fixes where those bytes go and how the destination is authenticated; it does not revisit 0071's envelope.

[ROADMAP §4.2](../ROADMAP.md#42-core-vault-m1) lists, Should: "Scheduled encrypted backups to user-chosen storage (local folder, WebDAV, S3-compatible) | M8". [ADR 0022](0022-server-mode-only.md) point 3 moved it here from the parked M4. [ADR 0023](0023-logical-backup-format.md) Risks anticipated it: "If operators need authenticated or encrypted backups (M8's scheduled backups, ROADMAP §4.2), that is a new format version and an ADR" — 0071 is the format half, this is the rest.

Server-initiated egress to an operator-named host is not entirely new: [ADR 0022](0022-server-mode-only.md) §2's live replacement of [ADR 0010](0010-server-shape.md) §1's roles table already gives `worker` an Outbound cell of "SMTP relay for notification mail, if configured (M3)" — Accepted but unbuilt (V: `crates/rizzy-server/src/config.rs` has no relay setting, only role-name tokens for the unbuilt `smtp`/`notify`/`icons` roles). This ADR closes the gap for backup destinations only; Open questions flags the M3 relay still needs its own.

## Decision

### 1. The job: in-process, one upload per run, capped

`worker` gains step 8 of `run_once`'s module doc: when a destination is configured, it calls `rizzy_storage::Database::dump` **in-process** ([ADR 0023](0023-logical-backup-format.md) §1; never shells out, never a second connection), seals it as [ADR 0071](0071-encrypted-db-backup-format.md)'s `SERVER_DB_BACKUP` envelope, and uploads the whole file in one request. With no destination configured, step 8 is one check. The leader lock gates every step, so a standby runs it zero times.

Default `RIZZY_BACKUP_UPLOAD_MAX_MIB = 512`, operator-raisable to 2048 (2 GiB, [ADR 0023](0023-logical-backup-format.md) §3's own cap), tighter than the reader's limit because the dump lives in server memory, not a short-lived CLI process. Over the cap, the run refuses before `dump` allocates further; it never truncates or retries silently. `RIZZY_BACKUP_INTERVAL_HOURS` (1–168, default 24) sets the run interval.

### 2. Destinations, naming, retention, and transport

- **Object naming (every kind).** Every upload's name embeds its envelope's `created_at_ms`: `local` writes `<RIZZY_BACKUP_DESTINATION_PATH>/<created_at_ms>.rzbak` (the setting names a **directory**, created if absent, not a file); `webdav` `PUT`s `<RIZZY_BACKUP_DESTINATION_URL>/<created_at_ms>.rzbak`; `s3` `PUT`s key `<RIZZY_BACKUP_DESTINATION_PREFIX><created_at_ms>.rzbak` under `RIZZY_BACKUP_DESTINATION_BUCKET`. So the second scheduled run of any kind writes a different name, not the same path `local`'s `create_new` would then refuse.
- **Retention.** This job never prunes. Every upload stays until something else removes it: an operator cron, `webdav`/`s3`'s own lifecycle rule, or a manual `find`/delete for `local`. Unbounded growth absent that is a named cost (Negative).
- **`local`**: a filesystem write, no network. Reuses [ADR 0023](0023-logical-backup-format.md) §4's file rules (mode 0600, `create_new`, never overwriting, removing a partial file on failure); refuses a path inside the data directory or the secrets mount ([ADR 0010](0010-server-shape.md) §4).
- **`webdav`**: one `PUT`, HTTP Basic auth (RFC 4918/7617 semantics: U, not read this session).
- **`s3`**: one `PUT`, header-based AWS Signature Version 4 `Authorization` from `hmac`+`sha2` (already pinned). **Never a presigned URL** — the signature would sit in the query string, forbidden below on INV-52's ground.
- Both network kinds: `https://` only; no redirects; connect timeout 10 s, total 300 s, both operator-configurable (`RIZZY_BACKUP_CONNECT_TIMEOUT_S`, `RIZZY_BACKUP_UPLOAD_TIMEOUT_S`). An optional `RIZZY_BACKUP_CA_FILE` (≤64 KiB, ≤16 `CERTIFICATE` blocks, parsed before a byte is sent, replacing the public roots) is a **new rule for this client**, modeled on [ADR 0030](0030-client-tls-rv.md) Decision 4/6 and [ADR 0035](0035-ca-file-ca-certificates-only.md) — those bind `rv`'s TLS only, not the server's.

### 3. HTTP client: hyper's `client` feature, now also a `rizzy-server` dependency

`rizzy-server` turns on hyper's `client` feature, mirroring `rizzy-cli`. `hyper-util`, `tokio-rustls`, `rustls`, `webpki-roots` and `http-body-util` are already in `Cargo.lock`, but only as `rizzy-cli`'s (V, above) — not `rizzy-server`'s. Two Accepted texts scope the last four to `rizzy-cli` only: [ADR 0030](0030-client-tls-rv.md) Decision 1's lead-in, and [ADR 0009](0009-crypto-dependency-policy.md)'s 2026-10-05 Amendment (the `rustls` crate-table clause and its "Where it is applied" sentence). This ADR widens both by name under [ADR 0020](0020-partial-supersession.md) point 9 (below), rather than reading [ADR 0013](0013-shared-client-core.md) as if it already covered a server HTTP client: its §2 "Each host provides five capabilities" table has an "HTTP transport" row with no server column (Web vault/Extension/Desktop/Mobile/CLI only), and its separate §1 layer table gives `rizzy-client`'s row "every client" only, unlike `rizzy-core`/`rizzy-proto`'s "every client, and the server". No WebDAV or S3 crate: two hand-rolled `PUT` methods, not a general client; `aws-sdk-s3` and a WebDAV crate are rejected below.

Approval, under [ADR 0009](0009-crypto-dependency-policy.md) "Approving a new crypto crate": items 2–7 (provenance, audits, advisories, `unsafe`, constant time, builds) are unchanged from the 2026-10-05 entry — same crates, pins and features, re-cited not re-run. Item 1, **Need**, is new: server-initiated HTTPS egress to an operator-named, arbitrary host (§2), not `rv`-to-own-server TB-1 transport ([ADR 0030](0030-client-tls-rv.md) Context) — a different trust boundary from the one 0009/0030 approved, even though the crates are identical. Item 8, **Tests**: the loopback destination tests of §2; `cargo xtask check-deps`'s `dangerous`/`danger::` scan already covers `crates/*/src` (ADR 0030 Decision 3), so `rizzy-server` is covered with no change to the rule itself. Running `cargo check-wasm`, `cargo deny check` and `check-deps` against the widened scope is **U** here (this is a read-only drafting pass); the implementing PR runs them, as ADR 0030's own "On acceptance" did for its item 7.

### 4. Credential sealing: a new §5.11 purpose, not plaintext config

New CRYPTO.md §5.11 purpose `SERVER_BACKUP_DESTINATION`, id `0x0106`, allocated across the 2026-10-11 batch in ADR-number order: 0x0100–0x0102 are taken (V, CRYPTO.md §5.11); ADR 0060 (SMTP credentials) takes `0x0103`, ADR 0066 (`SERVER_SHARE_EMAIL_CODE`) takes `0x0104`, and ADR 0071 (`SERVER_DB_BACKUP`) takes `0x0105`, each ahead of this ADR in ADR-number order. Construction 10 of CRYPTO §1 ("server-side sealing"), applied a second time. Keyed by §5.11's subkey derivation from `server_data_key` with `LABEL("server/backup-destination")`. Context `ctx = u32 destination_cred_seq`, incremented each time the operator sets new credentials: the table holds one row, so the sequence guards only against a stale row being reinstated, not cross-row movement (unlike `totp_credential_seq`).

**Rotation (closes a gap, not optional).** `worker` step 2 (CRYPTO.md §5.11 "Rotation") is extended: besides re-sealing TOTP rows under the account lock, it re-seals `storage_backup_destination` under the current data key when it names another, in its own update — no account lock, since the table holds one row. `ServerSecrets::drop_unused_data_keys` is extended to also query this row's `data_key_id`: today it scans only `TOTP_DATA_KEY_IDS` and `LOGIN_STATE_DATA_KEY_IDS` (V, above), so without this change the drop step would remove a key the backup-destination row still names, and the server would then refuse to start (§5.11: "refuses to start if a row names an id the file lacks"). The exact CRYPTO.md §5.11 Rotation-sentence replacement is under "On acceptance" below.

Why sealed, not plaintext config or the secrets file: the secret stays in the DB and only its key stays outside — INV-8's existing shape for TOTP secrets. [ADR 0010](0010-server-shape.md) §4 keeps the server from writing the secrets file except one-offs with the mount remounted writable; a routine credential rotation must not need that. [ADR 0023](0023-logical-backup-format.md) Alternatives already rejected a passphrase-encrypted file for the same reason repeated below: no operator is present at 3 a.m.

### 5. Storage: one new table, excluded from the backup dump

A new table, `storage_backup_destination` (one row), owned by `rizzy-storage` directly, outside [ADR 0011](0011-storage.md) point 5's `auth_`/`vault_`/… prefixes — following `storage_meta`/`storage_reconciliation`'s precedent (V, `tables.rs`). `cargo xtask check-tables` does not exist yet (V, `crates/xtask/src/check.rs`'s own doc comment); when written it must allow `storage_`, as it already must for the two existing tables. Columns: kind; non-secret fields (path, URL, bucket, prefix, region, endpoint, as the kind needs); the sealed credential and its `data_key_id`; `destination_cred_seq`; timestamps. **Excluded** from [ADR 0023](0023-logical-backup-format.md)'s `TABLES`, like `storage_meta`/`storage_reconciliation`: a restore must not silently re-point a freshly restored instance at another instance's remote destination. The operator reconfigures it after a restore, like the SMTP relay today.

### 6. Operator interface

`RIZZY_BACKUP_DESTINATION_KIND` (`none`/`local`/`webdav`/`s3`, default `none`); `RIZZY_BACKUP_DESTINATION_PATH`/`_URL`/`_BUCKET`/`_PREFIX`/`_REGION` as the kind needs (§2's naming); `RIZZY_BACKUP_INTERVAL_HOURS`, `RIZZY_BACKUP_UPLOAD_MAX_MIB`, the two timeouts, `RIZZY_BACKUP_CA_FILE`. No secret in the environment or config file — the one exception stays `RIZZY_DATABASE_URL`. `rizzy-vault backup-destination set` reads the credential once from stdin, seals it, writes the row; `backup-destination show` prints the non-secret fields and the last run's outcome, never the credential (INV-21); `backup-destination clear` empties the row. Failures are logged as counts and value-free text (INV-48).

### Proposed invariants (allocated as INV-99 across the 2026-10-11 batch, in ADR-number order. Provisional: the allocation was made across the 2026-10-11 batch in ADR-number order; if ADRs are accepted out of order, the owner renumbers at acceptance.)

- **Proposed INV-99.** The scheduled backup-upload job dials only an operator-configured destination: URL, kind and credential come from `RIZZY_*` settings or `backup-destination`, never from an API body, a client-supplied value or the backup file's contents. A `webdav`/`s3` destination is dialed only over `https`, no redirects. The uploaded bytes are exactly [ADR 0071](0071-encrypted-db-backup-format.md)'s `SERVER_DB_BACKUP` envelope. This job never reads the OPAQUE server setup or `enum_key`, and never uploads secrets-file bytes — INV-50's boundary (the setup stays outside the DB and any backup) is unchanged; it does read `server_data_key`, to unseal the destination credential (§4). A SigV4 request signs only in the `Authorization` header, never a query string (INV-52's rule, extended to this client). The credential is sealed at rest (§4), never logged or rendered (INV-21, INV-48). A dump over the cap refuses the run before any byte is read for upload.
- INV-51's SSRF allow-list does not extend here: it defends `icons`' content-derived fetches to addresses a remote page names, while a backup destination is operator-named and may legitimately be a LAN NAS.
- The M3 SMTP-relay outbound has no invariant either; out of scope here, flagged for that feature's own ADR.

## Consequences

### Positive

- Self-hosters get off-box backups without a separate cron-plus-`rclone` setup; the credential never sits in a config file an operator might commit or screenshot.
- [ADR 0071](0071-encrypted-db-backup-format.md) seals the dump under a key the destination never holds, so a mistyped destination, a hostile provider or a breached bucket yields a file nobody but this server can open.
- No new *package* enters `Cargo.lock` — `rizzy-cli` already pulls all four TLS/body crates — but `rizzy-server`'s own dependency list gains four it currently lacks (`tokio-rustls`, `rustls`, `webpki-roots`, `http-body-util`; V, its `Cargo.lock` block).

### Negative

- Hand-rolled WebDAV and SigV4 clients are more code to own than a library, for two destination kinds.
- Unbounded destination growth: this job never prunes (§2); an operator who does not script retention accumulates backups forever.
- `local` is the only destination with no network or auth code; `webdav`/`s3` share no code beyond the `PUT` body.

### Risks

- SigV4 corner cases (chunked/unsigned-payload modes, clock skew, non-AWS quirks) are U; a real interop failure the hand-rolled signer cannot patch is the signal to revisit with a client crate.
- A compromised server can re-point the destination or exfiltrate the sealed file. Already accepted under A2/AR-9 and bounded: the file stays sealed either way (TB-15, "On acceptance" above).

## Alternatives considered

- **`aws-sdk-s3`**: a large dependency tree for a feature SigV4-over-`hmac`/`sha2` already covers.
- **`reqwest`**: a second HTTP client crate beside the hyper stack the server already runs; ADR 0013/0030 already rejected this shape for `rv`.
- **A WebDAV crate**: thin ecosystem, little gain over one `PUT` with Basic auth.
- **Presigned S3 URLs**: signature material in the query string; rejected with INV-52 in mind.
- **A passphrase-derived key, like `SERVER_SECRETS_BACKUP`**: needs an operator present at every scheduled run; unusable unattended.

## Open questions for the owner

1. **Purpose id and INV number.** Resolved: `0x0106`/INV-99, the batch's purpose and INV ids reconciled in ADR-number order; confirm at acceptance in case an ADR lands out of order.
2. **Does `storage_backup_destination` ever join `TABLES`?** *Recommendation:* no, permanently excluded.
3. **Acceptance order with sibling [ADR 0071](0071-encrypted-db-backup-format.md), now resolved by scope, not order.** Confirmed in this cross-batch pass (2026-10-11): ADR 0071 replaces only the "Confidentiality is out of scope" bullet's first and last sentences of [ADR 0023](0023-logical-backup-format.md) §2 (for format_version 2); this ADR replaces only that bullet's middle "database holds only ciphertext…" sentence (unconditionally). The two edits target different sentences of the same bullet and do not overlap, so either order of acceptance works with no post-acceptance merge. *Recommendation:* accept in either order; no further coordination needed.
4. **Ship the private-CA file (§2) now, or defer to M9 polish?** *Recommendation:* now — a NAS-hosted WebDAV target is the likely M8 case and usually carries a private certificate.
5. **Are 512 MiB / 10 s / 300 s / 24 h the right defaults?** *Recommendation:* yes for M1-era personal-scale databases, [ADR 0023](0023-logical-backup-format.md) §3's own assumption; revisit with real sizes before M9.
