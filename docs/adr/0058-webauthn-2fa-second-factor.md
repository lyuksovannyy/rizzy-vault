# ADR 0058: WebAuthn/FIDO2 security keys as a server-side second factor

- Status: Proposed
- Date: 2026-10-11
- Deciders: project owner
- Milestone: M3

## Context

[ROADMAP §4.3](../ROADMAP.md#43-cryptography--authentication-m0m1-audited-in-m8) lists "2FA: TOTP, WebAuthn/FIDO2 security keys" with WebAuthn due M3. [ADR 0003](0003-authentication-opaque.md) point 11 already provides the slot: "**2FA** (TOTP in M1, WebAuthn in M3) gates server access only. It never feeds key derivation." This ADR fills that slot; it changes no part of ADR 0003's meaning, so it supersedes none of it (contrast ADR 0022's existing partial supersession of ADR 0003 point 10, On-device mode, which this ADR leaves untouched).

TOTP already ships this way ([CRYPTO.md §11.15](../CRYPTO.md#1115-totp-m1), [`rizzy-domain-auth::totp`](../../crates/rizzy-domain-auth/src/totp.rs)): a two-step enrolment gated by a fresh OPAQUE session (`Session::require_fresh_opaque`, [CRYPTO.md §5.10](../CRYPTO.md#510-sessions-after-authentication)), a secret sealed as `SERVER_TOTP_SECRET` (it is a shared secret), and a login-time check that accepts a code only above the last accepted time step, in the same transaction as the login. `AuthError::SecondFactorRequired` is returned "only ever after KE3 verified" — the server reveals nothing about an account's 2FA status before password and Secret Key are proven ([§5.9](../CRYPTO.md#59-account-enumeration)). A WebAuthn credential is not a shared secret: it is a public key, a credential id and a sign counter, none of which need confidentiality. The decision below reuses the fresh-session, challenge-TTL and read-once-under-the-lock machinery TOTP and device-auth already establish, rather than the sealing machinery, which does not fit.

This is a different feature from [ADR 0039](0039-passkeys-vault-and-extension.md): that ADR stores WebAuthn credentials *in the vault*, for logging into *other sites*, synced across the user's own devices with the counter fixed at 0 (we are the authenticator). This ADR is the reverse: rizzy-vault is the *relying party*, the credential lives in `rizzy-domain-auth`'s own tables, never in a vault item, and a hardware security key's counter is real and used for clone detection. [ADR 0041](0041-p256-crate-approval.md) approved `p256` for ES256 in that other context, and [ADR 0009](0009-crypto-dependency-policy.md)'s 2026-10-09 Amendment records it as declared "as a normal dependency of `rizzy-core` only" ([ADR 0039 §5](0039-passkeys-vault-and-extension.md#5-crate-and-module-boundaries)). This ADR reuses that same math, if `webauthn-rs` allows it, through a new `rizzy-core` entry point ([§7](#7-crate-boundary)) — not a second ECDSA implementation, and not a second crate boundary for `p256` to cross. The ceremony crate itself — `webauthn-rs`, and the `openssl` dependency it brings — is [ADR 0059](0059-webauthn-rs-crate-approval.md)'s decision, already pre-scoped by [ADR 0009](0009-crypto-dependency-policy.md) owner decision 1 (2026-09-25, **V**, read this session, including its distinct `wrappers` lists for `openssl` and `openssl-sys`) and [THREAT_MODEL Q-14](../THREAT_MODEL.md#10-open-questions-for-the-owner) (not re-read this session; carried from the prior draft, **L**): a narrow `deny.toml` exception for `openssl` and `openssl-sys`, each confined to `webauthn-rs-core` (`openssl-sys`'s list also names `openssl` itself, since `openssl` depends on it — [ADR 0059](0059-webauthn-rs-crate-approval.md) records the exact lines), confined by `cargo xtask check-deps` to `rizzy-server` and the auth domain crate, never reaching `rizzy-core` or any client. [ADR 0009](0009-crypto-dependency-policy.md)'s own Context says `deny.toml` bans `openssl`/`openssl-sys` outright today; the file itself was not re-read this session. That exception has not landed. This ADR assumes it lands via ADR 0059 and does not re-decide it.

Scope: user-account login only. The admin panel's own second factor, listener and origin are [ADR 0060](0060-admin-panel-stack-boundary.md)'s decision; if the admin panel sits on a different origin, its RP-ID binding is a separate question for that ADR, not this one.

## Decision

1. **Credential kind and storage.** A new `webauthn_credential` table in `rizzy-domain-auth` (own module, `webauthn`, next to `totp`), keyed by `account_id`, holding `credential_id` (bytes), `alg` (`1` = ES256, `2` = EdDSA — the same two values and meaning ADR 0039 §1's `passkey/<id>/alg` enum uses, for one mapping in the codebase), the COSE-encoded public key, `sign_count` (u32), `label`, `created_ms`. None of this is sealed: a public key, a credential id and a counter are not secrets, so no new `SERVER_*` envelope purpose is added to the server-only 0x0100–0x01FF range ([CRYPTO.md §5.11](../CRYPTO.md#511-server-side-encryption-not-zero-knowledge), [§9.5](../CRYPTO.md#95-parsing-and-allow-list-rules)); integrity comes from the account-locked transaction and from verifying every assertion's signature, the same way `device_certificate` rows (also public keys) are not sealed either. This does not touch [INV-8](../THREAT_MODEL.md#8-security-invariants), which is about *secrets*.

2. **Registration (enrolment).** Gated by `session.require_fresh_opaque`, identically to `totp_enrol_start`/`totp_enrol_confirm`. `webauthn_enrol_start` issues a 32-byte random challenge with a 60 s TTL, stored unsealed and single-use — the same shape as the device-auth challenge ([CRYPTO.md §5.10](../CRYPTO.md#510-sessions-after-authentication) step 1), not a new construction — together with `rp_id` = the server's canonical origin's host ([§5.3](../CRYPTO.md#53-context-identifiers-and-credential-identifier)), `user.id` = `account_id`, `pubKeyCredParams` = `[ES256, EdDSA]`, and `excludeCredentials` = the account's existing credential ids. `webauthn_enrol_confirm` takes the attestation response, checks `type == "webauthn.create"`, the challenge (read-and-deleted once), `clientDataJSON.origin` against the canonical origin, and `rpIdHash` against `SHA-256(rp_id)`; **the creation options request attestation conveyance `"none"`, and the enrolment path does not verify the returned attestation statement, whatever format actually arrives** — ADR 0059 records how the ceremony crate is configured to achieve that. We hold no attestation CA trust store, so verifying a `packed` or self-attestation statement would buy nothing, and refusing a registration merely because an authenticator ignored our `"none"` preference and attested anyway would turn away legitimate hardware keys for no security benefit. This applies, on the RP side, the same no-CA-trust-store reason [ADR 0039 §4](0039-passkeys-vault-and-extension.md#4-webauthn-message-assembly-no-new-cbor-dependency) gives for *our own* `"none"` attestation when rizzy-vault is the authenticator ("we are not a hardware authenticator claiming a certified attestation chain") — but it is not the same decision: ADR 0039's [Open questions item 2](0039-passkeys-vault-and-extension.md#open-questions-for-the-owner) and [Alternatives considered](0039-passkeys-vault-and-extension.md#alternatives-considered) rejected *producing* self-attestation there, for lack of a CA chain to back it; this ADR, as the RP, needs no such chain either, precisely because it verifies nothing; then stores the row.

3. **Assertion (login).** `LoginFinishRequest` already carries `totp: Option<TotpCode>` only after KE3 verifies. A WebAuthn assertion needs `allowCredentials` and a challenge, which cannot be produced before password and Secret Key are proven without leaking which accounts hold which credential ids pre-proof — a new enumeration channel §5.9 does not have today. So, unlike TOTP, a WebAuthn second factor needs one extra round trip: on `SecondFactorRequired` where the account's enrolled kinds include WebAuthn, the server does not delete the verified state outright (as it does today for a TOTP-only miss); it demotes it to a 60 s, unsealed, single-use "second-factor-pending" row (`pending_id`, `account_id`), from which `webauthn_login_challenge(pending_id)` returns `allowCredentials` and a fresh challenge, and `webauthn_login_finish(pending_id, assertion)` verifies it and issues the session. TOTP's existing restart-the-whole-OPAQUE-login path is unchanged; this new row is additive, used only when the client asks for it.

4. **Non-discoverable, no user verification required.** The password and Secret Key already authenticated the user before KE3 verifies; the key need only prove possession (`UV` not required, `UP` required). Credentials are server-side (non-discoverable): no usernameless/account-chooser flow, since the account is already known.

5. **Clone detection (proposed INV-83).** On every assertion: `stored = 0, received = 0` → accept, no detection possible for this authenticator (residual, recorded, same posture as a counter that never increments); `stored = 0, received > 0` → accept, begin tracking; `stored > 0, received > stored` → accept, update `sign_count`; `stored > 0, received ≤ stored` → refuse (fail closed, [CRYPTO.md §1](../CRYPTO.md#1-goals-non-goals-and-rules) Rule 6) and flag the account's security-event log (the R-row at THREAT_MODEL.md line ~975, INV-48) with a possible-clone signal; the credential is not auto-disabled (open question 4). This is the reverse of ADR 0039 §2, where *we* are the authenticator and fix our own counter at 0; here we are the RP consuming someone else's.

6. **RP-ID/origin binding (proposed INV-84).** A ceremony's `rpId` is always the server's own canonical origin's host — there is no third-party RP-ID the way [INV-64](../THREAT_MODEL.md#8-security-invariants) must police for vault passkeys in the extension, because this ceremony never runs inside a page the server does not control. `clientDataJSON.origin` must equal the canonical origin; a server reachable under more than one hostname has the same "configure one canonical origin" constraint OPAQUE's Context already carries ([ADR 0003](0003-authentication-opaque.md) point 5).

7. **Crate boundary.** Ceremony orchestration (challenge issuance, CBOR/COSE parsing of `attestationObject`, origin and `rpId` checks) runs through the crate ADR 0059 approves (`webauthn-rs`), inside `rizzy-domain-auth`/`rizzy-server`, never `rizzy-core` or any client — a security key's attestation object is adversary-controlled, multi-vendor wire format, which is exactly the class of input ADR 0018 and [ADR 0039 §4](0039-passkeys-vault-and-extension.md#4-webauthn-message-assembly-no-new-cbor-dependency) already reasoned against hand-rolling, unlike ADR 0039's own small, fixed CBOR subset entirely within our control. **`p256` itself is not taken as a direct dependency of `rizzy-domain-auth`/`rizzy-server`.** [ADR 0039 §5](0039-passkeys-vault-and-extension.md#5-crate-and-module-boundaries) places ES256 key generation and signing in `rizzy-core`, and [ADR 0009](0009-crypto-dependency-policy.md)'s 2026-10-09 Amendment records `p256` as declared "as a normal dependency of `rizzy-core` only." That entry is a record of what that implementation PR did under ADR 0039 §5, not a fresh rule — but nothing in it, or in ADR 0039, approves `p256` anywhere else, and [ADR 0016](0016-workspace-layout.md)'s crate-boundary rule means widening that placement needs a new ADR to name and supersede it first ([ADR 0020](0020-partial-supersession.md) points 4 and 9). This ADR does not do that. If ADR 0059 finds that `webauthn-rs`'s API exposes a seam to substitute a custom ES256 verifier, `rizzy-core` gains a small `verify_es256` entry point over the COSE key and signature bytes, in the spirit of [ADR 0009](0009-crypto-dependency-policy.md#our-code)'s "one entry point per construction" rule, and `rizzy-domain-auth` calls into it — it already depends on `rizzy-core` for OPAQUE and TOTP (**V**, `crates/rizzy-domain-auth/Cargo.toml`, read this session), so this adds no new crate edge. If no such seam exists, this ADR adds no new `rizzy-core` entry point at all: the ceremony crate owns the stored-key decode (point 1) and the assertion-time signature verification (`webauthn_login_finish`, point 3) end to end, through its own `openssl`-backed path, inside the exception already scoped to it. Either way `p256`'s crate boundary stays exactly where ADR 0039 §5 put it. Whether the seam exists is **U** (not read this session); ADR 0059 records the finding.

8. **Both algorithms, no new approval.** `pubKeyCredParams` offers ES256 and EdDSA; EdDSA costs nothing new (`ed25519-dalek` already approved, [ADR 0009](0009-crypto-dependency-policy.md)) and some keys prefer it, mirroring [ADR 0039 §3](0039-passkeys-vault-and-extension.md#3-signature-algorithms-and-the-new-dependency-gate)'s table.

9. **A new CRYPTO.md section is required before code lands.** [§5.10](../CRYPTO.md#510-sessions-after-authentication) only names "WebAuthn in M3" in passing, and there is no §11.16. A §11.16 "WebAuthn 2FA (M3)" must fix: challenge length and TTL, the allowed COSE algs, the `rpId`/origin rule, the counter rule of point 5, the stored credential shape of point 1, and the second-factor-pending row's shape and TTL. This is the standardized W3C WebAuthn Level 3 ceremony, not a new composition under [CRYPTO.md §1](../CRYPTO.md#1-goals-non-goals-and-rules) Rule 2 (the same reasoning ADR 0039 §4 gives for hand-written CBOR), so it does not join that rule's audit-target list.

## Consequences

### Positive
- A phishing-resistant second factor: the browser, not our code, enforces that a credential only answers for the origin it was created under.
- Reuses four already-accepted patterns (fresh-session gate, unsealed single-use challenge rows, account-locked read-once transactions, monotonic-counter rejection) instead of inventing new ones.
- No new confidentiality primitive and no new sealed purpose: the only new server state is public-key material.
- `AuthError::SecondFactorRequired`'s existing "only after KE3" discipline extends unchanged; WebAuthn adds no new pre-password enumeration surface.

### Negative
- A third round trip appears in the login flow for WebAuthn specifically (point 3), new protocol surface `rizzy-proto` and ADR 0028 conventions must cover.
- The `openssl` exception ADR 0059 must land before any of this code merges; until then this ADR is blocked, same as ADR 0039 was blocked on ADR 0041.
- Two 2FA kinds (TOTP, WebAuthn) now share one "has 2FA" gate in `login.rs`, growing that module's branch count and its test matrix (both-enrolled, either-only, neither).

### Risks
- **Whether `webauthn-rs` exposes a substitution seam for ES256 verification is unresolved** (point 7, **U**); either answer keeps `p256` inside `rizzy-core` only, so ADR 0059's audit scope needs only to record which path — `rizzy-core`'s `verify_es256` or `webauthn-rs`'s own — actually verifies assertions, not reopen where `p256` is declared.
- **Authenticators with a genuinely broken counter** (firmware bugs, not cloning) could trip the clone signal; mitigation is open question 4 (flag, do not auto-disable).
- **A second-factor-pending row that is never claimed** is a new kind of short-lived server state alongside `SERVER_LOGIN_STATE`; `maintenance`'s existing expired-state sweep (CRYPTO.md §5.11 "Rotation") must be extended to it.

## Alternatives considered

- **Hand-roll the ceremony ourselves**, as ADR 0039 did for its small fixed CBOR subset. Rejected: a security key's attestation statement format varies by vendor and is adversary-supplied, unlike ADR 0039's own encoder output; the WebAuthn spec's origin-confusion pitfalls are a well-known source of RP implementation bugs that an established crate already gets right.
- **Reuse an ADR 0039 vault-stored passkey as the server 2FA credential.** Rejected: circular trust boundary — a vault passkey only exists behind an unlocked vault, but a server 2FA key must work to let the user authenticate in the first place (the vault is not yet unlocked at that point).
- **Skip clone detection, fix the counter at 0 like ADR 0039.** Rejected for this feature: ADR 0039's credentials are software, synced by us, so a real counter would be meaningless; a hardware security key here is a "cannot be remotely cloned without physical access" value proposition, and discarding its counter throws that value away for no cost saved.
- **Put `allowCredentials` in `LoginStartResponse`**, before KE3. Rejected: leaks which accounts (and which credential ids) use WebAuthn 2FA to anyone who knows a login name, without proving the password — a new pre-auth enumeration channel §5.9 does not accept.

## Open questions for the owner

1. **Approve `webauthn-rs` with the ADR 0009/Q-14 pre-approved `openssl` exception, with its checklist run properly in [ADR 0059](0059-webauthn-rs-crate-approval.md).** *Recommendation:* approve; the exception's shape was already decided 2026-09-25, and no viable `openssl`-free alternative was found then.
2. **Does `webauthn-rs` expose a seam to substitute `rizzy-core`'s `verify_es256` for its own ES256 verification (point 7)?** *Recommendation:* ADR 0059 checks this during its crate review; if yes, add the entry point and use it; if no, add nothing and accept the crate's own verification within the already-scoped exception — either way, without taking `p256` as a direct dependency of `rizzy-domain-auth`/`rizzy-server`.
3. **Accept any attestation statement format on receipt, without verifying it (point 2)?** *Recommendation:* yes; we hold no attestation CA trust store to check one against, and refusing a security key that attests despite our `"none"` preference would reject legitimate hardware for no security benefit.
4. **Clone-signal response.** *Recommendation:* flag the account's security event log and notify, do not auto-disable the credential — an authenticator firmware bug should not lock a user out, and the user can remove the credential themselves once notified.
5. **Who writes CRYPTO.md §11.16 (point 9), and when?** *Recommendation:* the PR that accepts this ADR, mirroring how ADR 0003's acceptance fixed its own CRYPTO.md §5.1–§5.9 text inline; implementation waits for it, per the ADR-gate rule.
