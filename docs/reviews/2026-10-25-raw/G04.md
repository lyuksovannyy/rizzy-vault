### G04-5 [major] "Run `import` where it can be killed, a Web Worker" conflicts with ADR 0013's single-instance rule and the claim that the importer runs in the vault's wasm instance
- Type: B

## ADR 0034 — Re-authentication before every export and a hold before plaintext export (Partially superseded by 0074)
- Verdict: 1 finding

### G04-12 [minor] "An OPAQUE login" as the export re-authentication does not say when it counts as verified (second factor), or what becomes of the extra session it creates
- Type: B
- Where: docs/adr/0034-export-reauth-and-plaintext-hold.md §Decision 1–2 (lines 17–18); crates/rizzy-client/src/export/gate.rs lines 21–23
- Evidence: line 17: "an OPAQUE login of the session's account with the master password and the Secret Key, over the device session … `ExportGate` accepts it only if the account the login verified is the session's". gate.rs: "It runs the OPAQUE login itself (it owns the transport) and, once the login verified, calls [`ExportGate::accept_reauth`]".

## ADR 0036 — Browser extension: architecture and key custody (Partially superseded by 0040, 0043, 0076)
- Verdict: 3 findings

### G04-13 [major] The `storage.session` fallback cannot be built as decided: an acceptance precondition was never met, the snapshot has no defined content or format, and Chromium's offscreen document has no `storage`
- Type: A
- Where: docs/adr/0036-browser-extension-architecture-and-key-custody.md §2 (line 45); docs/adr/0013-shared-client-core.md line 80; apps/extension/README.md lines 211–232 and 266–273; apps/extension/src/core-host/core-context.ts lines 94–100
- Evidence: 0036 line 45: "**Confirming survival (M2 spike, required before this ADR can be Accepted as written).** … the extension restores unlocked state from `storage.session`". core-context.ts: "`DurableSession` has no "resume from an opaque snapshot" constructor yet … (`not_done`, tracked honestly rather than faked)".
- Why it is a gap: the ADR was accepted with its own precondition open. The README records a 6-minute Chromium soak only, with "longer soaks (hours), real memory pressure, and Firefox" unmeasured. - Suggested resolution: Record the spike results. Then either drop the fallback (a torn-down context means "locked", which the current code already does) or specify the snapshot fully: its contents, a wrap under a per-session key held outside `storage.session`, a version byte, which context writes it on Chromium, and the Firefox access-level check.

## ADR 0037 — URL matching and autofill rules (Accepted)
- Verdict: 3 findings

### G04-16 [major] *Regex* mode (an M2 Must) names no engine, dialect, match semantics or limits, so it is unbuilt
- Type: B
- Where: docs/adr/0037-url-matching-and-autofill-rules.md §4 row `0x0005` (line 58), owner answers (line 86); crates/rizzy-match/src/modes.rs lines 100–103; docs/ROADMAP.md line 130; docs/HANDOFF.md line 319 (gap 29)
- Evidence: line 58: "The URI's `value` is a user-authored regular expression; it matches when it matches the page's full normalised URL **and** the registrable-domain check passes first". modes.rs: "No regex crate is named by ADR 0037; this build implements Never/Exact/Host/`StartsWith`/`BaseDomain` only."
- Why it is a gap: the ADR leaves open the syntax (Rust `regex` vs ECMAScript, which differ on look-around and backreferences), whether "matches" means a full match or a search, case sensitivity, the pattern's size and complexity caps (patterns sync from other devices, and in M9 from vault members, so they are untrusted input under CLAUDE.md), and what an item with an invalid pattern does. Two implementers will disagree, and today the M2 Must row is met by a `NotSupported` stub.
- Fix route: new Proposed ADR superseding ADR 0037 §4 (row `0x0005`) in part
- Suggested resolution: Name the engine (a linear-time engine such as `regex`/`regex-lite` with `size_limit`). Define search vs full match, case rules, a pattern length cap below ADR 0018's 64 KiB value cap, and "invalid or over-limit pattern = never matches, flagged in the editor". Add a fuzz target.

### G04-17 [major] §2 point 6 (path and query kept only for *Starts with* and *Regex*) contradicts §4's *Exact* "full normalised URL", and the code follows neither reading for the query
- Type: C
- Where: docs/adr/0037-url-matching-and-autofill-rules.md §2 point 6 (line 34), §2 output (line 37), §4 rows `0x0003`/`0x0004` (lines 56–57); crates/rizzy-match/src/normalize.rs lines 85–88
- Evidence: line 34: "**Path and query.** Dropped for every mode except *Starts with* (keeps the path prefix) and *Regex* (matches against the full normalised URL, scheme and all". normalize.rs: "Query and fragment are dropped unconditionally, for every mode, including *Regex* (ADR 0037 §2 point 6: the full *normalised* URL, which never carries a query)."
- Why it is a gap: read literally, point 6 drops the path for *Exact*, which turns *Exact* into "same scheme, host and port". That is wider than *Starts with*, against INV-38's ordering intent. Point 6 also implies the query is kept for *Starts with*/*Regex*. The code keeps the path for *Exact* and drops the query everywhere. Each reading gives different candidates on real sites (`/login?next=…`), and a second client implementation could pick another.
- Fix route: erratum ADR
- Suggested resolution: State per mode exactly which components enter the compared string (scheme, host, port, path, query, fragment). Make the code's current behaviour the text if the owner agrees, and add vectors for `/login?x=1` under *Exact*, *Starts with* and *Regex*.

### G04-18 [minor] Registrable domain for IP-literal and single-label hosts is decided only in code
- Type: B
- Where: docs/adr/0037-url-matching-and-autofill-rules.md §2 point 7 (line 35); crates/rizzy-match/src/normalize.rs lines 77–83
- Evidence: line 35: "**Registrable domain (eTLD+1).** Computed from the IDNA A-label host against the compiled-in PSL snapshot". normalize.rs: "An IP-literal host (`192.168.1.1`, `::1`) is never run through the PSL at all … An unqualified single-label hostname … (`localhost`, a bare internal hostname) is treated the same way".
- Why it is a gap: a literal reading of point 7 runs `192.168.1.1` through the PSL's unlisted-TLD fallback. *Base domain* then over-matches every address sharing the last two octets, and self-hosters fill on LAN IPs often. The safe rule exists only in a code comment, so a second client or a rewrite has no binding text to follow.
- Fix route: erratum ADR
- Suggested resolution: Add to §2 point 7: IP literals (all WHATWG notations) and single-label hosts are their own registrable domain, take part in no equivalence group (ADR 0044 already refuses them as members), and *Base domain* on them equals *Host*.

## ADR 0038 — Equivalent-domain list: format, signing and governance (Partially superseded by 0044, 0080)
- Verdict: 1 finding (the equal-version defect of §2 is already superseded by ADR 0080 and fixed in INV-39; the unsigned `list_version 1` is HANDOFF gap 26 and is not re-reported)

### G04-19 [minor] The global list's decode caps exist only in code, so a validly signed list can be refused by every client
- Type: B
- Where: docs/adr/0038-equivalent-domain-list.md §1 (lines 25–41); crates/rizzy-match/src/error.rs lines 82–86
- Evidence: §1: "`u16 n ‖ n × group` … `u16 m ‖ m × str(domain)` registrable domains in the group, 2 ≤ m". error.rs: "`pub const MAX_LIST_LEN: usize = 1 << 20;` … `MAX_GROUPS: u16 = 4096;` … `MAX_GROUP_DOMAINS: u16 = 64;`".
- Why it is a gap: the signed format sets only a lower bound on `m`. The client refuses a list above caps that no ADR states. If the offline signing tool (`cargo xtask equivalence-list`) and the client ever disagree, the owner signs a list that every client rejects, and every account silently runs with no global groups (the failure mode ADR 0080 had to fix for equal versions). Per CLAUDE.md, untrusted/format input limits belong in the ADR.
- Fix route: erratum ADR
- Suggested resolution: Write the three caps (1 MiB, 4,096 groups, 64 domains per group) into ADR 0038 §1 as format rules, and require the signing tool to refuse to sign a list that the client decoder would refuse.

## ADR 0039 — Passkeys in the vault and in the browser extension (Accepted)
- Verdict: 2 findings

### G04-20 [major] `UV=1` on every assertion because "the unlock already authenticated the user", with no per-ceremony verification and no recorded residual
- Type: E
- Where: docs/adr/0039-passkeys-vault-and-extension.md §2 "User verification and presence" (line 51); docs/THREAT_MODEL.md lines 460–470 (Passkey provider) and line 1220 (INV-64)
- Evidence: line 51: "`authenticatorData` flags are set `UP=1` (user present: the gesture), `UV=1` (user verified: the unlock already authenticated the user)".
- Why it is a gap: an RP that asks `userVerification: "required"` for a step-up (payment, account recovery) treats UV as "the user proved identity for this ceremony". The extension asserts that on a single click while the vault is merely unlocked, which may be up to the auto-lock timeout (15 min default, user-configurable) after the last password entry, at an unattended browser. ADR 0034 handles the analogous export threat with a fresh re-authentication. Here THREAT_MODEL's passkey section and INV-64 address only origin/rpId binding and name neither a mitigation (re-prompt when UV is required, or a freshness window) nor an accepted residual. Its "Verified by" has no UV test.
- Fix route: owner question
- Suggested resolution: Either require a fresh master-password (or keystore) re-prompt when the request has `userVerification: "required"` and the last unlock is older than N minutes, or record the behaviour as an accepted residual (a new AR) in THREAT_MODEL with its reasoning. In either case add a test to INV-64's "Verified by".

### G04-21 [minor] §1 sends the concealed-by-default rule for `passkey/<id>/private_key` to "On acceptance", which says ADR 0018 is not edited; field caps exist only in code
- Type: D
- Where: docs/adr/0039-passkeys-vault-and-extension.md §1 table (lines 37–39), §"On acceptance" item 3 (line 133); crates/rizzy-core/src/item/schema.rs lines 63, 367, 372
- Evidence: line 39: "concealed by default like `login.password` ([ADR 0018] §7's concealed-by-default list gains this key, see [On acceptance](#on-acceptance))". On acceptance item 3: "**[ADR 0018]** is **not** edited … Its §7 … stay[s] as written".
- Why it is a gap: the link leads to text that does the opposite, so the only binding statement that this private key is concealed (not shown in list views, left out of an M5 share unless chosen) is the parenthesis itself. Readers of ADR 0018 §7's list (the M5 share and M9 member code) will not find it there. The ADR also gives the user handle cap only as "≤ 64 bytes … (**L**)" and no cap for `credential_id` and `rp_id`. The code chose 64 and 1,024 (`schema.rs:367,372`), and ADR 0074's CXF import depends on them.
- Fix route: erratum ADR
- Suggested resolution: State in one binding place (an erratum, or the next ADR touching ADR 0018 §7) that the concealed-by-default list includes `passkey/<id>/private_key`, and write down the field caps (user handle 64, credential id 1,024, rp_id 253) that the code uses.

## ADR 0040 — The extension's fill request comes from the inline menu, not the content script (Partially superseded by 0043, 0076)
- Verdict: 1 finding

### G04-22 [minor] Point 4 sends decrypted values to "the content script" of the tab, not to the document whose URL was just matched
- Type: B
- Where: docs/adr/0040-extension-fill-request-from-inline-menu.md point 3–4 (lines 22–23); apps/extension/src/core-host/content-handler.ts lines 89–95
- Evidence: line 23: "**Values still go only to the content script, at fill time,** which performs the DOM write". content-handler.ts: "`await ext.tabs.sendMessage(tabId, { type: "apply_fill", values } …)`" (no `frameId`/`documentId`).
- Why it is a gap: point 3 re-runs the matcher for "the browser-vouched top-frame URL of the sender's tab". Point 4 then delivers to whichever document the tab holds when the message lands. If the tab navigates between the two steps, the values reach the new document's content script. Ours drops them (`activeFillTargets` is per document, content-script.ts:71–83). A compromised content script, the attacker ADR 0040 exists for (Context, line 12), would get a matched item's password on a page it did not match. The ADR states no binding between the checked URL and the receiving document.
- Fix route: new Proposed ADR superseding ADR 0040 point 4 (in part)
- Suggested resolution: Require the push to target the exact document that was matched (`tabs.sendMessage` with `frameId: 0` and `documentId` captured when the sender's tab URL was read, where the browser supports it; otherwise re-read the tab URL right before sending and refuse on change). Add a navigation-race e2e test.
