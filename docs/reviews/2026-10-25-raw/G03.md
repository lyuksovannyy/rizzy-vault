- Type: A

### G03-2 [major] Client TLS policy for the native binding leaves and the Apple/Android hosts is decided nowhere
- Type: B
- Where: docs/adr/0019-native-clients.md §5 table row "HTTP and TLS" (line 413) and line 427; docs/adr/0030-client-tls-rv.md line 1 and line 59; docs/CRYPTO.md line 109
- Evidence: 0019: "The same Rust HTTP client as `rv` (chosen in M1, rustls only …)" … "Self-hosted servers with private CAs must still be reachable." ADR 0030's title is "Client-side TLS for `rv`", and its platform-verifier alternative is "Better suited to the M3 desktop bindings."
- Why it is a gap: ADR 0030 (and CRYPTO.md's "Transport (`rv`)" row) scope TLS 1.3, roots and the private-CA file to `rizzy-cli` only. For `rizzy-ffi`/`rizzy-ffi-cpp` (Windows, Linux) and for the URLSession/OkHttp hosts on macOS (M3), iOS and Android, nothing fixes the minimum TLS version, the root store (webpki-roots vs OS store vs platform verifier), how a private CA is configured, or whether the host may relax verification. ADR 0030 itself says TLS is "the only server authentication on the everyday path", so two implementers would build materially different trust boundaries.
- Fix route: new Proposed ADR superseding ADR 0030 Decision 1 (scope) in part
- Suggested resolution: One ADR for client TLS on every native client: TLS 1.3 floor, which root store per platform, private-CA configuration through the core (never a host toggle), and a CI check that host code never installs a custom trust-all delegate.

### G03-3 [major] The safe-Rust image decode in the binding leaf has no size limit and no decoder choice
- Type: B
- Where: docs/adr/0019-native-clients.md §5.1 first bullet (line 433); docs/THREAT_MODEL.md line 940 (§7.3 T row) and line 957 (§7.4)
- Evidence: "Hosts receive raw pixels of bounded dimensions (the limit is set in M3) …" … "The decoder crate goes through dependency review like any dependency with a security surface (chosen in M3, U)."
- Why it is a gap: Favicons arrive from the `icons` role in M3 and the macOS client is M3, yet no ADR sets the byte cap, the maximum width/height or pixel count, the accepted formats, the output pixel format, or the refusal behaviour; ADR 0052's limits (INV-76) bind only the server-side fetcher, and §5.1 says a malicious server skips that re-encoding. The decoder is untrusted-input parsing next to the keys (CLAUDE.md requires a size limit and a fuzz target), and the binding API shape depends on it.
- Fix route: new Proposed ADR (client image decoding in the binding leaves)
- Suggested resolution: Fix the input cap, the dimension/pixel cap, the formats (e.g. PNG/ICO only), the decoder crate with an ADR 0009-style record, the RGBA8 output shape and a fuzz target before `rizzy-ffi` exposes icons.

### G03-6 [major] The 2 GiB backup cap is below what one account may store, and the promised revisit never happened
- Type: C
- Where: docs/adr/0023-logical-backup-format.md §3 (line 50), Risks (line 97), open question 2 (line 110); docs/adr/0048-per-account-storage-quota.md line 68; docs/adr/0054-attachments-envelope-and-api.md line 116; docs/self-hosting.md line 376
- Evidence: 0023: "A future table with a very large column (M3 attachments) may exceed the value or file limits: that ADR must revisit §3." 0054: "inflating `rizzy-vault backup`/`restore` size and time … Accepted for M3; revisit before M8".
- Why it is a gap: ADR 0048 sets the per-account quota default to 5 GiB and ADR 0054 stores attachment bytes as database rows, so a single account at the default quota can make the whole instance's dump exceed the 2 GiB cap, and `backup` then refuses to write. That disables the only restore path that opens INV-59's reconciliation epoch. ADR 0054 acknowledged the growth but did not revisit §3, as ADR 0023 required, and no ADR raises the cap or adds a streaming reader.
- Fix route: new Proposed ADR superseding ADR 0023 §3 (and ADR 0048 point 1 if the default changes)
- Suggested resolution: Decide before M3 ships attachments: a streaming reader/writer with a larger cap, or an instance-wide quota sum capped below the backup limit, or a server warning and refusal of writes that would make the dump unrestorable. Reference the choice from INV-59's "Verified by".

### G03-8 [major] Windows and macOS have no core-dump/crash-report mechanism, though `rv` ships on Windows in M1
- Type: E
- Where: docs/adr/0024-core-dump-disabling-rustix.md Decision 3 (line 18); crates/rizzy-cli/src/coredump.rs lines 152–155; docs/THREAT_MODEL.md line 1248 (INV-60) and line 1327 (AR-28); docs/rv.md line 20
- Evidence: 0024: "Windows has neither call in rustix; its dumps stay AR-28 until M3 confirms a mechanism (U)." Code: `#[cfg(not(unix))] pub(crate) fn disable() -> Result<(), CoreDumpError> { Ok(()) }`
- Why it is a gap: INV-60 says every native process, `rv` included, disables core dumps at startup, and `rv` is supported on Windows today (docs/rv.md lists `%LOCALAPPDATA%\rizzy-vault`), but on Windows it does nothing and reports success. AR-28 covers only "a native client" (M3/M7), so the M1 `rv` on Windows (WER, LocalDumps) is neither mitigated nor an accepted risk. For macOS, which ships in M3, the crash-report opt-out is still "mechanism to confirm in M3, U" (INV-60), and no ADR has confirmed it. INV-60's "Verified by" has no Windows or macOS test.
- Fix route: new Proposed ADR superseding ADR 0024 Decision 3 in part
- Suggested resolution: Choose the Windows mechanism (for example `WerAddExcludedApplication` / `SetErrorMode` through a vetted safe wrapper, or an explicit accepted risk) and the macOS one. Until then, widen AR-28 to name `rv` on Windows and macOS explicitly, and add a per-OS test to INV-60's "Verified by".

### G03-9 [major] A large account cannot rotate keys, so it cannot revoke a stolen device or finish recovery, and the refusal is undefined
- Type: B
- Where: docs/adr/0025-rotation-vault-half.md §1 (lines 23, 25), Risks (line 89); crates/rizzy-domain-vault/src/rotation.rs lines 49–51; crates/rizzy-proto/src/limits.rs:129 (`MAX_OWNED_VAULTS` = 64), :152, :228
- Evidence: 0025: "Vaults above `MAX_ITEM_KEY_WRAPS` rows cannot rotate in M1 (their Fetch already fails with `WrapSetTooLarge`)." Code: "the rotation is refused as `invalid_request` (ADR 0025 "Risks")."
- Why it is a gap: The rotation is one atomic request with all vaults' re-wraps (one `VaultRotation` per vault, now up to 64 owned vaults under ADR 0081). The ADR's own estimate is about 290 bytes per wrap, so the 32 MiB default body limit is reached at roughly 115,000 wraps across all vaults, well below 64 × 65,536. Neither case has a defined error code, client behaviour or user message. The ADR names no cap at write time either, so the server lets a vault grow past the point where it can rotate. Rotation is how a stolen device is revoked (§11.8) and how recovery finishes (§11.9), so the failure is a security failure, not only an availability one.
- Fix route: new Proposed ADR superseding ADR 0025 §1 in part
- Suggested resolution: Either refuse new item creation before a vault or account reaches the rotatable limit (a defined code such as `rotation_limit`), or specify a multi-request rotation that keeps §11.6 step 9 atomic (staged re-wraps committed with the state CAS). Define the client's message and add a test at the limit.

### G03-12 [major] What an export does with attachments is undefined
- Type: B
- Where: docs/adr/0027-export-payload.md §1 "What is exported" (line 31), §2 step 3 (line 41), §3 (line 63); docs/adr/0054-attachments-envelope-and-api.md §4 (lines 43–50); crates/rizzy-client/src/vaults.rs lines 597 and 622
- Evidence: 0027: "with its registers and history exactly as the merge holds them, unknown keys and unsupported values included". 0054: "No `attachment/<id>/wrap` field exists: the wrap travels only through `attachments/get` (§6), never through item data".
- Why it is a gap: Since M3 (ADR 0054) an item carries `attachment/<id>/name|mime|size|order` registers, while the content and its key live only on the server. Under §1 and §3 these registers are exported, and under §2 step 3 they are imported byte for byte into a new item. The new item then lists attachments whose blobs and wraps do not exist, and the user silently loses the attachment content in an export the ADR calls portable. No Accepted ADR decides whether exports include attachment content (which the 16 MiB cap could not hold), strip the metadata, or report the loss. The copy path of ADR 0081 strips `attachment/` fields and re-uploads (vaults.rs:597, :622), which shows the problem is real; the export code has no attachment handling (grep of `crates/rizzy-client/src/export*`: no match).
- Fix route: new Proposed ADR superseding ADR 0027 §1, §2 step 3 and §3 in part
- Suggested resolution: Decide for M3: either strip `attachment/` registers on export and import, counted in the report and named in the warning, or define an attachment-carrying export container (a new payload version, chunked, with its own cap). Say the same for CSV.

## Summary

- Findings: 13. Blocker: 0. Major: 9 (G03-1, -2, -3, -6, -8, -9, -10, -12, -13). Minor: 4 (G03-4, -5, -7, -11).
- Top 5 by importance:
  1. **G03-9** (ADR 0025): rotation is one request bounded by `MAX_ITEM_KEY_WRAPS` per vault and the 32 MiB body limit across all vaults, with no write-time cap and no defined refusal. A large account cannot revoke a stolen device or finish recovery.
  2. **G03-8** (ADR 0024): `rv` on Windows disables nothing (`disable()` returns `Ok(())`) while INV-60 claims every native process does, and AR-28 does not cover `rv`. macOS's mechanism is unconfirmed for M3.
  3. **G03-10** (ADR 0026): owner answers 5/6, recorded only in a commit message, contradict §3/§4 step 1/§5. The code persists alarm byte 4 and allows removal under it with no binding text.
  4. **G03-12** (ADR 0027 × 0054): exports carry attachment metadata without content or keys, so import creates dangling attachments and loses data silently. No ADR decides it.
  5. **G03-2** (ADR 0019): no Accepted ADR fixes client TLS (version floor, root store, private CA) for `rizzy-ffi`/`rizzy-ffi-cpp` or the Apple/Android hosts. ADR 0030 is `rv`-only, and macOS ships in M3.

## Unverified suspicions

- `RecoveryCompleteResponse` returns every vault's wraps in one response (ADR 0025 §1). I did not check whether the client enforces a response-size limit that matches the server's, or what happens past `WrapSetTooLarge` on that path.
- TOTP login codes cross the wasm binding as `&str` (crates/rizzy-wasm/src/login.rs:267, device.rs:274), while ADR 0019 §3 says secrets cross as bytes. A TOTP code is not one of ADR 0013 rule 2's named exceptions, so this may be intended; not judged.
- `apps/extension/src/cache/stores.ts:31` declares `CACHE_FORMAT_VERSION = 1` "mirrored from ADR 0026 §5" while the shared core migrates `cache_meta.format` to 4; the constant appears unused (one grep), so this is likely only a stale comment.
- ADR 0019 §12's Windows release-manifest format is "not yet specified" (CRYPTO.md line 883). It is gated "before the Windows client ships", so I did not count it as a gap.
- ADR 0019 §4.5's C++ secrets module leaves "how to do that under Qt's implicit sharing … settled in M3 (U)". The Linux client is not in M3 (owner decision 12), so I did not count it as a gap.
- ADR 0019 §7–§9 artifacts (allowed-signers file, revocation denylist, compatibility matrix, release workflow with `git verify-tag`) do not exist yet (`.github/workflows` holds only ci.yml and fuzz.yml). I did not check whether any M3 macOS release is close enough to make this a gap.
