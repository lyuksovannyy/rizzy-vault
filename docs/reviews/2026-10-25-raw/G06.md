## ADR 0054 — Encrypted attachments: chunk layout, storage shape and upload/download API (Accepted)
- Verdict: 5 findings

### G06-1 [major] Purging an item (and ADR 0081's move) has no attachment-cleanup rule, so blobs and quota leak deterministically
- Type: B
- Where: docs/adr/0054-attachments-envelope-and-api.md §7 (line 83); docs/adr/0012-sync-engine.md §5 (lines 115–117); docs/adr/0081-multiple-vaults-personal-and-shared.md §A6 step 2 (line 149)
- Evidence: 0054 §7: "`attachments/delete` removes both tables' rows … the GC sweep below does the same" (sweep only covers rows "still short of `chunk_count`"); 0081: "a `Trash` op and a `Purge` op on the source item in one upload".
- Why it is a gap: Only clients purge (ADR 0012 §5, the server cannot see lifecycle), and no binding text says a client MUST call `attachments/delete` for an item's attachments when it purges the item (manual or 30-day auto-purge) or after a move's source purge. Owner answer 3 accepts orphans from "a client that skips `delete`", but here no rule tells the client to call it at all, so every purge of an item with attachments, and every 0081 move, leaves complete blobs billing the ADR 0048 quota forever (code check: `crates/rizzy-cli/src/device/vaults.rs` `move_item` trashes and purges the source and never sends `attachments/delete`; `crates/rizzy-client/src/items.rs` `purge_item` has no attachment handling).
- Fix route: new Proposed ADR superseding ADR 0054 §7 (in part)
- Suggested resolution: State that the purging client (including the auto-purger and the 0081 move) MUST delete each `attachment/<id>` of the item via `attachments/delete` after the Purge op is acknowledged, with `not_found` treated as success and crash-resume via the existing pending-move/pending-op rows; add a test.

### G06-2 [major] Export/import says nothing about attachments: an export keeps `attachment/<id>/…` fields but loses the contents
- Type: A
- Where: docs/adr/0054-attachments-envelope-and-api.md (no occurrence of "export"); docs/adr/0027-export-payload.md line 15
- Evidence: 0027: "An export … is a user-level portability file: the items of a vault as one client sees them"; `grep -ci attach docs/adr/0027*.md` = 0.
- Why it is a gap: ADR 0054 adds a new kind of user data that the only user-level portability path (ADR 0027, plus 0074) neither includes nor excludes. Two implementers will differ (embed blobs, drop the fields, or keep dangling fields). The code exports item registers only (`crates/rizzy-client/src/export*` has no attachment handling), so an imported copy carries attachment references to ids that do not exist in the new account, and the user silently loses the files.
- Fix route: owner question
- Suggested resolution: Decide whether exports carry attachments (and the size limit on the export file if so), or explicitly drop `attachment/` fields with a user-visible warning; record it in a Proposed ADR superseding ADR 0027 §1 in part.

### G06-3 [major] ADR 0023's 2 GiB backup reader limit was handed to this ADR and never revisited; the default quota makes it reachable by one account
- Type: A
- Where: docs/adr/0023-logical-backup-format.md lines 97 and 110; docs/adr/0054-attachments-envelope-and-api.md Consequences "Backup growth" (line 116); docs/adr/0048-per-account-storage-quota.md line 30
- Evidence: 0023: "A future table with a very large column (M3 attachments) may exceed the value or file limits: that ADR must revisit §3." / OQ 2: "the attachments ADR (M3) revisits it."
- Why it is a gap: ADR 0054 never cites ADR 0023 (0 matches) and only says dump size is "Accepted for M3; revisit before M8". With attachments stored as DB rows and `RIZZY_ACCOUNT_QUOTA_BYTES` defaulting to 5 GiB, a single account can push the dump past `MAX_BACKUP_FILE_LEN` = 2 GiB, after which `backup` refuses to write (ADR 0023 §3, line 50: "`backup` refuses to write a file longer than the reader's limit"; the M8 container keeps the same cap, `crates/rizzy-server/src/db_backup.rs` line 66), so the instance can no longer be backed up.
- Fix route: owner question
- Suggested resolution: Either raise or stream the reader limit in a Proposed ADR superseding ADR 0023 §3 (and ADR 0071 where it relies on it), or cap the default quota or total attachment bytes below the backup limit; until then, document the interaction in the operator docs.

- Why it is a gap: No ROADMAP row or ADR schedules it (grep "reconcil" finds only ADR 0054), and the five endpoints of §6 have no "list my attachments", which such a sweep needs, so the deferral has no owner and no route.

### G06-5 [minor] Zero-length attachments are neither allowed nor refused
- Type: B
- Where: docs/adr/0054-attachments-envelope-and-api.md §1–§2 (lines 33, 37), INV-79 (line 89)
- Evidence: "The client derives it from `attachment/<id>/size` … as `ceil(size / CHUNK_SIZE)`"
- Why it is a gap: For `size = 0`, `chunk_count` = 0, which yields an attachment with no chunks and no AEAD over any content; the ADR does not say whether `create` accepts it, whether the §7 sweep or INV-79 treat it as complete, or what download returns. The code allows it ("zero for an empty attachment", `crates/rizzy-core/src/attachment.rs` line 139), so another implementer that refuses it would be incompatible.
- Fix route: erratum ADR
- Suggested resolution: State explicitly whether `total_plaintext_len = 0` is valid (and that it is then complete with zero chunks) or is `invalid_request`.

### G06-9 [minor] No rule for a record whose OS keystore entry has been invalidated (`has_ks = 1` but the secret is gone)
- Type: B
- Where: docs/adr/0057-device-state-v2-keystore.md §2 "Lifecycle" (line 60) and "Context, not shape" (line 55); docs/CRYPTO.md §4.2 line 178; docs/THREAT_MODEL.md INV-62 line 1269
- Evidence: CRYPTO.md: the secret is deleted "On biometric-enrolment change, re-enrolment, or when the user turns keystore unlock off (then `E_ks` is deleted)"; 0057: "that lookup is host-side and out of this ADR's scope."
- Why it is a gap: Only the user-initiated "turn off" deletes `E_ks` from the record. When the OS invalidates the keystore item (biometric change, INV-62), the record still says `has_ks = 1`. The ADR does not say whether the client then clears `[ks]` (and writes the record), keeps offering a keystore unlock that always fails, or how the host tells "secret gone" from "user cancelled the prompt". Hosts on three platforms (macOS/iOS/Android `rizzy-ffi`) will each handle it differently.
- Fix route: erratum ADR
- Suggested resolution: Define a host signal "keystore entry missing or invalidated", and on it have `rizzy-client` clear `has_ks`/`[ks]` (leaving the forward chain, as §2 already requires) and fall back to the password unlock; add a test.

### G06-18 [major] Reconnect, missed-signal and polling behaviour are not specified
- Type: B
- Where: docs/adr/0061-notify-websocket-protocol.md §2–§3 (lines 43–66)
- Evidence: "A client that receives a frame does exactly what a background refresh already does — Fetch and verify (ADR 0012 §7) — and never trusts the frame's claim."
- Why it is a gap: Frames are lost while a socket is down (30 s revalidation close, 4002 eviction, network change, `notify` restart, profile C `LISTEN/NOTIFY` loss). The draft does not say whether a client must Fetch on every (re)connect, whether it keeps polling and at what interval, or what reconnect backoff and jitter it uses after 4001/4002/429. Without these, clients either miss updates silently or create reconnect storms against `notify`.
- Fix route: edit the Proposed ADR
- Suggested resolution: Require a full Fetch immediately after every successful authentication, keep a (longer) background poll as a safety net, and fix the reconnect backoff (e.g. exponential with jitter, no reconnect after 4001 until the session is renewed).

### G06-19 [minor] Event routing is per uploading account only, which cannot wake other members of an ADR 0081 Part B shared vault
- Type: B
- Where: docs/adr/0061-notify-websocket-protocol.md §3 "Event source" (line 64); docs/adr/0081-multiple-vaults-personal-and-shared.md Part B (M9)
- Evidence: "`OpStored { account, vault }` … `Event::account()` (line 157) already reads the account id off any of them; `notify` turns each straight into the frame above with no further logic."
- Why it is a gap: Routing by `Event::account()` delivers `scope: "vault"` frames only to the account that wrote the op. - Why it is a gap: THREAT_MODEL §7.8's D threat is connection exhaustion, but the only cap is per account and applies after authentication. Anyone can open unlimited upgraded sockets and hold each for 5 s. ADR 0028's `rate_limited` machinery is not cited for `GET /api/v1/notify`, and the draft sets no per-IP or global pre-auth limit, so `notify` can be exhausted without any credential.
- Fix route: edit the Proposed ADR
- Suggested resolution: Add a global and a per-client-address cap on sockets still waiting for the auth frame (refused with `429` before the upgrade), and apply the existing request rate limit to the upgrade request.

## ADR 0062 — Markdown-in-notes rendering: sanitization and rendering rules (Accepted)
Checked: INV-88 (THREAT_MODEL.md line 1256) and the A16 sentence (line 709) are in place; the implementation is `apps/web/src/markdown.ts` + `views/NoteMarkdown.tsx` with e2e `markdown-note.spec.ts` / `attack/markdown-allow-list.ts`, matching §3–§4 and INV-88's "Verified by". `MAX_NOTE_RENDER_LENGTH = 65_536` matches §10 / ADR 0018 §10.
- Verdict: 1 finding

### G06-21 [minor] §11 says an unrecognised construct makes the whole note plain text, while §5 says it becomes a literal text node in place
- Type: B
- Where: docs/adr/0062-markdown-notes-sanitization.md §5 (line 26), §11 (line 47); apps/web/src/markdown.ts lines 32–34, 42–44
- Evidence: §11: "Any exception, or any construct the tokenizer does not recognize, falls back to one plain text node holding the original stored string"; §5: "anything else in the source is a literal text node".
- Why it is a gap: Read literally, §11 means one `[text](url)` or table anywhere turns the whole note into a single unformatted node, while §5 (and the code: "Everything else … has no production rule and is literal text"; whole-note fallback only on length or exception) means in-place literal text. - Fix route: erratum ADR
- Suggested resolution: Restate §11 as "any exception, or an input over the length cap, falls back to one plain text node; an unrecognised construct is literal text in place (§5)", which is what the code does.

An M5 share built from it would include private keys and old passwords by default.
