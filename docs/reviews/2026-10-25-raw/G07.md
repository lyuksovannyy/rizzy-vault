## ADR 0066 — Recipient email verification by one-time code (Proposed)
- Verdict: 7 findings

### G07-1 [major] SMTP password in `RIZZY_SMTP_URL` contradicts Accepted ADR 0060 answer 2 / INV-86 (sealed at rest under 0x0103)
- Type: C
- Where: docs/adr/0066-share-email-otp-verification.md "What this ADR supersedes" (line 55); docs/adr/0060-admin-panel-stack-boundary.md line 134; docs/THREAT_MODEL.md line 1255 (INV-86); docs/adr/0086-instance-settings-persistence.md lines 186, 196
- Evidence: 0066 l.55: "Two settings can carry a secret: `RIZZY_DATABASE_URL` … and `RIZZY_SMTP_URL` (… with an optional user and password)". 0060 l.134: "Yes, SMTP credentials reuse Algorithm 0x01 under the server-only purpose `0x0103` (INV-86)."
- Why it is a gap: Accepted ADR 0060 and INV-86 make the SMTP password a sealed DB value managed in the admin panel; ADR 0066 puts the same password unsealed in the environment/config file and widens ADR 0028 item 12's secret boundary for it. Accepting 0066 as drafted would give two SMTP credential sources with different protection, and ADR 0086 (Proposed) already flags this (open question 4) without either ADR resolving it.
- Fix route: edit the Proposed ADR
- Suggested resolution: Revise 0066 before acceptance to read the SMTP relay and From address from ADR 0086's settings rows (sealed under 0x0103) and drop the ADR 0028 item 12 secret-boundary supersession; or, if the owner wants env configuration, say explicitly which source wins and amend INV-86 through its own ADR.

### G07-2 [major] Delivery retry schedule outlives the code's 15-minute lifetime
- Type: B
- Where: docs/adr/0066-share-email-otp-verification.md §3 (line 40), §1 (line 26)
- Evidence: l.40: "on failure it retries with backoff (1, 5, 15, 30, 60 min, 5 tries), then deletes the row … It also deletes any row past `expires_at` regardless of `sent_at`". l.26: "these rows expire within 15 minutes".
- Why it is a gap: Retries at +15/+30/+60 min (cumulative 21, 51, 111 min) can never happen, because the row is deleted at expiry first; and the ADR never states whether `expires_at` runs from `created_at` or `sent_at`. If it runs from creation, a code delivered at +6 min has 9 minutes left; if from `sent_at`, the "regardless of `sent_at`" deletion rule and the 15-minute key-drop argument for `--data-key` rotation both break. Two implementers will choose differently.
- Fix route: edit the Proposed ADR
- Suggested resolution: State `expires_at = created_at + 15 min` in §1 (one place, not a parenthesis), and cut the retry schedule to fit (for example 1 and 5 min), or define a separate send deadline after which an unsent row is deleted.

### G07-3 [major] A non-recipient link holder can burn every pending code by sending wrong values
- Type: E
- Where: docs/adr/0066-share-email-otp-verification.md §4 (lines 46, 48); Proposed INV-91 (line 62)
- Evidence: l.46: "`email_otp` **present but wrong**: every candidate row's `attempts_remaining` is decremented … a row reaching zero is deleted".
- Why it is a gap: The ADR protects real recipients only from callers who omit `email_otp`; anyone with the link and fragment who is not a recipient can send 8 arbitrary wrong codes and delete every pending row for every recipient, and repeat after each resend. The proposed THREAT_MODEL D row (l.48) and INV-91 cover only the absent case, so this denial of service has no stated mitigation or acceptance.
- Fix route: edit the Proposed ADR
- Suggested resolution: Add the recipient email (or `code_id`) to the `/open` body so a wrong guess decrements one row only, or accept the risk explicitly in the D row and Consequences and tie the limiter numbers (G07-4) to it.

### G07-4 [major] Rate limiter numbers and the backoff curve are not given
- Type: B
- Where: docs/adr/0066-share-email-otp-verification.md §4 (line 46), §2 "Rate limits" (line 34)
- Evidence: l.46: "a tight per-`(share_id, source)` bucket plus a looser per-`share_id` ceiling". l.34: "**exponential backoff per source IP**, never a hard lockout, mirroring INV-7".
- Why it is a gap: The `/open` email-OTP limiter has no numbers and no window, and the per-source backoff has no base, factor, cap or reset rule. These are what bounds the online guessing budget against a 10^8 code space, so implementers will build materially different security.
- Fix route: edit the Proposed ADR
- Suggested resolution: Give each bucket a count and window (for example 10 per (share, source) per 15 min, 50 per share per 24 h), and give the backoff parameters, or point to an existing INV-7 parameter set by reference.

### G07-5 [minor] "A new §11.16" collides with CRYPTO.md's existing §11.16 Breach check
- Type: D
- Where: docs/adr/0066-share-email-otp-verification.md §1 (line 26); docs/CRYPTO.md line 1256
- Evidence: 0066: "and a new §11.16 "Share recipient email verification (M5)"". CRYPTO.md l.1256: "### 11.16 Breach check (HIBP k-anonymity, M3)".
- Why it is a gap: §11.16 to §11.20 are now taken (HIBP, WebAuthn, vault create/delete, move/copy, vault invite), so the on-acceptance edit points to a section that means something else.
- Fix route: edit the Proposed ADR
- Suggested resolution: Name the target as "the next free §11.x" or renumber it to §11.21.

### G07-6 [minor] Stale `deny.toml` claim ("no wrapper exception at all yet")
- Type: F
- Where: docs/adr/0066-share-email-otp-verification.md §3 (line 40) and References; deny.toml lines 71–72
- Evidence: 0066: "currently bans `openssl` and `openssl-sys` outright, with no wrapper exception at all yet". deny.toml l.71: "{ crate = "openssl", wrappers = ["webauthn-attestation-ca", "webauthn-rs-core"], …".
- Why it is a gap: The ADR's argument that the rustls-only rule is enforced by an outright ban no longer holds: `openssl` is admitted through two wrappers. The constraint still holds for `lettre`, but the evidence cited is wrong.
- Fix route: edit the Proposed ADR
- Suggested resolution: Update the paragraph to the current `deny.toml` (wrappers limited to the webauthn crates, so `lettre` can still not pull `openssl`).

### G07-7 [minor] Open dependencies on Proposed ADR 0064 and an unhandled plaintext-code hygiene rule
- Type: A
- Where: docs/adr/0066-share-email-otp-verification.md line 54 (create-time refusal), Open questions 6 and 7
- Evidence: l.54: "Share *creation* with non-empty `recipient_emails` while it is unset is ADR 0064's to refuse … a dependency this ADR states but does not implement".
- Why it is a gap: The guard that keeps email-restricted shares openable, the per-account mail cap and the retry-class row all live in other ADRs that do not yet carry them (0064 is Proposed). Nor does the ADR say that the unsealed code (in `api` while sealing and in `worker` while rendering) is held in a zeroizing buffer; it states only "never logged".
- Fix route: edit the Proposed ADR
- Suggested resolution: Before acceptance, either add the three items to ADR 0064 in the same batch, or move them into 0066; add one sentence that the code plaintext is a zeroizing type on both sides.

## ADR 0067 — Send-style text/file share (Proposed)
- Verdict: 4 findings

### G07-8 [major] Send discriminator and entry split are deferred in a circle between 0067 and 0063
- Type: A
- Where: docs/adr/0067-send-style-share.md Decision points 3, 4 and 7 (lines 22–26); docs/adr/0063-share-snapshot-format.md Open question 6
- Evidence: 0067 point 7: "The exact split … is ADR 0063's to settle jointly with this ADR (ADR 0063 Open question 6), not fixed here". 0063 OQ6: "Not fixed by this ADR today. *Recommendation:* decided jointly with ADR 0067 before either is Accepted."
- Why it is a gap: Neither ADR defines the plaintext that marks a snapshot as a Send, or how text over the 65,536-byte per-value cap is split into entries. Each defers to the other, so this part of a persistent, signed-off ciphertext format has no text at all. Two clients (web recipient page, owner client) would encode it differently.
- Fix route: edit the Proposed ADR
- Suggested resolution: Fix the entry shape in one of the two ADRs, for example a reserved `field_key` such as `send/text/<n>` with sequential chunks and a reassembly and refusal rule, and have the other ADR cite it.

### G07-9 [minor] Point 9's precondition is stale: ADR 0054 is Accepted and `ATTACHMENT_CHUNK` is not a placeholder
- Type: D
- Where: docs/adr/0067-send-style-share.md point 9 (line 30); docs/CRYPTO.md lines 664, 768; docs/adr/0054-attachments-envelope-and-api.md line 3
- Evidence: 0067: "a defined chunked envelope (algorithm `0x03`): `ATTACHMENT_CHUNK` (`0x0033`) exists in CRYPTO.md §8.4 today only as a "defined by the M3 attachments ADR" placeholder". CRYPTO.md l.768: "| 0x03 | undefined | reserved; undefined …".
- Why it is a gap: ADR 0054 (Accepted) defines `ATTACHMENT_CHUNK` as algorithm-0x01 chunks and leaves 0x03 reserved, so the file-Send blocker list names a precondition that is already met and an algorithm that will not be used. The only blocker left is the item-less key wrap.
- Fix route: edit the Proposed ADR
- Suggested resolution: Restate point 9's dependency as "ADR 0054's chunk format plus a new share-scoped key-wrap purpose and ctx", and drop the 0x03 reference.

### G07-10 [minor] The M5 ROADMAP row "text/file share" is narrowed to text-only without a ROADMAP edit
- Type: C
- Where: docs/adr/0067-send-style-share.md points 1 and 9; docs/ROADMAP.md line 190
- Evidence: ROADMAP l.190: "| S | "Send"-style arbitrary text/file share (Bitwarden Send equivalent) | M5 |". 0067 point 1: "**Ship text-only Send in M5.**"
- Why it is a gap: CLAUDE.md says a scope change is a ROADMAP edit the owner approves, not something an ADR decides (ADR 0020 point 7, which 0067 cites). The file half is moved past M5 with no milestone and no ROADMAP change.
- Fix route: owner question
- Suggested resolution: Ask the owner to split row 8 into a text Send (M5) and a file Send (a named later milestone), or to keep both at M5 and add the key-wrap decision to this ADR.

### G07-11 [minor] The 1 MiB body budget ignores `recipient_emails`, which has no size cap
- Type: B
- Where: docs/adr/0067-send-style-share.md point 7 (line 26)
- Evidence: "1 MiB body minus ~2 KiB for the other JSON fields (`share_id`, two token hashes, expiry, flags)"
- Why it is a gap: The create body also carries `recipient_emails` (ADR 0066, CRYPTO.md §11.10 step 5), and no ADR caps its count or length. A Send near 512 KiB with a long recipient list could exceed the 1 MiB body, and the client would get a `413` it was told cannot happen.
- Fix route: edit the Proposed ADR
- Suggested resolution: Give `recipient_emails` a count and length cap (in ADR 0064 or 0066) and include it in point 7's budget.

## ADR 0068 — Alias identity model, storage, and no-enumeration lookup (Proposed)
- Verdict: 6 findings

### G07-12 [blocker] A deleted alias's address can be re-registered by another account (alias takeover)
- Type: E
- Where: docs/adr/0068-alias-identity-model.md §3 (line 45), §5 (line 90)
- Evidence: l.90: "Deleting removes the row outright." l.45: "Unique index on `(domain, local_part)` … the client picks `alias_id` and `local_part` (random, or user-typed for a human-readable address)".
- Why it is a gap: Once the row is gone, the unique index no longer reserves `(domain, local_part)`, so any account on the instance can create the same address and receive mail meant for the previous owner: password resets and login codes for every site the alias was registered on. With user-typed local parts (Open question 2) this is easy to exploit. No invariant, threat row or test covers it.
- Fix route: edit the Proposed ADR
- Suggested resolution: Make deletion leave a tombstone that permanently (or for a stated long period) reserves `(domain, local_part)` and rejects it at RCPT like a disabled alias; add an invariant ("a deleted alias address is never reassigned to another account") and a test.

### G07-13 [major] No list or re-enable endpoint, though the ADR's own reconciliation and UI need them
- Type: B
- Where: docs/adr/0068-alias-identity-model.md §3 (line 45), §5 (line 90), Open questions 1 and 3 (line 142)
- Evidence: Endpoints defined: `POST /api/v1/mail/aliases`, `…/disable`, `…/delete`. OQ3: "client-side only, on each alias-list fetch: diff the account's `mail_aliases` list against every item's `alias.id`".
- Why it is a gap: The alias-management screen (OQ1, labels shown while locked), the reconciliation in OQ3 and the Mailbox panel in ADR 0079 §9 all need to list the account's aliases, and "disable" has no inverse. The +3 endpoint count reconciled in ADR 0066 OQ7 assumes these three only, so adding list and enable changes the batch count too.
- Fix route: edit the Proposed ADR
- Suggested resolution: Add `POST /api/v1/mail/aliases/list` (owner session, returns `alias_id`, address, enabled, created_at, sealed label) and `…/enable`, with their body limits, retry classes and the corrected endpoint count.

### G07-14 [major] `MAIL_ALIAS_LABEL` is sealed under the account key with no epoch in its ctx, and key rotation does not re-encrypt it
- Type: B
- Where: docs/adr/0068-alias-identity-model.md §3 table (line 41); docs/CRYPTO.md §11.6 step 3 (lines 1100–1120)
- Evidence: 0068: "`Envelope(account_key, MAIL_ALIAS_LABEL, account_id ‖ alias_id)`". CRYPTO.md §11.6 step 3 re-wraps `E_id`, retired keys, `MAIL_SECRET_KEY`, `ACCOUNT_SETTINGS`, but not alias labels.
- Why it is a gap: After a standard or full rotation, the account key changes, but labels stored in `mail_aliases` stay sealed under the old key with no epoch to say which key to try. They become unreadable unless the rotation commit re-encrypts them, and the ADR names no such step. Every other account-key purpose carries an epoch or sequence in its ctx.
- Fix route: edit the Proposed ADR
- Suggested resolution: Add `u32 account_key_epoch` to the ctx and a §11.6 step-3 bullet (and server-side commit check) that re-seals every `mail_aliases.label` in the rotation; or drop the label (OQ1).

### G07-15 [major] No validation rule for `local_part`: length, charset, reserved names, per-account count
- Type: B
- Where: docs/adr/0068-alias-identity-model.md §3 table (line 39) and creation paragraph (line 45)
- Evidence: l.39: "`local_part` | `TEXT` | clear | ASCII, lowercased like `login_name`".
- Why it is a gap: The server must refuse bad input, but the ADR gives no maximum length (RFC 5321's 64 octets), no allowed characters (dots, `+`, quoting), no reserved names (`postmaster`, `abuse`, which RFC 5321 requires the domain to own) and no cap on aliases per account. A user-typed alias could claim `postmaster@` or squat names for other tenants; implementers will each pick a different rule.
- Fix route: edit the Proposed ADR
- Suggested resolution: Define the accepted `local_part` grammar and length, a reserved-name list refused with `invalid_request`, and an aliases-per-account cap with its error code.

### G07-16 [minor] Parsing rules 1 and 3 disagree on an unknown `mail_message_version`
- Type: B
- Where: docs/adr/0068-alias-identity-model.md §4 Parsing rules 1 and 3 (lines 82, 84)
- Evidence: Rule 1: "`mail_message_version ≠ 1` … → the whole record is rejected and reported like a failed decryption". Rule 3: "An unrecognised `mail_message_version` shows as "Unsupported message, update rizzy-vault" … not a dropped message."
- Why it is a gap: One rule treats version 2 as corruption, the other as a future format to keep and label. A client following rule 1 would show stored mail as broken after a format bump.
- Fix route: edit the Proposed ADR
- Suggested resolution: Split rule 1: 0 and 0xFF are rejected as corrupt; 2–254 skip parsing and show "Unsupported message", keeping the ciphertext.

### G07-17 [minor] Stale references to ADR 0048 and ADR 0028's status line
- Type: D
- Where: docs/adr/0068-alias-identity-model.md "On acceptance" item 5 (line 108), §4 Limits (line 78); docs/adr/0048-per-account-storage-quota.md lines 3, 54
- Evidence: 0068 l.108 quotes ADR 0028's status line as "Partially superseded by [ADR 0031] (item 3 in part); [ADR 0032] (item 3 in part)". 0068 l.78: "(ADR 0048, sibling in this batch)".
- Why it is a gap: ADR 0048 is Accepted and replaced ADR 0028 item 3 in full ("The complete item 3 replacement"), and ADR 0028's status line now lists many more ADRs. The new `409` code must amend the effective text, which now comes from ADR 0048, and the quoted status line is no longer the one to append to.
- Fix route: edit the Proposed ADR
- Suggested resolution: Say the `409` list in ADR 0048's item 3 replacement gains `alias_local_part_taken`, cite ADR 0048 as Accepted, and drop the quoted status line.

## ADR 0069 — SMTP ingress architecture: own listener vs MTA handoff, and the smtp↔api protocol (Proposed)
- Verdict: 6 findings

### G07-18 [major] `deliver` carries no `message_id` or `received_at_ms`, both of which are in `MAIL_MESSAGE`'s AAD
- Type: B
- Where: docs/adr/0069-smtp-ingress-architecture.md §4 `deliver` table (lines 59–65); docs/CRYPTO.md §8.4 line 671 and §11.13 step 3 (line 1217)
- Evidence: CRYPTO.md l.671: "`MAIL_MESSAGE` | 0x0060 | … | account_id ‖ alias_id ‖ message_id ‖ u64 received_at_ms". 0069 `deliver` request fields: `alias_id`, `ciphertext`, `padded_size` only.
- Why it is a gap: `smtp` seals before `deliver`, so it must pick `message_id` and `received_at_ms`, but the wire type never sends them to `api` to store. A client then cannot rebuild the AAD and cannot decrypt any message. If `api` assigns them instead, `smtp` cannot have sealed over them. Either way the protocol as written cannot work.
- Fix route: edit the Proposed ADR
- Suggested resolution: Add `message_id: Id` (smtp-generated, random) and `received_at_ms: u64` to `deliver`, say that `api` stores both verbatim and checks that `received_at_ms` is within a skew window of its own clock, and that `message_id` is unique (refuse a duplicate).

### G07-19 [major] No limits on the internet-facing SMTP session: line length, connections, timeouts, recipients, DATA size
- Type: B
- Where: docs/adr/0069-smtp-ingress-architecture.md §1 (line 20), Open question 3 (line 125)
- Evidence: l.20: "Grammar: HELO/EHLO, MAIL FROM, RCPT TO, DATA, RSET, NOOP, QUIT; no PIPELINING … Opportunistic STARTTLS". OQ3: "Operator-configurable message-size cap … Out of scope here."
- Why it is a gap: A hand-rolled parser on public port 25 needs a command-line length cap, a cap on RCPTs per transaction, per-IP concurrent-connection and idle/DATA timeouts, and a DATA size cap enforced while reading. CLAUDE.md requires untrusted input to be size-limited. The ADR also does not say how one message with several matching RCPTs is sealed (one `MAIL_MESSAGE` per alias, since `rcpt_to` is per alias in ADR 0068 §4?). STARTTLS is in, but it is not in the seven-command grammar list.
- Fix route: edit the Proposed ADR
- Suggested resolution: Give fixed limits (for example RFC 5321's 512-octet command line, 100 RCPTs, idle 5 min) and a DATA cap at or below ADR 0068's 16,776,520-byte ceiling, enforced while streaming. State one seal and one `deliver` per accepted RCPT, and add STARTTLS to the grammar.

### G07-20 [major] `deliver` behaviour on a full quota is still deferred, though ADR 0048 is now Accepted
- Type: A
- Where: docs/adr/0069-smtp-ingress-architecture.md §3 (line 32); docs/adr/0048-per-account-storage-quota.md lines 3, 56; docs/adr/0068-alias-identity-model.md line 78
- Evidence: 0069 l.32: "today none does; the sibling storage-quota ADR 0048's `quota_exceeded` … is the candidate once Accepted — `deliver` does not invent its own code ahead of that".
- Why it is a gap: ADR 0048 is Accepted with `quota_exceeded` 409, and ADR 0068 counts stored mail toward the quota, but nothing defines what `deliver` answers when an account is full or which SMTP reply `smtp` gives (452 temporary vs 552 permanent). Implementers will either bounce, defer forever, or silently store.
- Fix route: edit the Proposed ADR
- Suggested resolution: Name `409 quota_exceeded` as `deliver`'s refusal and map it to a fixed SMTP reply (for example 452 4.2.2), checked at RCPT time if possible.

### G07-21 [major] The bearer secret has no format, length, generation or rotation rule, and the "stored hash" has no source
- Type: B
- Where: docs/adr/0069-smtp-ingress-architecture.md §3 (line 30)
- Evidence: "`RIZZY_SMTP_SHARED_SECRET_FILE`, read by both `api` and `smtp`… `api` hashes the presented token (SHA-256) and compares it to a stored hash with `subtle::ConstantTimeEq`".
- Why it is a gap: Both roles read the same file, so it is unclear where `api`'s "stored hash" comes from (hashed at startup from the file?) and why it is hashed at all. The file's encoding, minimum entropy (bearer-token floor, INV-20-style), how it is generated, its file mode, whether it is zeroized in memory and how it is rotated without downtime are all missing. These are what INV-44's isolation rests on.
- Fix route: edit the Proposed ADR
- Suggested resolution: Specify a 32-byte CSPRNG token, base64url on one line, generated by a named `rizzy-vault` command; `api` hashes it at startup; refuse to start if it is short or malformed; keep it in a zeroizing buffer; allow two valid tokens during rotation.

### G07-22 [minor] `deliver` admits `alg_id` 0x12, but CRYPTO.md's allow-list for `MAIL_MESSAGE` is `{0x10}`
- Type: C
- Where: docs/adr/0069-smtp-ingress-architecture.md §4 (line 57); docs/CRYPTO.md §9.5 (line 789)
- Evidence: 0069: "reads `format_version = 0x01` and `alg_id ∈ {0x10, 0x12}` from the envelope header". CRYPTO.md l.789: "`VAULT_KEY_MEMBER_GRANT`, `MAIL_MESSAGE`: `{0x10}`;".
- Why it is a gap: `api` would store a 0x12 envelope that every client's allow-list then refuses, so the message is accepted at SMTP time and never readable.
- Fix route: edit the Proposed ADR
- Suggested resolution: Restrict `deliver` to the CRYPTO.md allow-list for `MAIL_MESSAGE` (today `{0x10}`), and widen both together when PQ HPKE lands.

### G07-23 [minor] `resolve` rate-limit buckets have no numbers, and the internal listener's loopback default cannot reach a separate `smtp` container
- Type: B
- Where: docs/adr/0069-smtp-ingress-architecture.md §4 (line 55), §3 (line 30)
- Evidence: l.55: "keyed, as its primary mechanism, by the bearer-secret principal … *Secondary* … a per-`alias_address` bucket". l.30: "`RIZZY_INTERNAL_LISTEN` (default `127.0.0.1:8081` …)".
- Why it is a gap: ADR 0010 §2's "`api` rate-limits `resolve`" is the control against a compromised `smtp` walking the alias space, but neither bucket has a count or window. A loopback default works only when `smtp` and `api` share a network namespace, which ADR 0010 §4's separate `ingress` network does not give; the supported compose layout would need a non-default value, and the ADR does not say which.
- Fix route: edit the Proposed ADR
- Suggested resolution: Give both bucket sizes and windows, and state the compose value for `RIZZY_INTERNAL_LISTEN` (bound to the `ingress` network address only) beside the single-host default.

## ADR 0070 — Crypto-crate approval: mail-auth for SPF/DKIM/DMARC verification (Proposed)
- Verdict: 3 findings

### G07-24 [minor] "`ring` is approved only in `rizzy-cli`" is stale; the on-acceptance amendment text repeats it
- Type: D
- Where: docs/adr/0070-mail-auth-crate-approval.md Decision (line 30) and "On acceptance" amendment quote; docs/CRYPTO.md §3 line 110

- Why it is a gap: `ring` now also reaches `rizzy-icon-proxy` (ADR 0052) and, through `rustls`/`sqlx`, `rizzy-storage`, `rizzy-domain-*` and `rizzy-server` (`cargo tree -i ring`). - Fix route: edit the Proposed ADR

### G07-25 [minor] Proposed invariant has no number, while the batch allocation was closed in THREAT_MODEL
- Type: D

- Evidence: 0070 l.59: "| INV-?? | `mail-auth`'s crypto-provider feature is pinned to `ring`." THREAT_MODEL l.1131: "IDs INV-70 to INV-100 were allocated across the 2026-10-11 ADR batch … From INV-101 on, ids are the next free ones".
- Why it is a gap: THREAT_MODEL's reservation list names every Proposed batch ADR's ids but none for 0070, and INV-101 to INV-106 are already taken, so this ADR's invariant will need a post-106 id that neither document records.
- Fix route: edit the Proposed ADR

### G07-26 [minor] Resolver configuration, DNS timeouts and per-message lookup budget are left to crate defaults
- Type: B
- Where: docs/adr/0070-mail-auth-crate-approval.md feature list (line 33), Open question 3
- Evidence: l.33: "`dns-hickory` (→ `dep:hickory-resolver` `=0.26.x`, which keeps its own on-by-default `system-config` and `tokio` features)".
- Why it is a gap: Every accepted message triggers SPF/DKIM/DMARC lookups on attacker-chosen domains, but the ADR fixes neither which resolver `smtp` uses (host `resolv.conf` through `system-config`, or a configured one), nor a lookup timeout, nor a per-message DNS budget. A slow or deep SPF chain can then stall `smtp` sessions, and two deployments behave differently.
- Fix route: edit the Proposed ADR

## ADR 0072 — Remote backup destinations (WebDAV, S3) and destination-credential storage (Proposed)

### G07-31 [major] Retention is deferred in a circle with Accepted ADR 0071, so backup-key lifetime has no owner
- Type: A
- Where: docs/adr/0072-remote-backup-destinations.md §2 "Retention" (line 30); docs/adr/0071-encrypted-db-backup-format.md "Owner answers" 3 (line 81)

### G07-32 [major] No failure, overlap or alerting behaviour for the upload job
- Type: B
- Where: docs/adr/0072-remote-backup-destinations.md §1 (lines 23–25), §2 (line 34), §5 (line 56)
