## ADR 0042 — ACCOUNT_SETTINGS plaintext: canonical layout and the M2 matching section (Partially superseded by ADR 0081 (§2 in part))
- Verdict: 4 findings (effective text: §2 "Tag registry." bullet replaced by ADR 0081 §0 entry 6, plus the 2026-10-24 amendment adding tag 0x0004; everything else binds)

### G05-1 [major] The public-suffix check runs on read, so a PSL update can make a whole account's settings record (including the vault directory) unreadable
- Type: B (also C with §4's own heading)
- Where: docs/adr/0042-account-settings-matching-layout.md §2 (line 82–86), §4 heading "Validation on write" (line 115, 120–122), §8 (line 172–173); code crates/rizzy-match/src/settings.rs:304–309 (`decode` calls `is_valid_user_group`), crates/rizzy-client/src/settings.rs:188–190 (any matching-section error → whole record `InvalidServerResponse`)
- Evidence: §2: "Rejected outright (same severity as failed decryption): … or any violation inside a *recognised* tag (§3)"; §8 negative vectors include "a public-suffix domain".
- Why it is a gap: §4 frames the PSL refusal as a *write-time* check, but §2/§8 make it a decode-time rejection, and the code does that against the compiled-in PSL snapshot. A user group that was valid when written becomes a "violation" in a newer client whose PSL now lists that domain (private-section additions such as hosting domains are routine), so the newer client rejects the *whole* record — since ADR 0081 §A2 that includes tag 0x0002, the vault directory — while older clients accept it. Validity of a stored, signed-fresh record must not depend on the reader's PSL version.
- Fix route: new Proposed ADR superseding ADR 0042 §2 ("Rejected outright", in part) and §8 (in part)
- Suggested resolution: Make the PSL/registrable-domain check write-time only; on read, a user group that fails it is kept verbatim but ignored for matching (and flagged in the UI), never a whole-record reject. Add a vector for "valid-at-write, suffix-at-read".

### G05-2 [major] "A reject blocks further settings writes until resolved": no resolution path and no read-side fallback
- Type: B
- Where: docs/adr/0042-account-settings-matching-layout.md §2 (line 85–86); code crates/rizzy-client/src/settings.rs:167–190
- Evidence: "There is no cross-device merge to fall back on … so a reject blocks further settings writes until resolved."
- Why it is a gap: Nothing says who or what "resolves" a rejected record (overwrite with defaults? keep the last good copy from the ADR 0026 cache? user-confirmed reset?), nor what matching does meanwhile. Falling back to the §3 defaults would silently re-enable global groups the user disabled (an INV-38-relevant widening), and the code collapses every case into the generic `InvalidServerResponse`, so two implementers will diverge. With tag 0x0002 in the same record, a stuck reject also blocks vault creation/moves (ADR 0081).
- Fix route: new Proposed ADR superseding ADR 0042 §2 ("Rejected outright", in part)
- Suggested resolution: Define (a) a dedicated error code, (b) read-side behaviour while rejected (fail closed for matching: no equivalence matches beyond exact registrable domain; vault directory from the last verified cache), and (c) an explicit, user-confirmed "reset settings" write that re-emits unknown tags and drops only the invalid recognised tag.

### G05-3 [minor] No bound on the whole record; the stated bound is not implied by the limits
- Type: B
- Where: docs/adr/0042-account-settings-matching-layout.md §4 (line 129–136)
- Evidence: "`MAX_SETTINGS_ENTRIES = 256` … The whole plaintext stays far under `rizzy-proto::limits::MAX_ENVELOPE_LEN` (16 MiB)"
- Why it is a gap: 256 entries × 1 MiB per entry allows ~256 MiB, so "stays far under 16 MiB" is not guaranteed by the stated limits; the only real cap is the envelope limit, and the ADR does not say which layer refuses an oversize record or with what error.
- Fix route: erratum ADR
- Suggested resolution: State a total plaintext cap (e.g. ≤ MAX_ENVELOPE_LEN minus envelope overhead), refused on write by the client with a named error, and on read as a malformed record.

### G05-4 [minor] `format_version ≠ 1` is listed both as "rejected outright" and as "parked, not rejected"
- Type: A
- Where: docs/adr/0042-account-settings-matching-layout.md §2 (line 82–84) vs §8 (line 173–174); code crates/rizzy-client/src/settings.rs:172–174 (`SettingsUpdateRequired`)
- Evidence: §2 "Rejected outright … `format_version ≠ 1` (parked and reported "update required" …)"; §8 "`format_version ≠ 1` (parked, not rejected)".
- Why it is a gap: The two sections disagree on whether a future-version record is a reject (which per §2 "blocks further settings writes") or a park. The code parks (distinct error), which matches §8; the §2 wording should not be read as blocking writes for a newer format.
- Fix route: erratum ADR
- Suggested resolution: Move `format_version ≠ 1` out of the "Rejected outright" list and state that a parked record also blocks writes (a client must never overwrite a newer-format record).


## ADR 0043 — A per-instance token for the inline-menu and passkey-consent iframes (Accepted)
- Verdict: 2 findings (the 0043/0076 rewrite of ADR 0036 §4 is already in HANDOFF §1 and not re-reported)

### G05-5 [minor] Decision point 5 says revocation deletes "immediately"; owner answer 4 says it waits for in-flight requests
- Type: A

### G05-6 [minor] The "bounded store" has no stated bound or eviction rule
- Type: B
- Where: docs/adr/0043-inline-menu-instance-token.md §Decision point 2 (line 49–51), owner answer 2 (line 107); code apps/extension/src/core-host/iframe-instance.ts:33, 37, 122–128
- Evidence: "binds the token to `(sender.tab.id, trustedOrigin)` and a TTL (recommend 30 min; Open questions), in a bounded store shaped like `passkeyCeremonies`."

## ADR 0044 — Equivalence-group member rules: no IP literals, registrable domains only (Accepted)
- Verdict: 2 findings

### G05-7 [major] Owner answer 1 rests on a false premise: ADR 0042 §4's PSL check does not "cover the same inputs", it also rejects the dotless members ADR 0044 says "must not be rejected"
- Type: A (also C between ADR 0042 §4 and ADR 0044 rule 2)
- Where: docs/adr/0044-equivalence-group-member-rules.md rule 2 (line 26), owner answer 1 (line 60), "Where this applies" (line 34); docs/adr/0042-account-settings-matching-layout.md §4 (line 120–122); code crates/rizzy-match/src/settings.rs:27–30, 131–155
- Evidence: 0044 rule 2: "accepts a dotless single-label member like `"nas"` … a bare intranet hostname like `nas` is fully reachable and must not be rejected"; owner answer 1: "The check therefore stays binding, alongside the `EquivalenceGroup::new` rule that now covers the same inputs."
- Why it is a gap: ADR 0042 §4 requires the domain to equal its own *PSL* registrable domain, which a dotless name never is; the code says so explicitly ("the first check adds, for a user group, only the refusal of a dotless name"). So for user groups — the place intranet names like `nas` actually occur — the two Accepted texts give opposite answers, and the owner's resolution was made on the belief that they agree. The question whether to drop ADR 0042's check is also left explicitly open ("this stays open"). ADR 0044 additionally still calls ADR 0042 "Proposed, reference only" (lines 34, 98) although 0042 was Accepted the day before 0044.
- Fix route: owner question
- Suggested resolution: Ask the owner whether a user group may contain a dotless intranet host; then a Proposed ADR superseding ADR 0042 §4 (public-suffix bullet, in part) either drops the PSL check in favour of ADR 0044's rule or states the dotless refusal as intended for user groups.

### G05-8 [minor] "A PSL bump" covers only the signed global list, not user groups stored in ACCOUNT_SETTINGS that the same `decode` rule now applies to
- Type: B
- Where: docs/adr/0044-equivalence-group-member-rules.md "A PSL bump that turns a signed member into a suffix" (line 36–38), "Where this applies" (line 32–34)
- Evidence: "Mitigation is process, not code: a PSL bump (ADR 0037 §3) re-runs the equivalence-list builder against the new snapshot in the same review"
- Why it is a gap: The rule lives in `EquivalenceGroup::decode`, which also decodes user groups from ACCOUNT_SETTINGS (ADR 0042 §3), but a release-time process cannot re-check users' stored data. A PSL bump therefore turns a stored user group into a decode failure on new clients only; see G05-1 for the consequence (whole record rejected).
- Fix route: new Proposed ADR superseding ADR 0042 §2 (in part) (same ADR as G05-1)
- Suggested resolution: Resolve together with G05-1: decode-time member validation for *stored user* data must tolerate PSL drift (keep verbatim, ignore for matching, surface to the user).

## ADR 0050 — Paged Fetch: tombstone covers that can span a page boundary (Accepted)
- Verdict: 2 findings

### G05-21 [major] The cursor advances past a held header, but the ADR never says it must fall back when the hold lapses or is lost on restart
- Type: B
- Where: docs/adr/0050-paged-fetch-tombstone-boundary.md §1 ADR 0012 replacement (line 26), §2 (line 36, 40), Open question 1 (line 103); code crates/rizzy-sync/src/causal.rs:122–135 ("the cursor entry drops below the first of them")
- Evidence: §2: "so that the chain's head and cursor advance past it instead of the walk ending in `Report::Gap`"; line 40: "A process restart before the hold resolves drops it: the next Fetch starts a fresh sequence from whatever cursor was last persisted."
- Why it is a gap: The Fetch cursor (ADR 0012 §7) is what the server serves from. If the advanced cursor is used (or persisted, ADR 0026) after a lapse or a mid-sequence restart, the bodiless header and its cover are never served again, so the held dot never settles and everything causally after it waits forever — contradicting OQ1's premise that the claim "is retried from scratch next sequence". The code adds an unstated rule (on lapse "the cursor entry drops below the first of them"); the ADR is silent on the rewind and on whether a persisted cursor may ever include a held link, so a second implementer can build the permanent-stall version.
- Fix route: erratum ADR
- Suggested resolution: State normatively that a held link never advances the *persisted* cursor, and that a lapse (sequence complete, release, or the cap below) rewinds the in-memory cursor to just below the first held link so the next Fetch re-serves it; add a restart-mid-sequence test to §4.

### G05-22 [minor] No bound on the number of held covers; the code's `MAX_HELD_ITEMS = 256` and "final at once" overflow rule are not in the ADR
- Type: B
- Where: docs/adr/0050-paged-fetch-tombstone-boundary.md §2–§3 (line 36–52); code crates/rizzy-sync/src/causal.rs:136, 254, 927–932
- Evidence: §3: "`ItemMerge` keeps the refused cover pending per item, as a `(SnapshotHeader, SecretBytes)` pair"
- Why it is a gap: Each hold keeps decrypted snapshot plaintext in memory for a whole response sequence and the server picks the pages, so a malicious or buggy server can make a client hold an unbounded number of covers; the ADR gives no cap and no overflow behaviour, and the code's choice (256 items, then an immediate final refusal reported as a gap) is a behaviour a second client (web/extension through `rizzy-wasm`, M3 native) must reproduce.
- Fix route: erratum ADR
- Suggested resolution: Record `MAX_HELD_ITEMS` and the overflow rule in the ADR (and INV-74), so the bound is part of the binding text.

## ADR 0052 — Icon-proxy (favicon) role: fetch, cache and re-encode mechanism (Accepted)
- Verdict: 1 finding (checked: CRYPTO.md:110 gained the `rizzy-icon-proxy` transport row; ADR 0028 status line names 0052 incl. the `blob:` token; INV-76 row exists, THREAT_MODEL.md:1252)

### G05-24 [major] No user-level control: clients send every item's website host to the server whenever a vault is opened, and the "cannot correlate" claim only holds inside the `icons` process
- Type: E (also C with ROADMAP.md:140)
- Where: docs/adr/0052-icon-proxy-role.md point 5 (line 33), point 6 (line 34); ROADMAP.md:140; THREAT_MODEL.md:106 (AST-13); code apps/web/src/views/VaultView.tsx:160–168 (an `IconLoader` per unlocked session, no setting), packages/ui/src/itemIcons.ts:19 ("a server without the role" — the request is still sent)
- Evidence: point 5: "No account, session or request identifier ever reaches `rizzy-icon-proxy` … so the cache cannot correlate requests to a user."; ROADMAP.md:140: "Fetching website favicons through our server without privacy controls (leaks which sites you use) — must be optional / proxied / cached anonymously".
- Why it is a gap: The only "optional" control is the operator's role switch. The endpoint is on the same origin, behind the same reverse proxy and usually on the same HTTP/2 connection as the authenticated `/api/v1` calls, so a malicious or compromised operator (an in-scope attacker) links each `icons/fetch` body to the account by connection/IP/timing and learns the user's list of sites — data that is otherwise end-to-end encrypted item content. The ADR defines no user opt-in/opt-out, no rule that clients ask only when `/api/meta` advertises the role (today the web vault sends hosts even when the role is off, to an `api` process that answers `not_found`), and no statement of this residual risk.
- Fix route: new Proposed ADR superseding ADR 0052 point 6 (in part)
- Suggested resolution: Add a per-account, default-off "show website icons" setting (an ADR 0042 tag), have clients fetch only when it is on *and* the server advertises the role, and record the operator-correlation residual as an accepted risk in THREAT_MODEL with the opt-in as its mitigation.

## Summary

Counts: **1 blocker, 9 major, 18 minor** (28 findings). ADR 0049 has no gaps.

Top 5 by importance:
1. **G05-12 (blocker)**: ADR 0046 (accepted 2026-10-24) replaced ADR 0026 §2's device_state grammar with a version-1-only block and says `RECORD_VERSION` stays 1. That contradicts ADR 0057 (Accepted, writes version 2, adds `has_ks`/`forward`). The code follows 0057.
2. **G05-1 + G05-2 (major)**: the ADR 0042 public-suffix check runs on *read* against the compiled-in PSL. A PSL update can make a whole ACCOUNT_SETTINGS record, vault directory included, "rejected outright", and §2 gives no way to resolve the reject and no fallback for reads.
3. **G05-24 (major)**: the ADR 0052 favicons have no user opt-in. The web vault sends every item's host to the server on unlock (even when the role is off), so a malicious operator can link the hosts to the account. ROADMAP's "must be optional" is met only at the operator level.
4. **G05-13 (major)**: ADR 0046 has no exit if the user cannot type the new master password of an interrupted recovery. `device forget` refuses stage 3 and INV-71 blocks a new kit, so the machine is stuck.
5. **G05-7 (major)**: ADR 0044 owner answer 1 says ADR 0042's PSL check "covers the same inputs". It does not: it refuses dotless intranet names, which ADR 0044 says "must not be rejected". For user groups the two Accepted texts give opposite answers, and the owner left the question open.
