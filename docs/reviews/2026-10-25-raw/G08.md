## ADR 0076 — Autocomplete-driven autofill: field detection, TOTP-code fill and custom-field autocomplete ids (Accepted)
- Verdict: 5 findings

### G08-1 [major] ADRs 0043 and 0076 give two different binding replacement texts for ADR 0036 §4, first bullet; still no reconciling ADR
- Type: C
- Where: docs/adr/0076-autocomplete-driven-autofill.md §9 (line 332) and the ADR 0040 point 2 row (line 331); docs/adr/0043-inline-menu-instance-token.md "What this ADR supersedes" (line 142); docs/HANDOFF.md:65
- Evidence: 0076 line 332: "sends only: detected-field reports and submitted-form reports (ADR 0076 §5.1 ...)". 0043 line 142: "sends only: detected-field reports, submitted-credential reports, and a per-instance registration/revocation message ... (ADR 0043)".
- Why it is a gap: Both ADRs are Accepted (2026-10-22) and each replaces the same quoted part. Neither names the other, so under ADR 0020 point 9 two "sends only" lists bind at once, and each one forbids a message the other requires. HANDOFF.md:65 records this as an open owner question with "Until a small reconciling ADR settles it", but none of ADRs 0077–0087 mentions ADR 0043 (grep), so it is still open. The ADR 0040 point 2 replacement (0076 line 331) has the same problem: it lists "detected-field reports and submitted-form reports" only, with no register/revoke message.
- Fix route: new Proposed ADR superseding <ADR 0076 §9 rows 2–3 and ADR 0043 "What this ADR supersedes" row 1>
- Suggested resolution: Write one reconciling ADR that gives a single replacement text for ADR 0036 §4 first bullet and ADR 0040 point 2. The text lists detected-field reports, submitted-form reports (with the §5.1 custom captures), and the ADR 0043 register/revoke message for every extension-origin iframe, the save dialog included. Then fix the status lines of 0036 and 0040.

### G08-2 [major] The save dialog's sender authentication and its "save-prompt token" are never specified
- Type: B
- Where: docs/adr/0076-autocomplete-driven-autofill.md §5.2 (line 262), §5.1 (line 260); docs/adr/0043-inline-menu-instance-token.md (title and line 38: tokens for "an inline-menu or passkey-consent iframe" only); apps/extension/src/save-dialog/protocol.ts:3-9, apps/extension/src/messaging/contract.ts:323-327
- Evidence: "The dialog fetches its choices from the long-lived context directly, by the save-prompt token." / "zeroizes them when the prompt is resolved or times out".
- Why it is a gap: "save-prompt token" is not defined anywhere in the ADRs (grep for "save-prompt token" / "save prompt" finds only 0076). The ADR gives no format, entropy, lifetime, timeout value, single-use rule, tab binding, or the refusal when it is wrong. It also does not say how the long-lived context tells the save-dialog iframe apart from another extension-origin document in the same tab. ADR 0043 says sender information alone cannot do that, and it covers only the inline-menu and passkey-consent iframes. The code adds an ADR 0043 `instanceToken` to `SaveDialogRequestMessage`, which is a sensible choice, but no Accepted text requires it. A second implementer could leave it out, and then any extension-origin document in the tab could read the captured rows' labels and resolve the prompt.
- Fix route: new Proposed ADR superseding <ADR 0076 §5.2 in part> (it can be the same reconciling ADR as G08-1)
- Suggested resolution: Define the save-prompt token: 16 random bytes, single use, bound to the tab id, with a stated lifetime equal to the capture zeroization timeout. Extend ADR 0043's per-instance token to the save-dialog iframe, and list the refusals (missing, expired, other tab, used).

### G08-3 [major] No clickjacking mitigation is specified for the new save-dialog iframe
- Type: E
- Where: docs/adr/0076-autocomplete-driven-autofill.md §6 (line 283 covers only "Clickjacking the menu"), Negative (line 418); docs/THREAT_MODEL.md:458 (A7 bullet for 0076) and :1212 (INV-36 row); apps/extension/src/save-dialog/main.ts:173
- Evidence: line 418: "A second extension-origin iframe (the save dialog) to build and clickjack-harden like the inline menu." The §6 row: "Clickjacking the menu | Unchanged M2 mitigations (`menu-visibility.ts`, IntersectionObserver v2 where available)".
- Why it is a gap: The hardening appears only as a Consequence. No Decision rule requires it, and §6 has no row for a clickjacked save dialog. A page that overlays the dialog can turn a user's click into "save" of page-chosen values under a page-chosen autocomplete id, and those values then fill on that site (§5.3 checks new text fields by default). THREAT_MODEL's INV-36 column covers only "the save dialog's choices cannot be changed by the page", not clickjacking. Spot check: `save-dialog/main.ts` checks only `event.isTrusted`. It has none of the IntersectionObserver v2 `isVisible` gate that `inline-menu/main.ts:25-42` has.
- Fix route: new Proposed ADR superseding <ADR 0076 §5.2 in part>, plus doc fix (THREAT_MODEL)
- Suggested resolution: Make "the save dialog uses the same visibility and topmost gates and IOv2 check as the inline menu" a Decision rule. Add a §6 row and a THREAT_MODEL A7 mitigation with an e2e test (an overlaid or transparent save dialog does not save).

### G08-4 [minor] W5 is implemented with an order-only exemption that the ADR text does not give
- Type: F
- Where: docs/adr/0076-autocomplete-driven-autofill.md §2.3 W5 (line 136), §2.4 (line 138); crates/rizzy-client/src/autofill/tests.rs:168-171
- Evidence: ADR: "a write that creates a custom field, or edits any attribute of an existing one other than removing it, must leave its displayed `label` holding at least one non-whitespace character." Code test: "// An order-only write is a layout write, not an edit."
- Why it is a gap: Under the ADR text, reordering an "Unnamed field" (a write to `field/<id>/order`) is refused with `LabelRequired`. The code allows it. The code's choice is the more usable one, but the ADR does not say whether a list reorder counts as an "edit", so a review or test written against the text would flag correct code.
- Fix route: new Proposed ADR superseding <ADR 0076 §2.3 W5 in part> (or an erratum ADR)
- Suggested resolution: State that writes only to layout attributes (`order`, and `kind` subject to W4) are not edits for W5, which matches the code.

### G08-5 [minor] Behaviour when a tab exceeds 4 open offers is unspecified
- Type: B
- Where: docs/adr/0076-autocomplete-driven-autofill.md §4.1 step 3 (line 202); apps/extension/src/core-host/offer-store.ts:74-79
- Evidence: "It lives at most 120 s, is used once, and is dropped on lock and when the tab navigates. A tab has at most 4 open offers."
- Why it is a gap: The text does not say whether a fifth offer request is refused or evicts the oldest offer. The code evicts the oldest, so a menu showing an evicted offer gets a "missing" refusal on click. A refusing implementation would instead leave the newest menu unusable. The user-visible results differ.
- Fix route: erratum ADR
- Suggested resolution: State "the oldest open offer of the tab is dropped", as implemented, and say what the iframe shows when its offer is gone.

### G08-6 [major] No per-account security-key limit, although the login state that carries every credential is capped at 64 KiB and refused above it
- Type: B
- Where: docs/adr/0077-webauthn-rs-integration-fixes.md Context (line 17), §2 "Where" (line 60), §4 (line 89); crates/rizzy-proto/src/limits.rs:163-165; crates/rizzy-domain-auth/src/webauthn.rs:90-91, 149
- Evidence: line 17: "Authentication: the full `Credential` record of every allowed credential (credential id, COSE public key, counter, UV and backup flags, any parsed attestation)". Line 60: "or whose `state` exceeds 64 KiB, is refused on read (bounded input, fail closed); the ceremony restarts."
- Why it is a gap: The login state grows with the number of enrolled keys and with the size of each key's parsed attestation, which §5 keeps. Neither ADR 0058 nor 0077 caps either. An account with enough keys, or keys with large attestation chains, gets a state that is refused on every read, and the restart then fails the same way, so the second factor fails closed for good. The text names no error code and no recovery for this case. The code fills the gap with its own choice (`MAX_WEBAUTHN_CREDENTIALS = 32`, commented "this crate's choice"), and it also applies the 64 KiB cap to stored `security_key` values, which the ADR does not say. A second implementer could pick other numbers, or none.
- Fix route: new Proposed ADR superseding <ADR 0077 §2 "Where" in part and §4 in part>
- Suggested resolution: Fix a per-account key limit and a per-`security_key` size limit whose product, with headroom, stays under the 64 KiB state cap (for example 32 keys × 1.5 KiB). Name the enrolment refusal code (the code uses `Conflict`). Also cap the concurrent enrolment-state rows per account.

### G08-7 [minor] OpenSSL advisories fall outside `cargo deny`, and no detection process is named
- Type: E
- Where: docs/adr/0077-webauthn-rs-integration-fixes.md §8 (line 109), Negative (line 179); §9 entry 2 (line 122)
- Evidence: "the release binary links a C crypto library whose version comes from Alpine, not from Cargo.lock, so `cargo deny` does not see its advisories." / "an OpenSSL security release triggers an image rebuild."
- Why it is a gap: The rebuild trigger needs someone or something to notice an Alpine OpenSSL security release. Nothing in the ADR does that: no scanner, no CI job, no owner duty. The SBOM entry that could feed a scanner is itself U ("the entry may have to be added explicitly"), and ADR 0073's SBOM is still blocked on its approval records (HANDOFF.md:169). The OpenSSL here verifies every WebAuthn 2FA signature, so a missed advisory is a security gap.
- Fix route: doc fix (CRYPTO/THREAT_MODEL/ROADMAP/README), or an owner question if a CI job is wanted
- Suggested resolution: Name the detection: for example, a scheduled CI job that compares the builder image's `apk info -v openssl` against Alpine's security tracker, or an explicit owner duty in RELEASING or THREAT_MODEL §supply chain. Make the SBOM entry mandatory rather than "may".

### G08-8 [major] What a cross-vault move, or "move items to Personal, then delete", does with a retired `0x0009` (or any unsupported-type) item is unspecified
- Type: B
- Where: docs/adr/0078-retire-bank-account-item-type.md §1 (line 43), §3 "Import" bullet (line 65); docs/adr/0081-multiple-vaults-personal-and-shared.md §A5 (line 138), §A6 step 1 (line 146); crates/rizzy-client/src/items.rs:420-425 (doc of `import_item_writes`)
- Evidence: 0078 line 43: "trash, restore and purge work, and field edits are not offered. `ItemType::supported()` returns `None` for it, so `check_write` refuses a create of it". 0081 line 146: "the client creates a new item in the target vault through the importer path ADR 0027 §2 step 4 already uses (`VaultSync::import_item`)".
- Why it is a gap: ADR 0081 (Accepted 2026-10-24, after 0078) builds both move and copy on the importer path. That path refuses an unsupported type: `InvalidEdit` "for a type that is not a supported user item type", and ADR 0027 §2 step 4 says such an entry "is skipped". So a `0x0009` item cannot be moved. Neither ADR says whether the move or copy is offered for it, which error is shown, or, in the bulk "Move its N items to Personal, then delete" flow, whether the vault deletion aborts or goes ahead. If it goes ahead, the retired item, with its concealed account and routing numbers, is deleted along with the vault, although the user chose "move". ADR 0078 says the user must be able to "move the data out by hand", and this silent loss works against it.
- Fix route: new Proposed ADR superseding <ADR 0081 §A5–§A6 in part> (or an owner question)
- Suggested resolution: State that items of unsupported or retired types cannot be moved or copied, and say how the UI shows that. Make "move N items then delete" refuse, before touching anything, while any such item remains, and name the item so the user can trash or purge it explicitly. Add a test with a `0x0009` item in a vault being deleted.

### G08-9 [major] "After that the last-used range", remembered in synced ACCOUNT_SETTINGS (Open question 7 (a)), cannot be written at create time without a fresh session; the implementation keeps it session-only instead
- Type: C
- Where: docs/adr/0079-identity-generator.md §3 "The default" (line 188), Open question 7 (a) (answered by "Owner answers at acceptance", line 79); docs/adr/0042-account-settings-matching-layout.md Amendments 2026-10-24 (lines 270-297); apps/web/src/identity-memory.ts:1-13
- Evidence: ADR line 188: "**The default.** 18–27 the first time; after that the last-used range (preset, custom or exact). Where that is remembered is Open question 7." Code: "writing the synced defaults ... is an `account/commit`, which the server takes only within five minutes of a login (`server_fresh_session_required`)".
- Why it is a gap: The accepted answer, (a) synced, places the last-used range in tag `0x0004`. But every ACCOUNT_SETTINGS write is an `account/commit` that needs a fresh OPAQUE session. A create made more than five minutes after login therefore cannot record the range without failing or asking the user to re-authenticate. The ADR does not address this. The code keeps a session-only last-used range over the synced defaults and writes the tag only from Settings. That diverges from the ADR (HANDOFF.md:189 lists it as a deviation), and another client could implement it differently, for example by prompting for re-authentication on save.
- Fix route: new Proposed ADR superseding <ADR 0079 §3 "The default" in part> (or an owner question)
- Suggested resolution: Split "synced defaults", written only from Settings under the fresh-session rule, from "last-used in this session", which is memory only and dropped on lock, as the code does. Say which one wins on the next open.

### G08-10 [minor] `rv` uses the UTC date, but the ADR says the local date

### G08-12 [major] Unproven members were merged into the human-editable source, and nothing mechanical stops a list being signed from them
- Type: C
- Where: docs/adr/0038-equivalent-domain-list.md §4 rule 1 (line 63); docs/adr/0080-default-site-groups-vaultwarden-seed.md §2 (line 153), §3 (lines 169-180); data/equivalence/groups.txt:74-75 (commit 8405bb6); data/equivalence/EVIDENCE.md "Status"; crates/xtask/src/equivalence_list.rs:389-395

- Why it is a gap: ADR 0080 §2–§3 says members "must find their evidence in the import PR or be dropped", and ADR 0038 §4 rule 1 (binding, not superseded by 0080 §7) requires proof before the merge. Top 5 by importance:
1. **G08-3** (0076): no Decision rule or THREAT_MODEL mitigation covers clickjacking of the new extension-origin save dialog. A spot check shows the dialog lacks the inline menu's IOv2 `isVisible` gate. A clickjacked "save" stores page-chosen values under a page-chosen autocomplete id.
2. **G08-1** (0076/0043): two Accepted ADRs give conflicting "sends only" replacement texts for ADR 0036 §4 first bullet (and ADR 0040 point 2). HANDOFF promised a reconciling ADR, and none exists among 0077–0087.
3. **G08-12** (0080): all 22 seed groups (184 domains) are in `groups.txt` with "TODO (owner)" evidence, against ADR 0038 §4 rule 1 ("before it is merged"). No tool check stops a list being signed from them.
4. **G08-8** (0078/0081): moving a retired `0x0009` item between vaults, or deleting its vault with "move items to Personal", is undefined. The importer path refuses the type, so the item can be lost silently with the vault.
5. **G08-2** (0076): the save dialog's "save-prompt token" and its sender authentication are undefined. ADR 0043's per-instance token covers only the inline-menu and passkey-consent iframes; the code extends it to the dialog without ADR text.

Also notable: G08-6 (0077), no per-account security-key cap, although the login state holding every credential fails closed above 64 KiB; G08-9 (0079), synced "last-used" defaults conflict with the fresh-session rule for ACCOUNT_SETTINGS writes.

## Unverified suspicions

- **0076 save dialog placement:** `content-script.ts`'s `SaveDialog` (lines 1397-1470) sets `zIndex = MAX_Z_INDEX` but shows no visibility or topmost gate, unlike the inline menu. I did not trace whether the shared gate in `menu-visibility.ts` is applied elsewhere for the dialog. This would strengthen G08-3.
- **0076 TOTP rule (g):** it relies on `hasTotp` per candidate from the long-lived context, but the content script decides whether to open a menu at a TOTP-only step (§4.1 step 1, "only if a candidate has it"). I did not check whether a compromised content script opening a TOTP menu anyway is harmless. It appears to be, since the offer recomputes candidates.
- **0077 state size:** I did not measure the real JSON size of a `SecurityKeyAuthentication` with N credentials and packed attestation, so the point at which G08-6's 64 KiB cap is reached (N≈20–40?) is an estimate.
- **0077 RS256 refusal:** §6 says a non-ES256 credential is refused "with a typed error". I did not check that `AuthError` has a distinct code for it rather than a generic `InvalidInput`. The doc comment at `webauthn.rs`:397 suggests a specific variant.
- **0079:** `cargo xtask identity-data --check` determinism and the 384 KiB size-budget test were not run. `identity-data-v1.txt` is reported as 347 KB in HANDOFF.
- **0080:** the upstream re-check ("At each scheduled re-check … diff against bitwarden/server's current `StaticStore.cs`") has no named schedule before v1.0 (no release cycle exists yet). Possibly a minor B gap; not verified against RELEASING docs.
