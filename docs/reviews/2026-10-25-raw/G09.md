### G09-1 [major] `vault_join` self-grant is checked "as §A3 does", but §A3 requires vault epoch 0
- Type: B
- Where: docs/adr/0081-multiple-vaults-personal-and-shared.md §B5 step 4 (line 271); §A3 (line 130)
- Evidence: §B5: "The server checks the self-grant as §A3 does, stores it under `(vault_id, account_id)`"; §A3: "whose self-grant is not at the new state's `account_key_epoch` and vault epoch 0 … (`invalid_request`)".
- Why it is a gap: A joined vault is at the epoch of the latest `vault-membership` statement (any vault that has had a removal or rekey is at epoch ≥ 1). Read literally, the server refuses every join after the first rekey; read loosely, the server checks no epoch at all. Two server implementers will diverge, and neither reading is "the statement's `vault_key_epoch`".
- Fix route: erratum ADR
- Suggested resolution: State the `vault_join` (and `vault/members/adopt`) checks explicitly: account-key epoch and key id as §A3, vault epoch equal to the stored statement's `vault_key_epoch`, and the member state `invited`.

### G09-2 [major] The `vault-membership` statement does not identify its signer; server and readers verify against different keys
- Type: B
- Where: docs/adr/0081-multiple-vaults-personal-and-shared.md §B3 body (lines 234–250) and "Signer" (line 252); §B9 (line 306); §B11 `vault_memberships` table (line 327)
- Evidence: §B3: "signing with the identity Ed25519 key that statement lists for it"; §B9: "the signature against the signer's current bundle (held by the `auth` domain …), and that the signer is a manager in the stored statement".
- Why it is a gap: Neither the body, the `vault/members/update`/`invite` request nor the `vault_memberships` row carries a signer account id, so a verifier must either try every manager's key or assume the uploader's session account; implementers will differ. The server checks the signer's *current* bundle while readers check the key listed in statement `seq − 1`; after a manager's full rotation (or for the owner, who §B3 lets sign with a new key) the two layers accept different statements, which §B3's own rule about re-listing makes a normal case, not an edge case.
- Fix route: erratum ADR
- Suggested resolution: Add `signer account_id (16)` to the signed body (or the signed envelope), and have the server verify against the key the stored statement lists for that signer, the same rule readers apply.

### G09-3 [major] Fetch must return "statements after the client's pinned `membership_seq`", but the request carries no seq
- Type: B
- Where: docs/adr/0081-multiple-vaults-personal-and-shared.md §B11 "Responses" (line 325); §B3 INV-105 (line 254, line 372)
- Evidence: "`FetchRequest` gains `membership: bool` … the Fetch response adds the statements after the client's pinned `membership_seq`".
- Why it is a gap: The pin lives in the client's encrypted directory (§A2), which the server cannot read, and the request adds only a boolean; so the server cannot know where to start. INV-105 also requires verification "from `seq = 1`", so a fresh device needs the whole chain, which no request shape or response limit (count, bytes) covers.
- Fix route: erratum ADR
- Suggested resolution: Add `membership_after: u64` (0 = whole chain) to the per-vault Fetch request, give a cap on statements per response with paging, and state that a new device fetches from 0.

### G09-4 [major] Re-publishing membership statements after a backup restore is left to "the Part B implementation"
- Type: A
- Where: docs/adr/0081-multiple-vaults-personal-and-shared.md Risks (line 417); §B9 "`seq = stored + 1`" (line 306)
- Evidence: "clients detect it through their pins and must re-publish their highest statements through healing, which the Part B implementation adds."
- Why it is a gap: This is a protocol and persistent-format change (a new healing payload, the server accepting a chain above `stored + 1` signed under the old stored state, which client re-publishes, what happens to member grants and self-grants that the restore also rolled back) decided by no ADR; ADR 0032/0021 healing has no membership notion (grep for "membership" in 0021 and 0032: no hits). Under CLAUDE.md's ADR gate the "implementation" cannot add it.
- Fix route: new Proposed ADR superseding 0081 Risks/§B9 in part (or folded into the M9 Part B follow-up)
- Suggested resolution: Specify a membership-healing request (statements `stored+1..n` with their signatures, verified as a chain against the stored head), which client sends it, and the treatment of restored grants, before Part B code starts.

## ADR 0085 — Admin authentication: operator accounts, the bootstrap token, mandatory TOTP and admin sessions (Proposed)
- Verdict: 6 findings

Notes: Context facts spot-checked: THREAT_MODEL INV-69 text (THREAT_MODEL.md:1249) and INV-7 (:1143) as quoted; 0x0107 and INV-107 are not claimed by 0086 or 0087 (grep: no hits), INV-106 is ADR 0077's (THREAT_MODEL.md:1131), so the provisional numbers are free today.

### G09-14 [major] The global admin-login bucket lets anyone who reaches the listener lock the operator out, which §9.1 forbids
- Type: B / C
- Where: docs/adr/0085-admin-authentication-bootstrap.md §9 items 1–2 (lines 309–316); §1.3 (lines 112–115)
- Evidence: §9.1: "**No hard lockout** (… a lockout would let anyone who reaches the listener lock the operator out …)"; §9.2: "`admin_login_global` per instance, 20 per hour, then backoff from 60 s doubling to 1 h … A blocked attempt answers `429` without running Argon2id."
- Why it is a gap: A tunnel/VPN peer, another local user or a misconfigured proxy (the very adversaries §1.3 lists) can keep the per-instance bucket saturated with 20 bad attempts an hour from rotating sources; every attempt by the real operator then gets `429` before its password is checked, so the operator is locked out for as long as the attacker keeps going — a hard lockout in effect, with `admin reset` (server stopped) as the only exit. The same holds for `admin_bootstrap_global` during the 24 h bootstrap window, which then expires unredeemed.
- Fix route: edit the Proposed ADR
- Suggested resolution: Make the global limit a cost/concurrency limit (the Argon2id semaphore already is one) rather than a refusal, or exempt a source with no recent failures, or let a correct password+TOTP pass the global bucket; state the chosen rule and test "flooding from many sources does not block a correct login", as INV-7's "Verified by" does for vault accounts.

- Why it is a gap: Concurrency between the offline command, a running server's `worker` re-seal pass (§5 "Rotation" rewrites the same `smtp_password` row) and `secrets rotate --data-key` (which takes the exclusive lock) is an ADR-level ordering rule; "recommended" leaves it open, and `settings set smtp` needs the secrets file while rotation may be replacing it.

- Suggested resolution: Decide the lock (shared instance lock, refused while an exclusive holder runs) and state that `settings set smtp` seals under the `current_data_key_id` read in the same transaction as the write.

### G09-24 [major] The three sibling drafts record "who did it" in three incompatible shapes, and the invite events' audit home is conditional
- Type: B
- Where: docs/adr/0087-invite-only-signup-tokens.md §15 (lines 337, 346, 360), §12 (lines 282–284); docs/adr/0086-instance-settings-persistence.md §1 (lines 43, 49); docs/adr/0085-admin-authentication-bootstrap.md §8 (lines 297, 302), §9.3 (lines 317–322)

## Summary

Counts: blocker 0, major 9, minor 16 (25 findings across 7 ADRs: 0081 9, 0082 1, 0083 2, 0084 1, 0085 6, 0086 3, 0087 3).

Top 5 by importance:
1. **G09-14** (0085, major): the per-instance admin-login (and bootstrap) bucket refuses the real operator with `429` whenever an outsider saturates it — a remote lockout §9.1 itself forbids.
2. **G09-15** (0085, major; also gates 0086's recovery-wait screen): INV-69's per-account security event log (M3, Accepted invariant with a named test) has no ADR at all, so the invariant can be neither met nor verified.
3. **G09-2** (0081 Part B, major): the `vault-membership` statement carries no signer id, and the server verifies against the signer's *current* bundle while readers verify against the key listed in statement `seq − 1`, so the two layers accept different statements after a full rotation.
4. **G09-23** (0087, major): `RIZZY_SIGNUP=invite` widens Accepted text (ADR 0028 item 12 as replaced by ADR 0048 §1) while the ADR claims "Supersedes: none".
5. **G09-3 / G09-1** (0081 Part B, major): Fetch must return statements after a pin the server cannot read (request carries only `membership: bool`), and `vault_join` is checked "as §A3 does", which requires vault epoch 0 and so refuses every join after a rekey.

Also notable: G09-4 (membership healing after restore is left to "the Part B implementation" with no ADR), G09-20 (0086 never says whether its table is in backups), G09-24 (three incompatible actor encodings across 0085/0086/0087).
